## 第5章: 提案手法 SPEC&Project

### 5-01: SPECとProjectに分ける解法全体像（章タイトル）

- 第4章で「好循環を回すには仕組みが必要」と予告しました。ここからその答えです。ただし、大げさなフレームワークではありません。2つの概念だけで回します
- 概念理解で終わらず、日常運用の型に落とすところまでやります。理論ではなく実践の話です
- → では早速、この2つの概念を見ていきましょう。拍子抜けするほどシンプルです

### 5-02: SPECとProjectの役割分担

- **問題提起（上段の課題カードを指しながら）**: 設計書が古くなる。変更理由が消える。案件が変わるたびに文書が切れる。皆さんの現場でも心当たりがあるのではないでしょうか
- **原因の指摘**: これらの問題の根っこは、「今の仕様」と「今回の変更」を1つの文書に同居させていること。目的が違う情報を1つの器に入れているから壊れるんです
- **SPECの定義（左のSPECカードを指しながら）**: SPECは「アプリケーションの最新仕様」。画面、API、DB、型、業務ルールを置き、参照先を常にここに寄せる。古い版や変更理由は持たず、最新仕様だけを残します
- **Projectの定義（右のProjectカードを指しながら）**: Projectは「今回の変更案件」。なぜ変えるか、どう変えるか、どう確認したかをまとめる。要求、設計、実装、試験、報告を束ね、完了後も消さず履歴として持ちます
- **ハードルを下げる**: 新しい文書を増やすのではなく、既存文書を"現在"と"変更"に分けて置き直すだけです。今あるドキュメントを捨てるのではなく、置き場を整理するだけですから
- → では、SPECの中身を具体的に見ていきます。「最新仕様」って具体的に何を置くのか

---

### 5-03: SPECが最新仕様の正しい知識を束ねる役割

- **3つの運用ルール（上段の3つのピルを左から順に指しながら）**: 「最新版だけを持つ」「上書き更新する」「参照先は常に1つ」。この3つがSPECの運用ルールです
- **4レイヤの構成（2×2のグリッドカードをそれぞれ指しながら）**: SPECは4つのレイヤに分かれています。画面/UI、API/Backend、DB/Type/State、Architecture/Rule。それぞれにbasic-designやdetail-designのファイルが置かれます
- **現在断面だけの原則**: 古い状態や変更理由はProjectへ逃がし、SPECには現在断面だけを残す。これが鉄則です。SPECはアプリケーションの"今の姿"を写した鏡だと思ってください
- **コールアウト（下部のコールアウトを指しながら）**: 既存の設計書やAPI仕様書をSPECに移すところから始められます。新しく何かを書く必要はなく、置き場を決めるだけです
- → 次に、もう一方の入れ物、Projectの中身を見ましょう

---

### 5-04: Projectが変更理由と経緯を束ねる役割

- **Projectの正体**: Projectは変更要求を起点に、要求整理から実施報告までを1つのフォルダにまとめた「変更パッケージ」です
- **5つのフェーズ（フェーズカードを左から右へたどりながら）**: 10_requirements（要求整理）、20_basic-design（基本設計）、30_detail-design（詳細設計）、40_test-spec（試験設計）、50_report（実施報告）。番号付きフォルダで時系列が分かります
- **各フェーズの役割**: 背景・目的・スコープを定義し、画面構成やAPI要件を切り、具体的な設計まで落とし、確認方法を決め、最後に結果を残す。この流れが1つのProjectに入ります
- **完了後も消さない**: Projectは完了しても消しません。これが将来の"なぜこう変えたのか"に答える唯一の場所になるからです
- **SPECとの対比**: Projectは"今の仕様"ではなく、"今回どう変えるか"と"どう実施したか"を残すための束です
- **コールアウト（下部のコールアウトを指しながら）**: ドキュメントが増えて負担が増えるのでは？ と思うかもしれません。しかし、これらの文書の多くはAIが下書きします。人間の仕事は妥当性の確認と承認です
- → SPECとProject、2つの入れ物が見えました。では、この2つはどう連携するのか。ここが一番大事なポイントです

---

### 5-05: 差分だけを正しい知識へ戻す更新フロー

  ※間を置いて「ここが最も重要なポイントです」と明言する
- **現在のSPEC（左のステートカードを指しながら）**: 各レイヤの最新版だけを保持した正しい知識。画面仕様、API/Backend責務、DB/型/業務ルールが入っています
- **今回のProject（中央のステートカードを指しながら）**: 1つの変更要求を起点に、requirements、basic-design、detail-design、test-spec/reportまで分解します
- **更新フロー（左から右へフロー矢印をたどりながら）**: Projectから承認された差分だけをSPECに反映する。Projectは消さない。だからSPECは常に最新で、Projectは変更理由の記録として残り続けます
- **2つの役割の対比（下部の2カラムカードを指しながら）**: SPECは常に1つの正しい知識として参照する。Projectは案件ごとに複数残り、変更理由の履歴になる
- 「差分だけを戻す」は、構成管理やリリース管理でやっていることと同じ発想です。文書にもそれを適用するだけです
- → では、このフローの中でAIはどう使い、品質はどう守るのか。「AIに任せて大丈夫か？」という疑問に答えます

### 5-07: AI下書きと人間承認を分ける責任設計

- **原則（上部のプリンシプルバンドを指しながら）**: AIに全部任せるわけではありません。「AIが下書きする、人間が承認する、SPECに反映する」。このフローが全てに一貫する原則です
- **3つのゲート（3列のゲートカードを左から順に指しながら）**:
  - 要求整理 -- AIが叩き台を作成し、人間が妥当性を承認
  - 設計判断 -- AIが設計案を作成し、人間が技術判断を承認
  - SPEC更新 -- AIが更新案を作成し、人間が最終承認
- **役割分担の明確化**: AIは叩き台を高速に作る係、人間は妥当性を判断する係。AIの出力が間違っていても、承認で止まる。だから盲信にはなりません
- **コールアウト（下部のコールアウトを指しながら）**: 皆さんが日々やっているレビューの延長線上です。違いは叩き台をAIが作ること。レビューの質を担保するのは、これまで通り皆さんの経験と判断力です
- → ここまでの話を整理します。SPEC&Projectが、これまで出してきた課題にどう答えるのかを一覧で確認しましょう

### 5-09: SPECとProjectが課題へ答える構造

- **まとめの位置づけ**: ここまでの話を整理します。第2章で見た情報の散在、第3章で見た仕様の陳腐化、第4章で見た好循環。この全てに対してSPEC&Projectは具体的な答えを持っています
- **5つの課題と解法（各行を上から順に指しながら）**:
  - 情報が散在し、矛盾する → SPECを正しい知識に固定し、参照先を1つに寄せる
  - 仕様書が古くなる → 案件完了条件にSPEC更新を入れ、現在断面を維持する
  - 変更理由が失われる → Projectに要求・設計判断・報告を束ねて履歴として残す
  - PJごとに知識が断絶する → 最新SPECを次案件の起点にし、Projectを変更履歴として重ねる
  - AI活用が停滞する → 最新仕様と変更文脈を分けて渡し、好循環を起動する
- **コールアウト（下部のリードカードを指しながら）**: 抽象論ではなく、文書の役割を分けて運用に組み込むことで解ける課題群です。完璧な銀の弾丸ではありませんが、構造的な原因に対する構造的な回答になっています
- → ではこの型が本当に有効なのか。第6章で確認していきます

## 第6章: なぜSPEC&Projectが今の開発に有効なのか

### 6-01: AI出力を左右する文脈密度の考え方

- **第1章の原理に立ち返る**: 第1章でLLMの仕組みを学びましたね。コンテキストウィンドウに何を入れるかで出力が決まる。SPEC&Projectは、まさにこの原理を開発プロセスに実装したものです
- **従来の問題点（左カラムを指しながら）**: 古い仕様、チャット履歴、関連の薄い資料まで混ざる。ノイズが多くLLMの注意が散る。同じモデルでも、ぶれた回答になりやすい
- **SPEC&Projectの強み（右カラムを指しながら）**: 最新仕様と今回の変更要件だけを切り出して渡せる。有用情報の比率が高く、文脈の焦点がぶれない。同じモデルでも、説明の精度と一貫性が上がります
- **「密度」という概念**: 同じトークン数の中に、より多くの有用な情報が詰まっている状態。これがSPEC&Projectの最大の実務的優位性です。従来のやり方が悪いのではなく、AIという新しい消費者に合わせた情報設計が必要になったということです
- → コンテキスト密度を高めることの意味が分かったところで、次はもう少し深い設計思想の話をします。保存すべきものは何か、という問題です

### 6-03: 正しい知識と生成物の保存対象を分ける設計

  ※少し間を取って、重要さを演出する。ここが講義全体の転換点
- **2層分離の提示（上下2層の構造全体を指しながら）**: SSOT層とアウトプット層の2つに分ける。これが設計思想の核心です
- **SSOT層（上段の緑枠カードを指しながら）**: SPECは「現在の正しい知識 -- 仕様・設計・構造」、Projectは「変更の文脈 -- 要件・判断理由・経緯」。この両方が揃って初めてSSOTが成立します
- **アウトプット層（下段の4つのカードを指しながら）**: 目的別にAIが生成する。使い捨てでよい。レビュー資料、新メンバー説明、顧客向け報告、開発用コンテキスト。これらは全てSSOTから必要なときに生成すればよいんです
- **逆転の気づき**: 従来は1つの文書がコミュニケーションと情報管理を兼ねて、両方中途半端だった。この2層分離で役割が明確になります。レビュー資料も新メンバー説明も顧客報告書も、SPECから目的別に自動生成できる。同じ情報を何度も変換する作業が構造的になくなります
- **核心メッセージ**: SSOTが正しければ何度でも再生成できる。成果物は使い捨て、知識だけを守る
- → ここまでの議論を、第0章で見た"ネイティブ"のフレームに当てはめてみましょう。全部つながります

### 6-04: AIネイティブ開発の新しい定義

- **第0章の伏線回収**: 第0章で3つの事例を見ました。インターネットネイティブ、デジタル、クラウド。同じフレームでAIネイティブを整理するとこうなります
- **比較表の読み解き（表の各行を上から順に指しながら）**:
  - インターネット: 配信コスト低下 → 配信制約から探索制約へ → 配信の独占が脱構築 → 検索・発見基盤へ再構築
  - デジタル: 試行コスト低下 → 失敗回避から学習速度へ → 事前最適化が脱構築 → 事後学習ループへ再構築
  - クラウド: 変更コスト低下 → 変更回数最小化から変更単位最小化へ → 変更抑制が脱構築 → 変更の細分化へ再構築
- **AIネイティブ（最下行を強調して指しながら）**: 言語化コスト低下 → 言語化の回避から正しい知識の維持へ → 暗黙知依存・文書化軽視が脱構築 → 正しい知識の一元管理と目的別生成へ再構築
- **伏線の完成**: 第0章で意図的に出さなかった4行目が、ここで完成しました。AIネイティブ開発とは、AI前提で情報管理を組み替えることです
- 脱構築の欄に"暗黙知依存、文書化軽視"とありますが、これは"間違い"ではありません。当時の最適解だった。前提が変わった今、次の最適解に移行する。それがネイティブの本質であり、皆さんが過去にやってきたことと同じです
- → では、今日の講義全体を振り返りましょう。ここからクロージングに入ります

### C-03: 1案件から運用転換を始める

- **2つのアクション（左右のカードを順に指しながら）**:

- **フローピル（下段のトークンロウを左から右へたどりながら）**: 小さく始める → 1回回す → 結果で広げる。この3ステップだけです
- **コールアウト（下部のコールアウトを指しながら）**: 好循環が一度回り始めると、もう情報が散在した状態には戻りにくくなる。やるかどうかは皆さんが判断すること。まず1つのSPECを作り、1つのProjectで更新してみる。結果を見てから次を決める。それがこれまで皆さんが変化を推進してきたときのやり方と同じはずです
  ※間を置く。「皆さんの現場で、最初のSPECにするとしたら何が思い浮かびますか？」と心の中で考えてもらう
