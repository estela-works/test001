# プロット詳細: エージェントAIを利用したシステム開発

## 第0章: AIネイティブ開発とは何か（アイスブレイク）

### 問いかけ

- 「今日のテーマは"AIを活用したシステム開発"ですが、最近よく聞く言葉があります」
- 「**AIネイティブ開発**って、何だと思いますか？」
- （会場に少し考える間を取る）
- よくある想定回答: 「AIをたくさん使う」「Copilotで爆速コーディング」「プロンプトエンジニアリングを駆使する」

### ゆさぶり — 「○○ネイティブ」の本当の意味

- 「インターネットネイティブはネット検索が速い人のことですか？」
- 「クラウドネイティブはAWSに詳しい人のことですか？」
- → どちらも違う。「○○ネイティブ」には共通する構造がある

### 過去の○○ネイティブを振り返る — 「制約→最適化対象→合理的戦略」のフレーム

- 各時代の変化を同じフレームで整理する:
  - **制約**が変わると → **最適化すべき対象**が変わり → **合理的な戦略**が変わる

---

- **インターネットネイティブ（1990年代後半〜）**
  - **最適化対象の変化: 「配信制約の最適化」→「探索制約の最適化」**
  - 旧制約: 配信コスト・複製コストが高い
    - 1対1通信（電話・電報）、1対多配信（新聞・テレビ）、静的な蓄積（電話帳・百科事典）はあった
    - しかし多対多の流通は不可能。蓄積はあっても索引の切り口でしか引けない
    - → 最適化対象: **限られた流通枠の効率利用** → 合理的戦略: ゲートキーパーによる選別（1対多）
  - 新制約: 配信コストが限界費用ゼロに。検索コストも低下
    - → 最適化対象: **情報の発見効率** → 合理的戦略: N対N流通＋検索ベースの発見
  - 脱構造 — 「配信の独占」が価値を失う:
    - 流通の選別者（出版社の中間的編集機能、テレビ局の編成、レコード会社の流通独占）
    - 静的索引ビジネス（電話帳、紙の百科事典）
    - 物理的流通インフラ（CD・DVD小売、新聞販売網・取次）
  - 再構築 — 「探索・発見の最適化」に価値が移る:
    - 検索・ランキング（検索エンジン、SEO、レコメンド）
    - フィルタリング・キュレーション（インフルエンサー、レビュー文化）
    - 直接流通の支援（プラットフォーム: YouTube、Spotify等）
    - 評判の可視化（レーティング、フォロワー経済）

---

- **クラウドネイティブ（2010年代〜）**
  - **最適化対象の変化: 「変更回数の最小化」→「変更単位の最小化」**
  - 旧制約: リソース調達・変更コストが高い
    - サーバー調達に4〜12週間、数千万〜数億円のCAPEX
    - → 最適化対象: **変更回数の最小化** → 合理的戦略: 事前設計・大規模変更・低頻度リリース（CAB承認、四半期リリース）
  - 新制約: 調達が秒単位、従量課金、廃棄コストもゼロ
    - → 最適化対象: **リスク分散（変更あたりの影響最小化）** → 合理的戦略: 小さな変更を高頻度で実施
  - 脱構造 — 「変更抑制」が価値を失う:
    - 重い変更管理プロセス（CAB、四半期リリース承認組織）
    - サーバー調達・設置中心の運用、手作業の構成管理
    - モノリシック前提の設計、Active-Standby中心の"障害ゼロ"冗長構成
  - 再構築 — 「変更の細分化と高速化」に価値が移る:
    - 自動化・コード化（IaC、CI/CD、GitOps）
    - 分割前提の設計（マイクロサービス、コンテナ）
    - 障害前提の設計（Chaos Engineering、Circuit Breaker）
    - 可観測性とリスク制御（SRE、SLO/Error Budget、カナリアリリース）

---

### 共通構造の提示

- 2つの変化を並べるだけでも、同じ論理構造が見える:

  | 時代 | 制約の変化 | 最適化対象の移動 | 失われたもの | 生まれたもの |
  |------|-----------|-----------------|------------|------------|
  | インターネット | 配信コスト↓ | 配信制約 → 探索制約 | 配信の独占 | 探索・発見の最適化 |
  | クラウド | 変更コスト↓ | 変更回数最小化 → 変更単位最小化 | 変更抑制 | 変更の細分化と高速化 |

- **共通する因果構造**:
  ```
  1. 制約が変わる（コスト構造の激変）
  2. 最適化すべき対象が変わる（旧い目的関数が無効化される）
  3. 旧い最適化対象に依存していた仕組み・産業が価値を失う【脱構造】
  4. 新しい最適化対象に対する仕組み・産業が生まれる【再構築】
  5. それを「当たり前」として行動する = ○○ネイティブ
  ```

- **一段抽象化すると:**
  - **価値は「希少だったもの」ではなく「新たにボトルネックになったもの」に移る**
  - 制約が消えると、その周辺の産業は消える。新しいボトルネックに対する産業が生まれる

- **「○○ネイティブ」の本質は、新技術を使うことではない**
- **旧い制約下で合理的だった最適化対象を捨て、新しいボトルネックに対して最適化する世界観で行動すること**

### 伏線 — 今日の講義の予告

- 「では、AIネイティブ開発において、脱構築されるべき"旧い常識"とは何か？」
- 「システム開発の現場には、長年の合理的判断の中で育まれた常識がある」
- 「それは本当に"今も"合理的なのか？」
- 「今日の講義では、その常識を一度解きほぐし、AIがある前提で再構築していきます」

- 「仕組みがわかれば、何が変わり、何が変わらないかが見えてきます」

## 第1章: LLMの基礎

### 導入（つかみ）

- 「ChatGPTやCopilotを使ったことがある人？」→ 会場に問いかけ
- 「便利だけど、期待通りの結果が出ないこともありますよね？」
- なぜそうなるのかを理解するために、まず仕組みを押さえる

### 1-1. LLMの動作原理 — 次のトークン予測

- LLMがやっていることは本質的に1つだけ
  - **「前段の文章をもとに、次のトークン（単語の断片）を予測する」**
  - これを繰り返すことで文章が生成される
- 具体例で示す:
  - 入力: 「日本の首都は」→ 予測: 「東京」→ 予測: 「です」→ ...
  - 前にある文章が変われば、次の予測も変わる
- **「会話」も次のトークン予測にすぎない**
  - 一見AIと会話しているように見えるが、実態は違う
  - AIが見ているのは「Aさんの発話、Bさんの発話、Aさんの発話、...」と続くテキスト
  - その続きとして「次にBさんが言いそうなこと」を予測しているだけ
  - 会話を理解しているのではなく、会話パターンの文章の次を予測している
- この原理が意味すること:
  - LLMは「前段の文章」に完全に依存している
  - 前段に正しい情報があれば正しく予測する
  - 前段に間違った情報があればそれに引きずられる
  - → **渡す情報（コンテキスト）が全てを決める**という結論への伏線

### 1-2. AIエージェントでも消えない文脈上限

- 現在のAIエージェントは、長い仕事を継続しているように見える
- しかし「セッション継続」と「全部を覚えている」は別問題
- 一度に参照できる文脈量には上限がある
- 長い履歴はそのまま無限に使えるわけではない
  - 必要情報の選別
  - 要約
  - 再投入
- → **AIエージェントも文脈上限から自由ではない**

### 1-4. コンテキストウィンドウ

- LLMが一度に処理できる情報量には上限がある
- この枠＝コンテキストウィンドウ
- 枠の中に何を入れるかで、出力が大きく変わる
- 例え話：「試験で持ち込み可能なカンペ」
  - カンペの内容が正確なら良い答案が書ける
  - 間違いだらけのカンペなら答案も間違う
  - そもそもカンペが白紙なら、記憶（学習データ）頼みになる
- → 大事なのは「枠が大きいか」だけでなく、**限られた枠へ何を入れるか**

### 1-5. コンテキストの質が出力の質を決める

- 良いコンテキストの3条件
  - **正確**: 事実として正しい
  - **一貫**: 矛盾がない
  - **最新**: 古い情報が混ざっていない
- 同じモデルでも、渡す情報で結果が劇的に変わるデモがあると効果的
- 有限な枠だからこそ、3条件を満たす情報だけを厳選して入れる必要がある
- **この章の結論**: AIの能力を引き出すには「何を渡すか」と「どこまでを一度に頼むか」が全て

### 1-6. 原理から導かれる活用ノウハウ

- 動作原理を理解すると、やってはいけないことが自然に見えてくる
- **セッション継続と依頼スコープは別に考える**
  - 会話が続いていても、一度に抱え込む仕事が大きいほど文脈上限にぶつかる
  - 設計、実装、調査、レビューを全部一度に頼むほど不安定になる
  - 対策: 問題ごと、成果物ごと、判断ごとに依頼を小さく切る
- **現在のAIエージェントは役割分担で安定させる**
  - 探索、確認、整理、実装を一つの文脈へ全部載せない
  - メインは本題の推論、補助は探索や確認、返すのは結果だけ
  - 対策: メインエージェントとサブエージェントで文脈を分ける
- **まとめ: コンテキストは「短く・集中・クリーン」に保つ**
  - 原理を知ると、依頼スコープを小さく切るべき理由まで自然に見える
  - 「AIが使えない」のではなく「枠内に収まる仕事設計ができていない」ことが多い

## 第2章: LLMによる開発の課題

### 導入 — 第1章から導かれるAI活用の原則

- 第1章で「前段の文章をもとに次のトークンを予測する」という原理を学んだ
- この原理から、AIに最大限の能力を発揮させるための条件が導き出せる:
  - **必要な情報だけに絞って渡す** — 余分な情報は推論のノイズになる
  - **情報同士が矛盾しない** — 矛盾があるとどちらに基づいて予測すべきか定まらない
  - **問題解決に無関係な情報を含めない** — 不要な文脈を拾って推論がぶれる
- つまり「正確で、一貫していて、必要最小限の情報」を渡すことがAI活用の大原則
- **では、システム開発の現場でこの原則は守れているか？**

### 2-1. 開発現場の情報はどうなっているか

- 現実を見ると、先ほどの原則がことごとく破られている
- **情報が散在している** — 必要な情報に絞れない
  - 設計書（Word/Excel）
  - コード上のコメント
  - チャット（Slack/Teams）での合意事項
  - 議事録
  - 個人のメモ
  - どれが最新かわからない、人によって参照するソースが違う
- **情報が矛盾している** — 一貫性がない
  - 設計書とコードの仕様が食い違っている
  - チャットで合意した変更がドキュメントに反映されていない
  - 古い情報と新しい情報が区別なく混在している
- **余分な情報が多すぎる** — 必要最小限にならない
  - 過去の検討経緯、却下された案、古いバージョンの仕様が整理されずに残っている
  - どれが「今の正しい情報」か判別するだけで大きなコスト

### 2-2. この状態でAIに渡すと何が起きるか

- 散在した情報をかき集めてプロンプトに入れる
- しかし第1章の原理を思い出してほしい:
  - LLMはコンテキスト内の全てのトークンの越しに次を予測する
  - 矛盾した情報があれば、出力も矛盾する
  - 古い情報が混ざれば、古い仕様に基づいた回答が返る
  - 余分な情報が多ければ、関係ない文脈に引きずられる
- → 「AIが使えない」のではなく「原則を満たせる情報が用意できていない」

### 2-3. 根本原因: SSOT（Single Source of Truth）の欠如

- なぜ原則を満たせないのか？ → 情報管理の仕組みが壊れているから
- 同じ事実が複数箇所に書かれている（情報の重複）
- 一方を更新しても他方が更新されない（情報の乖離）
- どれが正（権威あるソース）かが定義されていない
- 実はこの問題には名前がついている: **SSOT — Single Source of Truth**
  - データ管理の分野で確立された原則
  - 1970年、Edgar F. Codd がリレーショナルモデルで「データの重複排除」を理論化（正規化）
  - 1992年、Bill Inmon が *"Building the Data Warehouse"* でエンタープライズ全体の「単一の信頼できるデータソース」を体系化
  - データ管理の業界標準 DAMA-DMBOK でも中核原則として定義されている
  - 定義: **「あらゆる情報要素は、システム全体でただ一つの場所にのみ管理され、他はそこを参照する」**
- この原則が守られていれば:
  - 必要な情報はそのソースを見ればよい（絞れる）
  - 1つしかないから矛盾しない（一貫する）
  - 余分な重複情報がない（最小限になる）
- SSOTはデータベース設計では当たり前に実践されている
  - しかし「システム開発プロジェクトの情報管理」には適用されてこなかった
  - 設計書、仕様書、ナレッジ...プロジェクト情報のSSOTは存在しない
- 現状はこの原則が守られていない → AI活用以前に、人間同士のコミュニケーションでも問題が起きている

### 2-4. なぜSSOTが成立しないのか — 情報管理とコミュニケーションの目的の違い

- SSOTの必要性は理解できた。ではなぜ実現できないのか？
- 根本的な原因: **人間が作るドキュメントは「コミュニケーション」に最適化されている**
- レビュー資料、報告書、説明資料を作るとき、人間は無意識にこうしている:
  - 相手が既に知っている情報は省く
  - 相手が知らない背景を足す
  - 今回の論点に関係ない部分を削る
  - 理解しやすい順序に並べ替える
- つまり、人間が作るドキュメントは常に**SSOTの部分集合＋文脈依存の調整**
- **コミュニケーション最適化と情報管理最適化は目的が違う**
  - コミュニケーション最適化: 相手・場面に合わせて情報を取捨選択する（不完全でよい）
  - 情報管理最適化: 完全・正確・構造化された情報を維持する（相手に関係なく網羅的）
  - 1つの文書でこの2つを同時に満たすことはできない
- **結果として、開発現場のドキュメントはどちらの目的も中途半端に満たす**
  - レビュー資料としては情報が多すぎ（コミュニケーションに不要な部分がある）
  - SSOTとしては情報が足りない（コミュニケーションのために省略された部分がある）
  - どちらにも使えない文書が量産される → これが情報の散在・矛盾の温床
- → SSOTを実現するには、「情報を保管する行為」と「情報を伝える行為」を分離する必要がある

## 第3章: システム開発手法の歴史的課題

### 導入

- 情報管理の問題は開発者のスキル不足ではない
- 業界全体が合理的な判断のもとで、情報管理より開発に注力してきた歴史がある
- それはなぜか？ そしてなぜ今、変わる必要があるのか？

### 3-1. 「0→完成」に最適化された開発手法

- 2つの主要アプローチは、不確実性への対処方針が異なる
- **ウォーターフォール — 検討で不確実性を減らすアプローチ**
  - 抽象概念から具体へ段階的に落としていく行為
  - 要件定義→設計→実装→テスト→納品
  - 前提: 検討（分析・設計）によって不確実性を十分に減らせる案件に向く
  - 検討のコストパフォーマンスが高い場合に最適な手法
- **アジャイル — 作ることで不確実性を減らすアプローチ**
  - 重要な部分から先に製作していく行為
  - 前提: 検討だけでは不確実性を減らしきれない（作ってみないとわからない）
  - だから小さく作り、フィードバックを得て、方向修正する
  - 検討コストより試作コストの方が合理的な場合に最適な手法
- **共通する課題: 情報管理の仕組みは「完成時点」を想定している**
  - 注意: ここで言いたいのは「手法そのものが継続開発を想定していない」ではない
  - アジャイル、特にスクラムは思想として継続的進化を許容している（プロダクトバックログは本質的に終わらないリスト）
  - しかし、**情報管理の仕組み**に注目すると景色が変わる:
    - ウォーターフォール: 設計書は「納品時点の成果物」として完成する。改修時の更新プロセスは手法に組み込まれていない
    - アジャイル: 各スプリントの成果物は「動くソフトウェア」。仕様の継続的な文書化は手法の関心外
  - どちらも「コードを完成させる・進化させる」プロセスは手厚いが、「情報を最新に保ち続ける」プロセスは手法として定義されていない
- **つまり、開発手法は進化したが、情報管理は置き去りになった**
  - システムは継続的に進化する前提になった
  - しかし仕様書・設計書・ナレッジを継続的に最新化する仕組みは、どの手法にも組み込まれていない
  - 結果として、コードは進化するが情報は劣化する

### 3-2. 継続的バージョンアップへの手当ての薄さ

- **既存手法が手厚くケアしている領域**
  - 新規開発時の設計プロセス
    - 要件定義の手法、設計パターン、レビュープロセスなど豊富な知見がある
  - テスト戦略
    - 単体テスト、結合テスト、E2Eテストなど体系化されている
    - TDD、BDDなどテストを起点にした開発手法も確立
  - リリース管理
    - CI/CD、ブランチ戦略、デプロイ手順の標準化
  - → これらは「完成に向かう工程」を支えるプラクティスとして成熟している
- **手薄な領域: 「完成の後」に必要なこと**
  - 仕様の継続的な最新化
    - 初版の設計書は作る。しかし改修のたびに設計書を更新する仕組みがない
    - 3回目の改修で設計書と実態が乖離し、5回目にはもう誰も設計書を見ない
    - コードが唯一の真実になるが、コードからは「なぜこう設計したか」は読み取れない
  - 変更の文脈（なぜ変えたか）の構造的な蓄積
    - gitのコミットログやチケットに断片的に残るが、構造化されていない
    - 「この仕様はなぜこうなっているのか」→ 当時のメンバーに聞くしかない
    - そのメンバーが異動・退職すると、理由ごと失われる
  - 長期にわたる情報の一貫性維持
    - 初期は設計書・コード・テストが整合している
    - 改修を重ねるたびに少しずつ乖離が広がる
    - ある時点で「正しい情報がどこにあるかわからない」状態に陥る
    - 第2章で見たSSOTの欠如が、ここで構造的に発生している

### 3-3. XPとアジャイル宣言 — 組織パフォーマンスの最適化

- エクストリームプログラミング（XP）の登場背景
  - 1990年代後半、肥大化するドキュメント管理への反発
  - 「正しく管理する」コストがあまりに高い
  - ドキュメントを書いても、すぐ陳腐化する
  - → それなら「動くコードを唯一の真実にしよう」
- アジャイル宣言（2001年）
  - 「包括的なドキュメントよりも動くソフトウェアを」
  - これは**組織パフォーマンスを最大化するための最適化**だった
- **メンバーのリソースを最も価値ある活動に集中させる戦略**
  - エンジニアの時間は有限のリソース
  - 当時の技術水準では、情報管理は「人間が手作業で」行うしかなかった
  - ドキュメント作成・更新・整合性維持に費やす時間は膨大
  - その時間を開発・テスト・フィードバックサイクルに振り向けた方が、成果物の品質もスピードも上がる
  - → 情報管理を必要最低限に絞り、メンバーの力を開発に集中させることでチームの生産性を最大化した
- これは**怠慢ではなく、合理的なトレードオフ判断**
  - 限られたリソースをどこに配分するかの経営判断
  - 「情報管理をしない」のではなく「コストに見合う最小限の管理に留めた」
  - ペアプログラミング、スタンドアップ、レトロスペクティブなど、ドキュメントに頼らない知識共有の仕組みで補完した
  - 結果として、当時の条件下では最も効率的な開発手法として広く成功した
- **ただし、このトレードオフには構造的な限界がある**
  - メンバーの記憶と口伝に依存する知識共有はスケールしない
  - コード以外の情報（設計意図、変更理由、業務知識）は蓄積されない
  - 新メンバーのオンボーディングコストが高い
  - 「なぜこうなっているか」がコードからは読み取れない
  - 長期運用になるほど、失われた情報の代償が大きくなる

### 3-4. スクラム — 暗黙知を肯定した開発プロセス

- スクラムは3-3のXP/アジャイルの流れをさらに推し進めた手法
- **スクラムの本質: 暗黙知でチームを回すことを前提とした工程**
  - デイリースクラム: 文書ではなく対話で状況を共有する
  - スプリントレビュー: 動くものを見せて合意を取る。仕様書ではなくデモが真実
  - レトロスペクティブ: 振り返りの知見はチームの記憶に蓄積される
  - プロダクトバックログ: 要求の優先順位はPOの頭の中にある。リストはその影にすぎない
- **これは「暗黙知をネガティブに捉えない」という割り切り**
  - 形式知化（ドキュメント化）にコストをかけるより、チーム内の暗黙知を高速に回す方が生産的
  - 少人数のチームが密にコミュニケーションすれば、暗黙知で十分回る
  - 最高に自己組織化したスクラムチームは阿吽の呼吸で開発が終わる。これがスクラムの理想形
  - 3-3で見たXPと同じ思想: メンバーの力を情報管理ではなく開発に集中させる
- **暗黙知で回すことの合理性と限界**
  - 合理性:
    - チームが安定していれば非常に効率的
    - ドキュメント作成・メンテナンスの負荷がない分、開発速度が上がる
    - 対面・リアルタイムのコミュニケーションは情報伝達の帯域が最も広い
  - 限界:
    - 暗黙知はチームの外に持ち出せない（別チーム・後任・AIに渡せない）
    - メンバーが抜けると知識ごと失われる
    - チームが大きくなると暗黙知の共有コストが急増する
    - そして — **AIは暗黙知を読めない**
- **AIの時代における暗黙知の問題**
  - AIにとってコンテキストは「明示的に渡されたテキスト」が全て
  - チームの暗黙知がどれだけ豊かでも、AIのコンテキストウィンドウには載らない
  - 暗黙知で回すチーム ＝ AIに渡せる情報が少ないチーム
  - → 暗黙知の肯定は、人間だけで開発していた時代の最適解だった
  - → AIを活用する時代には、暗黙知を形式知に転換する仕組みが必要になる

### 3-5. この章のまとめ

- 情報管理を後回しにしたのは、組織パフォーマンスを最大化するための合理的な判断だった
- XPは情報管理を最小限にし、スクラムは暗黙知で回すことを理想形にまで高めた
- しかしその結果、継続開発に必要な形式知の蓄積が仕組み化されなかった
- これはコストの問題であって、意志の問題ではない
- → コスト構造が変われば、判断も変わるはず

### → 第4章への橋渡し

- 「コストが問題なら、コストが変われば話が変わる」
- 「AIの登場により、まさにそのコスト構造が激変している」

## 第4章: AIが変える情報管理のコスト構造

### 導入

- 第3章で見てきたこと:
  - 開発手法は情報管理より開発に注力する合理的な選択をしてきた（3-3）
  - スクラムは暗黙知で回すことを前提にした理想形を追求した（3-4）
  - どちらも「情報管理のコストが高すぎた」ことが根本にある
- AIの登場により、この前提が崩れつつある

### 4-1. 情報の記載・更新コストの劇的な低下

- AIによるドキュメント生成
  - コードから仕様書を生成
  - 変更差分から更新箇所を特定・反映
  - 自然言語での記述をAIが代行
- 人間の役割の変化
  - 「書く人」→「確認・レビューする人」へ
  - 0→1で書き起こす負荷と、生成されたものを確認・修正する負荷では桁が違う
- **ただし、コストが0になるわけではない**
  - 第1章で見たとおり、LLMは確率的に予測しているだけで事実確認はしない
  - AIが生成した情報の正確性を人間が確認するコストは残る
  - しかし重要なのは、かつてのトレードオフの**バランスが大きく変わった**こと
- かつてのトレードオフが崩れる
  - 以前: 情報管理コスト ＞＞ 開発コスト → 情報管理を諦めるのが合理的だった
  - 現在: 情報管理コストが劇的に下がり、管理する方が合理的な領域が広がった
  - XPが諦めた「正しく管理する」が、現実的なコストで可能になりつつある

### 4-2. 暗黙知を形式知に転換できる時代

- 第3章で見た問題を思い出す:
  - 暗黙知はチームの外に持ち出せない（3-4）
  - メンバーが抜けると知識ごと失われる（3-3）
  - AIは暗黙知を読めない（3-4）
- AIが形式知化のコストを下げることで、この構造が変わる
  - コードの変更意図 → AIが変更差分から設計判断を文書化
  - チーム内の口頭合意 → 要点をAIが構造化して記録
  - 属人的なノウハウ → AIとの対話を通じて形式知に変換
- **暗黙知の肯定を否定するのではない**
  - 阿吽の呼吸で開発できるスクラムチームの価値は変わらない
  - しかし、その阿吽の呼吸を形式知としても残せるようになった
  - 人間同士の暗黙知 ＋ AIが読める形式知 ＝ チーム能力の拡張

### 4-3. 好循環のフライホイール

- ここで第1章の知識が活きる
- ループ構造:
  ```
  適切な情報管理（形式知の蓄積）
      ↓
  良質なコンテキストをAIに提供
      ↓
  AIの出力品質が向上
      ↓
  AIが情報管理をさらに効率化
      ↓
  さらに適切な情報管理 → ...（加速）
  ```
- **好循環に入るかどうかは「情報管理」が分岐点**

### 4-4. この章のまとめ

- AIにより情報管理コストが劇的に下がり、「管理する方が得」の時代が来ている
- 暗黙知を形式知に転換し、AIと共有できる基盤を作ることが鍵
- 好循環を回す仕組みを作れば、チーム全体の生産性が飛躍的に向上する
- では具体的にどう仕組み化するか？

### → 第5章への橋渡し

- 「好循環を回すには、情報管理の"型"が必要」
- 「そこで提案するのがProject/SPEC方式です」

## 第5章: 提案手法 — SPEC&Project

### 導入

- 第1〜4章で示した問題と可能性を、具体的な手法に落とし込む
- 必要なのは大げさなフレームワークではなく、シンプルな「型」
- 2つの概念だけで、これまでの課題をすべてカバーする

### 5-1. 2つの管理対象の定義

- **SPEC（最新断面の仕様）**
  - システムの「今の正しい姿」を記述したもの
  - 常に最新に保たれる唯一の真実 — 第2章で見たSSOTそのもの
  - 含まれるもの: アーキテクチャ、API仕様、データモデル、業務ルール、etc.
  - 特徴: 上書き更新される。過去の状態はSPECには残さない
  - → 第3章の「3回目の改修で設計書と実態が乖離する」問題の解決策
- **Project（変更行為）**
  - 「何を・なぜ・どのように変えるか」を記録する単位
  - 変更の文脈（背景・目的・判断理由）を保持する
  - 含まれるもの: 要件、設計、実装記録、テスト結果
  - 特徴: 完了しても消さない。変更履歴として蓄積される
  - → 第3章の「メンバーが抜けると理由ごと失われる」問題の解決策

### 5-2. SPECとProjectの関係

- SPECは「今」を、Projectは「変化」を管理する
- 例え話:
  - SPECは「地図の最新版」→ 常に現在の地形を反映
  - Projectは「工事記録」→ いつ・なぜ・どう地形を変えたか
- 両方あることで:
  - AIには最新のSPECを渡せば正確な回答が得られる（第1章: コンテキストの質＝出力の質）
  - 「なぜこうなっているか」はProject履歴をたどれる（暗黙知の形式知化）
  - SSOT（第2章）がSPECにより実現される
- **第3章で見たプロジェクト間の断絶を解消する**
  - 従来: プロジェクトAの成果物とプロジェクトBの成果物に連続性がない
  - Project/SPEC方式: どのProjectもSPECを起点に始まり、SPECを更新して終わる
  - SPECが「バトン」の役割を果たし、プロジェクトをまたいで情報が受け継がれる

### 5-3. 運用サイクル

```
1. Projectを立ち上げる
   - 変更の目的とスコープを定義
   - 現在のSPECを参照して要件・設計を記述
   - AIはSPECを読んで「今の姿」を正確に把握した上で支援

2. 実装を進める
   - AIはSPEC + Project（設計方針）をコンテキストに開発を支援
   - Projectに設計判断・進捗を記録

3. 実装完了・レビュー
   - 成果物の確認
   - Projectに結果を記録
   - 変更内容をSPECへ反映する

4. 次のProjectへ
   - 蓄積されたSPECとProject履歴が次の開発を加速
   - 新しいProjectは最新のSPECから始まる → 情報の断絶が起きない
```

### 5-4. なぜ品質が維持されるのか

- 「AIが更新したSPECが間違っていたら？」という懸念への回答
- **SPECの更新は必ず人間がレビューする**
  - AIは変更内容からSPECの更新案を生成する（コスト削減）
  - 人間が内容を確認して承認する（品質保証）
  - 0→1の執筆コストはAIが吸収し、人間は確認に集中する
- **好循環が品質を自己強化する**
  - SPECの品質が高い → AIの出力品質が高い → SPEC更新案の品質も高い → レビュー負荷が下がる
  - 回すほどSPECの品質が上がり、レビューが楽になる
- **悪循環に入った場合の検知**
  - AIの出力がおかしい → SPECを疑う → 修正する → 品質が回復
  - SPECが唯一のソースだからこそ、問題箇所の特定が容易

### 5-5. この方式がもたらす効果（課題へのアンサー）

- **SSOT（第2章）の実現**
  - SPECが唯一の権威あるソース
  - 「どれが最新？」問題が消える
  - 第1章の3条件（正確・一貫・最新）をSPECが満たす
- **暗黙知の形式知化（第3章3-4）**
  - スクラムチームの阿吽の呼吸はそのままに
  - その知識がSPEC/Projectとしても残る
  - AIもチームの知識にアクセスできるようになる
- **プロジェクト間の連続性（第3章3-2）**
  - SPECがバトンとなり、プロジェクトを重ねるほど情報が蓄積される
  - 従来の「プロジェクトを重ねるほど情報が劣化する」が逆転する
- **好循環のフライホイール（第4章4-3）**
  - 最新のSPECをコンテキストとして渡す → 高品質な出力
  - 高品質な出力 → さらなる情報管理の効率化
- **開発チームの能力拡張**
  - AIが正確な情報をベースに作業 → 手戻り減少
  - 人間は判断と確認に集中できる
  - 新メンバーはSPECを読みProjectを追えば、チームの歴史を理解できる

## 第6章: なぜSPEC&Projectが今の開発に有効なのか

### 導入

- 第5章で手法を紹介した。では具体的に何がどう良くなるのか？
- コンテキスト密度と情報の2層分離という観点から有効性を示す

### 6-1. コンテキストの密度が上がり、AIの性能が上がる

- **SPEC&Projectの最大の武器: 情報の適切な分割と正確性**
- 第1章の原理を思い出す:
  - LLMは前段の文章をもとに次を予測する
  - 渡す情報の質＝出力の質
- SPEC&Projectでは:
  - SPECは「今の正しい姿」だけが書かれている（余分な情報がない）
  - Projectは「この変更に関する情報」だけが書かれている（他の話題が混ざらない）
  - → AIに渡すコンテキストが**必要な情報だけに絞られ、かつ正確**
- **コンテキストの密度が上がる**とは:
  - 同じトークン数の中に、より多くの有用な情報が詰まっている状態
  - ノイズ（古い情報、矛盾、無関係な文脈）が排除されている
  - LLMの注意が正しい情報に集中する → 推論精度が上がる
- 具体例:
  - API仕様を変更する案件で、AIに渡すもの:
    - 従来: 散在した情報をかき集めた大量のテキスト（ノイズまみれ）
    - SPEC&Project: `specs/api/対象API.md`（最新仕様）+ `projects/今回の案件/requirements.md`（変更要件）
    - 同じAIモデルでも、後者の方が圧倒的に精度が高い

### 6-2. 課題「情報管理とコミュニケーションの両立」（第2章2-4）へのアンサー

- **課題**: 人間のドキュメントはコミュニケーションに最適化されており、SSOTとしては不完全
- **アンサー**: SSOT層（情報基盤）とアウトプット層（目的別ドキュメント）を分離する
- **SSOT層 = SPEC**
  - 完全・正確・構造化された情報を保管する
  - 人間が直接読むためのものではなく、情報を正しく維持するためのもの
  - AIはここを参照すれば正しい情報を得られる
- **アウトプット層 = 目的に応じてAIが生成するドキュメント**
  - SSOTからAIが必要な情報をピックアップし、目的に合わせて調整する
  - 例:
    - レビュー用資料: 論点に関連するSPECだけを抽出し、変更差分を強調
    - 新メンバー向け説明: 前提知識から丁寧に、SPECの全体像を俯瞰して解説
    - 顧客向け報告書: 技術詳細を省き、成果と影響に焦点
    - 開発時のコンテキスト: 該当箇所のSPECと関連Projectを抽出
  - これらは「使い捨て」でよい。SSOTが正しければいつでも再生成できる
- **従来の問題がなぜ解決するか**:
  - 従来: 1つの文書がコミュニケーションと情報管理を兼ねる → 両方中途半端
  - SPEC&Project: 情報管理はSPECが担う。コミュニケーションはAIがSPECから生成する → 役割分離
  - SSOTは汚れない。目的別ドキュメントは必要なときに必要な形で生成される

### 6-3. テンプレートによるSSOTの構造維持

- SPEC&Projectの品質を支えるもう一つの武器: **テンプレート**
- **テンプレートがAIのぶれを抑え込む**
  - AIは自由に書かせると、毎回異なるフォーマット・構成で出力する
  - テンプレートを渡すことで「この構造で書け」と制約をかけられる
  - 第1章の原理: テンプレートのトークンが前段に入ることで、出力パターンが強く制約される
  - → AIの出力がぶれない。構造が統一される
- **構造としてSSOTを維持する設計**
  - SPECのテンプレート: API仕様、DB仕様、画面仕様などの記述フォーマットを定義
    - 全案件で同じ構造のSPECが書かれる → 比較・差分検出が容易
    - AIが更新するときも構造が崩れない
  - Projectのテンプレート: 要件→基本設計→詳細設計→テスト→報告の各フェーズのフォーマットを定義
    - 「何を書くべきか」がテンプレートに定義されている → 情報の抜け漏れがない
    - どのProjectも同じ構造で記録される → 案件横断で比較・検索できる
- **テンプレートは「AIへの構造的な指示書」として機能する**
  - 人間にとってのテンプレート: 何を書けばいいか迷わない
  - AIにとってのテンプレート: 出力フォーマットの制約 → ぶれを抑制
  - 両方にとって: 情報の構造が統一される → SSOTの一貫性が維持される
- 実例: このリポジトリの `docs/projects/template/`
  - 要件定義〜テスト仕様〜作業報告まで全フェーズのテンプレートが整備されている
  - 11案件すべてが同じ構造で記録されている → 一貫性が保たれている

  - AIの登場でコスト構造が変わり、形式知化のコストが劇的に下がった（第4章）

  - コンテキスト密度の向上と、SSOT層・アウトプット層の分離が有効性の核心（第6章）
- **核心メッセージ**:
  - AIの能力を引き出すために情報を整備するのではない
  - 情報を整備する行為自体をAIが支援してくれる
  - 適切に分割された正確な情報が、AIの性能を引き上げる
  - だから「まず始める」ことが大事
- **呼びかけ**:
  - 「まずは小さく始めてみてください」
  - 「1つのSPECを作り、1つのProjectで更新してみる」
  - 「好循環が回り始めると、もう戻れなくなります」
