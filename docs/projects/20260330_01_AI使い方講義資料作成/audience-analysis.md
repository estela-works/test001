# 聴講者心理分析: セクション別 既知・未知・ストレス怒り・ワクワク

## 想定ペルソナ

**技術情報に明るい正義感の強い若手**

- ChatGPT/Copilotは使ったことがある
- DB正規化やCI/CDなど基礎的な技術概念は理解している
- アジャイル/スクラムの基本は知っている
- 「正しいことが正しく行われていない」状況に苛立ちを感じるタイプ
- 行動力があり、自分が変えたいという意志がある

## 第0章: AIネイティブ開発とは何か（アイスブレイク）

### 問いかけ — 「AIネイティブ開発って何だと思いますか？」

| 観点 | 内容 |
|------|------|
| **既知** | 「デジタルネイティブ」「インターネットネイティブ」「クラウドネイティブ」という言葉自体は聞いたことがある。技術に明るいのでクラウドネイティブは実務で触れている可能性も高い |
| **未知** | 「○○ネイティブ」を統一的な構造（旧トレードオフの脱構築→新前提での再構築）として捉える視点 |
| **ストレス・怒り** | なし。アイスブレイクなのでリラックスした状態。ただし「AIネイティブ＝AIをたくさん使うこと」と安易に答えそうになる自分への軽い気恥ずかしさ |
| **ワクワク** | 「○○ネイティブの本質は技術を使うことではない」という切り口の新鮮さ。「自分が知ってるつもりの概念に、こんな深い構造があったのか」という知的興奮 |

### ゆさぶり — 過去の○○ネイティブの振り返り

| 観点 | 内容 |
|------|------|
| **既知** | 各ネイティブの「旧世代の常識」と「今の当たり前」は知っている（図書館→検索、専用機→スマホ、オンプレ→クラウド） |
| **未知** | その変化が「コスト構造の激変→旧トレードオフの崩壊→脱構築→再構築」という同一パターンで説明できること |
| **ストレス・怒り** | なし。むしろ過去のネイティブは「もう当たり前」として受け入れているので、安心して聞ける領域 |
| **ワクワク** | パターンが見えてくる面白さ。技術者はパターン認識が好き。「じゃあAIネイティブもこのパターンで…？」という推論が走り始める |

### 共通構造の提示 — 脱構築と再構築

| 観点 | 内容 |
|------|------|
| **既知** | 個々のネイティブの変化は知っている |
| **未知** | 5ステップの共通構造としての定式化。「ネイティブとは、新技術を使う人ではなく、新しいトレードオフの上に再構築した世界観で行動する人」という定義 |
| **ストレス・怒り** | なし。ただし「では自分はAIネイティブか？　単にAIを使っているだけではないか？」という内省的な緊張感 |
| **ワクワク** | **強いワクワク**。「脱構築されるべき旧い常識って何だろう？」という問いが頭に残る。講義全体を通じて答え合わせをする楽しみが生まれる。正義感の強い若手は「旧い常識を壊す」というフレーミングに特に惹かれる |

### 伏線 — 今日の講義の予告

| 観点 | 内容 |
|------|------|
| **既知** | なし（ここからが本題） |
| **未知** | 「システム開発の現場には、脱構築されるべき常識がある」という予告 |
| **ストレス・怒り** | 「自分たちの常識が間違っているかもしれない」という健全な不安。ただし正義感から「間違っているなら正したい」という前向きな緊張 |
| **ワクワク** | 「今日の講義で答えがわかる」という期待感。全体の地図が見えたことで安心して聴ける準備が整う |

## 第1章: LLMの基礎

### 1-1. LLMの動作原理 — 次のトークン予測

| 観点 | 内容 |
|------|------|
| **既知** | ChatGPT/Copilotの存在、使ったことがある、「なんか賢い」くらいの理解 |
| **未知** | 「全部が次のトークン予測に過ぎない」という還元的理解。会話も予測の連鎖であるという事実 |
| **ストレス・怒り** | 特になし。ただし「え、会話を理解してないの？」という軽い衝撃・裏切り感 |
| **ワクワク** | 「仕組みがわかればハックできそう」という技術者的好奇心。原理がシンプルなことへの知的快感 |

### 1-2. LLMの特性

| 観点 | 内容 |
|------|------|
| **既知** | ハルシネーションという言葉、「AIが嘘をつく」現象は体験済み |
| **未知** | ハルシネーションがトークン予測の原理から「当然の帰結」であるという構造的理解 |
| **ストレス・怒り** | 「知ってたけど、なんでそうなるかまでは考えてなかった」という自分への軽い悔しさ |
| **ワクワク** | 原理から特性が導出できる＝予測可能＝制御できるかもしれないという期待 |

### 1-4. コンテキストウィンドウ

| 観点 | 内容 |
|------|------|
| **既知** | トークン制限がある、長すぎると入らないという断片的知識 |
| **未知** | 「枠の中身の質がそのまま出力の質になる」というダイレクトな因果関係 |
| **ストレス・怒り** | なし。カンペの例えで直感的に腹落ちするフェーズ |
| **ワクワク** | 「じゃあカンペを良くすればいいだけじゃん」という手が打てる感覚 |

### 1-5. コンテキストの質が出力の質を決める

| 観点 | 内容 |
|------|------|
| **既知** | 「プロンプトが大事」という漠然とした理解 |
| **未知** | 「正確・一貫・最新」という3条件の明確化。モデル性能ではなく入力が本質という逆転 |
| **ストレス・怒り** | 「今まで"AIが悪い"と思ってたけど、自分の渡し方の問題だったのか…」というモヤモヤ |
| **ワクワク** | モデルを変えなくても結果が劇的に変わるという実践的希望 |

### 1-6. 原理から導かれる活用ノウハウ

| 観点 | 内容 |
|------|------|
| **既知** | 「セッション長いと精度落ちる気がする」という経験則。話題は分けた方がいいらしいという噂レベルの知識 |
| **未知** | それが「全て前段のトークン越しに予測する」原理から論理的に導出できること。検索・チェック行為もコンテキスト汚染になるという認識 |
| **ストレス・怒り** | 「自分がやってた使い方、全部コンテキスト汚してたのか…」という反省。正義感の強い若手ほど「正しい使い方を知らなかった」ことにストレスを感じる |
| **ワクワク** | ノウハウが原理から演繹できる＝暗記ではなく理解で戦える、という知的充足感 |

## 第2章: LLMによる開発の課題

### 2-1. 開発現場の情報はどうなっているか

| 観点 | 内容 |
|------|------|
| **既知** | 設計書とコードが食い違っている現実。Slackでの合意がドキュメントに反映されない経験。「どれが最新かわからない」日常 |
| **未知** | これが第1章の「3条件（正確・一貫・最新）」をことごとく破っているという構造的な対応関係 |
| **ストレス・怒り** | **ここが最初の怒りポイント**。「散らかってるのわかってるのに、誰も直そうとしない」「先輩たちはなぜこれを放置してきたのか」という正義感からの苛立ち |
| **ワクワク** | 問題が明確に言語化されたことへの「やっぱりそうだよな」という共感の気持ちよさ |

### 2-2. この状態でAIに渡すと何が起きるか

| 観点 | 内容 |
|------|------|
| **既知** | AIに雑に情報を渡すとダメな結果が返ってくる体験 |
| **未知** | 「AIが使えない」のではなく「原則を満たす情報が存在しない」という問題の再定義 |
| **ストレス・怒り** | 「AIのせいじゃなく、組織の情報管理のせいだったのか」という怒りの矛先の転換。正義感の強い若手は「正しいものが正しく使われない」状況に特にフラストレーションを感じる |
| **ワクワク** | 問題の所在が明確になった＝解ける問題になった、という希望 |

### 2-3. 根本原因: SSOT（Single Source of Truth）の欠如

| 観点 | 内容 |
|------|------|
| **既知** | DB正規化の概念（技術に明るいので知っている）。「情報が重複してると困る」という直感 |
| **未知** | SSOTという名前と歴史（Codd、Inmon、DAMA-DMBOK）。DB設計では当たり前のことがプロジェクト情報管理には適用されていないという指摘 |
| **ストレス・怒り** | **強い怒り**。「DBでは正規化するのが当たり前なのに、なぜプロジェクト情報はこんなに非正規化なんだ」。技術的に正しいことが実践されていない状況への義憤 |
| **ワクワク** | 「既に解決理論がある問題なんだ」という知的安心感。解決の方向性が見えてくる |

### 2-4. なぜSSOTが成立しないのか — 情報管理とコミュニケーションの目的の違い

| 観点 | 内容 |
|------|------|
| **既知** | ドキュメントを書くとき相手に合わせて情報を取捨選択する経験 |
| **未知** | 「コミュニケーション最適化」と「情報管理最適化」は**原理的に両立しない**という構造的理解。どちらにも使えない文書が量産される仕組み |
| **ストレス・怒り** | 怒りから「なるほど…」への転換。犯人探しではなく構造的問題だと気づく。ただし「じゃあどうすればいいんだ」というもどかしさ |
| **ワクワク** | 「保管と伝達を分離すれば解ける」というヒントが提示され、解法の輪郭が見える |

## 第3章: システム開発手法の歴史的課題

### 3-1. 「0→完成」に最適化された開発手法

| 観点 | 内容 |
|------|------|
| **既知** | ウォーターフォールとアジャイルの概要。スクラムの基本的なプロセス |
| **未知** | 両者の違いが「不確実性への対処方針」の違いとして統一的に説明できること。**情報管理の仕組み**に注目すると両者とも「完成時点」しか想定していないという共通の盲点 |
| **ストレス・怒り** | 「手法自体に継続的な情報管理が組み込まれていない」という構造的欠陥への気づき。正義感から「なぜ業界はこれを問題視しなかったのか」 |
| **ワクワク** | 手法の枠組みを超えた視点を得ている実感。「みんなが見えてないところが見えた」 |

### 3-2. 継続的バージョンアップへの手当ての薄さ

| 観点 | 内容 |
|------|------|
| **既知** | 「設計書が古くて使えない」体験。当時のメンバーに聞くしかない状況。CI/CDやテスト戦略は充実している実感 |
| **未知** | 「手厚い領域」と「手薄な領域」の対比による**体系的な整理**。「コードが唯一の真実になるが、設計意図は読み取れない」という明確な言語化。プロジェクト単位で完結する設計が情報劣化の構造的原因であること |
| **ストレス・怒り** | **共感からくる怒り**。「5回目の改修で誰も設計書を見ない」「当時のメンバーが退職すると理由ごと失われる」は若手が最も身近に感じる痛み。「自分たちがいつも尻拭いしてるのはこの構造のせいか」 |
| **ワクワク** | 問題が個人の怠慢ではなく構造にあると分かったことで、「構造を変えれば解ける」という方向性が見える |

### 3-3. XPとアジャイル宣言 — 組織パフォーマンスの最適化

| 観点 | 内容 |
|------|------|
| **既知** | アジャイル宣言の内容（「動くソフトウェアを」）。XPの存在 |
| **未知** | 「ドキュメント軽視」が**怠慢ではなく合理的なリソース配分の結果**だったという歴史的文脈。当時の技術水準では情報管理は人力に頼るしかなく、コストが見合わなかったという構造 |
| **ストレス・怒り** | 怒りの**緩和**。正義感の強い若手ほど「ドキュメント書かない先輩」に苛立っていたはず。それが「合理的なトレードオフだった」と理解することで怒りの矛先が収まる。ただし「でもこのままでいいはずはない」という焦燥は残る |
| **ワクワク** | 「当時は合理的だったが、今は前提が変わっている」という伏線を感じ取る期待感 |

### 3-4. スクラム — 暗黙知を肯定した開発プロセス

| 観点 | 内容 |
|------|------|
| **既知** | デイリースクラム、スプリントレビューなどスクラムのセレモニー。「ドキュメントよりコミュニケーション」という空気感 |
| **未知** | スクラムが**暗黙知を積極的に肯定する設計思想**であるという本質的理解。「AIは暗黙知を読めない」という時代の変化に対する致命的な限界 |
| **ストレス・怒り** | 「暗黙知で回すのが理想形」と言われてきたが、**AIの時代にはそれが足枷になる**という危機感。「自分たちが学んできたベストプラクティスが通用しなくなるのか」という不安 |
| **ワクワク** | 「暗黙知を形式知に転換する仕組みが必要」→ まだ誰もやっていない＝**自分たちが先駆者になれる**という可能性 |

### 3-5. この章のまとめ

| 観点 | 内容 |
|------|------|
| **既知** | ここまでの議論の流れ |
| **未知** | 「コストの問題であって、意志の問題ではない」という総括。コスト構造が変われば判断も変わるという論理 |
| **ストレス・怒り** | 怒りは収まり、**焦り**に変わっている。「コスト構造が変わるなら、早く動かないと」 |
| **ワクワク** | 「コストが変われば話が変わる」→ 第4章への強い期待感 |

## 第4章: AIが変える情報管理のコスト構造

### 4-1. 情報の記載・更新コストの劇的な低下

| 観点 | 内容 |
|------|------|
| **既知** | AIがドキュメント生成できること。Copilotのコード補完体験 |
| **未知** | 「書く人→確認する人」へのパラダイムシフト。0→1の執筆コストと確認・修正コストの**桁違いの差**。第3章のトレードオフが逆転する具体的メカニズム |
| **ストレス・怒り** | ほぼ解消。「今まで合理的だった判断が、もう合理的ではない」→ 現状維持への正義感からの怒りが復活：「知っているのにやらないのは、もう怠慢だ」 |
| **ワクワク** | **高揚感**。「XPが諦めた"正しく管理する"が現実的になりつつある」。技術の進歩が構造的問題を解決するという興奮 |

### 4-2. 暗黙知を形式知に転換できる時代

| 観点 | 内容 |
|------|------|
| **既知** | AIで文書化できるという漠然とした認識 |
| **未知** | 「暗黙知の肯定を否定するのではない」という丁寧な位置づけ。人間の暗黙知＋AIが読める形式知＝**チーム能力の拡張**というフレーミング |
| **ストレス・怒り** | なし。スクラムの価値を否定されていないことへの安堵 |
| **ワクワク** | 「暗黙知も残しつつ形式知も増やせる」＝**トレードオフの解消**。両取りできるという興奮 |

### 4-3. 好循環のフライホイール

| 観点 | 内容 |
|------|------|
| **既知** | フライホイール効果という概念（技術に明るいので知っている可能性高い） |
| **未知** | 情報管理→コンテキスト品質→AI出力品質→情報管理効率化という**具体的なループ構造**。逆の悪循環（「AIは使えない」判断）の構造 |
| **ストレス・怒り** | 悪循環の図を見て「うちのチーム、まさにこれだ…」という危機感。「停滞」側にいることへの焦り |
| **ワクワク** | **最大のワクワクポイント**。好循環に入れば加速する＝早く始めた者が圧倒的に有利。「今すぐ始めたい」 |

### 4-4. 第3章の課題がすべて解決に向かう

| 観点 | 内容 |
|------|------|
| **既知** | 第3章で提示された各課題 |
| **未知** | それぞれの課題にAIがどう対応するかの**具体的マッピング**。「あったらいいな」ではなく「もう実現可能」であること |
| **ストレス・怒り** | 「実現可能なのに仕組みがない」→ 正義感から「じゃあ仕組みを作るべきだ」という使命感 |
| **ワクワク** | 全課題に解法があるという見通しの明るさ。「ただし仕組みが必要」→ 次章への期待 |

### 4-5. この章のまとめ

| 観点 | 内容 |
|------|------|
| **既知** | ここまでの議論の流れ |
| **未知** | 「管理する方が得」の時代という価値判断の逆転 |
| **ストレス・怒り** | 「好循環を回す仕組み」がまだ示されていない焦り |
| **ワクワク** | 第5章で具体的な型が示されるという期待。「いよいよ答えが来る」 |

## 第5章: 提案手法 — SPEC&Project

### 5-1. 2つの管理対象の定義

| 観点 | 内容 |
|------|------|
| **既知** | 仕様書と変更管理の概念自体は知っている |
| **未知** | SPEC=「今の正しい姿（上書き更新）」、Project=「変更行為（蓄積）」という**明確な役割分離**。この2つだけで第2-3章の課題をカバーするというシンプルさ |
| **ストレス・怒り** | なし。「大げさなフレームワークではない」ことへの安心感 |
| **ワクワク** | 「2つの概念だけ」というシンプルさへの好感。技術者は複雑なものより**エレガントなシンプルさ**に惹かれる |

### 5-2. SPECとProjectの関係

| 観点 | 内容 |
|------|------|
| **既知** | 地図と工事記録の比喩は直感的に理解できる |
| **未知** | SPECが「バトン」としてプロジェクト間の連続性を保証するメカニズム |
| **ストレス・怒り** | なし |
| **ワクワク** | 第2-3章の抽象的な課題が、具体的な仕組みとして結実している満足感 |

### 5-3. 運用サイクル

| 観点 | 内容 |
|------|------|
| **既知** | 開発サイクルの一般的な流れ |
| **未知** | 「Project完了→SPEC更新」が**サイクルに組み込まれている**こと。AIが下書き・人間が承認という役割分担の具体形 |
| **ストレス・怒り** | 「これ、うちのチームでできるのか？」という現実的な不安がわずかに |
| **ワクワク** | ステップが明確＝**明日から始められる**。実践のイメージが湧く |

### 5-4. なぜ品質が維持されるのか

| 観点 | 内容 |
|------|------|
| **既知** | 「AIが間違えることがある」という懸念（自分も持っている） |
| **未知** | 好循環が品質を**自己強化する**メカニズム。コードという「動く事実」との照合で正しい内容に収束するロジック。悪循環に入っても検知・回復できる設計 |
| **ストレス・怒り** | 懸念が構造的に解消される安心感。「AIを盲信しない」姿勢が組み込まれていることへの信頼 |
| **ワクワク** | 「回すほど楽になる」という自己強化ループの魅力 |

### 5-5. この方式がもたらす効果

| 観点 | 内容 |
|------|------|
| **既知** | 第2-3章で提示された各課題 |
| **未知** | 全課題がSPEC&Projectでどう解決されるかの**一覧性のある対応表** |
