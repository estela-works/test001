# テスト設計ガイド

テスト方針書を作成する前に読むドキュメント。
テストレベルの全体像、各レベルの役割分担、重複しやすい領域の境界ルールを定義する。

---

## 1. テストレベルの全体像

本プロジェクトでは、テストを3つのレベルに分けて設計する。

```
┌─────────────────────────────────────────────────────────────────┐
│  43 総合試験                                                     │
│  「業務として正しいか？」                                          │
│                                                                   │
│  ユーザー視点で業務シナリオ全体を検証する                           │
│  フロントエンド + バックエンド + DB がすべて実環境で結合             │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ E2E自動テスト（Playwright）= 総合試験の自動化パート        │   │
│  └──────────────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────────────┤
│  42 結合試験                                                     │
│  「モジュールを繋いだとき、接合部で問題は起きないか？」               │
│                                                                   │
│  ┌──────────────┐ ┌──────────────┐ ┌─────────────────────┐    │
│  │ FE結合        │ │ BE結合        │ │ 外部コンポーネント   │    │
│  │               │ │               │ │ 接続                │    │
│  │ Component     │ │ Controller    │ │                     │    │
│  │   ↕ 実結合    │ │   ↕ 実結合    │ │ 自システム           │    │
│  │ Store         │ │ Service       │ │   ↕ スタブ/実環境    │    │
│  │   ↕ MSW      │ │   ↕ 実結合    │ │ 外部API / DB /      │    │
│  │ (API境界)     │ │ Mapper + DB   │ │ MQ / 認証基盤       │    │
│  └──────────────┘ └──────────────┘ └─────────────────────┘    │
├─────────────────────────────────────────────────────────────────┤
│  41 単体試験                                                     │
│  「このモジュール単独で正しく動くか？」                              │
│                                                                   │
│  ┌──────────────┐ ┌──────────────┐                              │
│  │ FE単体        │ │ BE単体        │                              │
│  │               │ │               │                              │
│  │ Component     │ │ Mapper (H2)   │   すべての外部依存を          │
│  │ Store         │ │ Service       │   モック化して検証             │
│  │ 純粋関数      │ │ (Mapper=Mock) │                              │
│  └──────────────┘ └──────────────┘                              │
└─────────────────────────────────────────────────────────────────┘
```

### 各レベルが答える問い

| レベル | 問い | 不合格＝何が悪い？ |
|--------|------|------------------|
| 単体試験 | このモジュール**単独**で正しく動くか？ | そのモジュール自体のバグ |
| 結合試験 | モジュールを**繋いだ**とき接合部で問題は起きないか？ | インターフェースの不整合、データ変換ミス、エラー伝播の欠落 |
| 総合試験 | **業務として**正しく動くか？要件を満たしているか？ | 仕様の解釈ミス、業務フローの欠陥、非機能要件の未達 |

## 2. 各レベルの詳細

### 41 - 単体試験

| 項目 | 内容 |
|------|------|
| 焦点 | モジュール内部のロジック |
| 依存の扱い | **すべてモック化** |
| 実行速度 | 高速（ミリ秒単位） |
| 実行タイミング | 開発中に随時 |
| 失敗時の原因特定 | 容易（対象モジュールに限定） |

詳細: [41_unit-test/README.md](41_unit-test/README.md)

### 42 - 結合試験

| 項目 | 内容 |
|------|------|
| 焦点 | モジュール間の**接合部** |
| 依存の扱い | **実結合**（外部コンポーネントはスタブ可） |
| 実行速度 | 中速（秒単位） |
| 実行タイミング | 実装完了後 |
| 失敗時の原因特定 | 中程度（接合部に絞れる） |

詳細: [42_integration-test/README.md](42_integration-test/README.md)

### 43 - 総合試験

| 項目 | 内容 |
|------|------|
| 焦点 | 業務シナリオ全体・非機能要件 |
| 依存の扱い | **すべて実環境** |
| 実行速度 | 低速（分単位。手動テスト含む） |
| 実行タイミング | リリース前 |
| 失敗時の原因特定 | 困難（全体を調査する必要あり） |

詳細: [43_system-test/README.md](43_system-test/README.md)

## 3. テストレベル間の境界ルール

### 3.1 判断の原則

テストケースをどのレベルに配置するかは**依存をどう扱っているか**で決まる。

```
依存をモック化している        → 単体試験
依存を実結合している          → 結合試験
システム全体を実環境で動かす   → 総合試験
```

### 3.2 重複しやすい領域と境界

#### 単体試験 vs 結合試験

最も境界が曖昧になりやすい。**判断基準は「依存がモックか実物か」**。

| ケース | 判断 | 理由 |
|--------|------|------|
| ストア単体テスト（API呼び出しを`vi.fn()`でモック） | **単体** | 依存をモック化している |
| コンポーネント + 実ストア + MSW | **結合** | ストアを実物で使い、複数モジュールが連携 |
| Service単体テスト（Mapperを`@Mock`） | **単体** | 依存をモック化している |
| Service + 実Mapper + H2 DB | **結合** | 複数レイヤーが実結合 |
| Controller + MockMvc + 全層実結合 | **結合** | HTTPレイヤーから全層が実結合 |

**注意**: 「テストフレームワークの種類」では判断しない。`@SpringBootTest`でもMapperをモック化していれば単体試験。

#### 結合試験 vs 総合試験

**判断基準は「技術的な接合部の検証か、業務シナリオの検証か」**。

| ケース | 判断 | 理由 |
|--------|------|------|
| 画面Aから画面Bへのパラメータ受け渡し | **結合** | 2画面間のインターフェース検証 |
| 画面A→画面B→画面Cの業務フロー全体 | **総合** | ユーザー視点の一連シナリオ |
| APIエンドポイント単位の正常/異常応答 | **結合** | API単位の技術的検証 |
| 「チケット作成→編集→完了」の一連操作 | **総合** | 業務フロー全体の検証 |
| 外部APIのタイムアウト時のリトライ動作 | **結合** | 外部接合部の異常系検証 |
| ネットワーク切断時のユーザー体験 | **総合** | ユーザー視点の障害リカバリ |

#### 総合試験（手動） vs E2Eテスト（自動）

E2Eは総合試験の一部。**自動化するかどうか**で分ける。

| ケース | 判断 | 理由 |
|--------|------|------|
| クリティカルパスの回帰テスト | **E2E自動** | 繰り返し実行が必要 |
| 初回リリース時の探索的テスト | **手動** | 自動化のコスト対効果が低い |
| データ受け渡しの正確性検証 | **E2E自動** | 確定的に検証可能 |
| UIの見た目・使い勝手の確認 | **手動** | 人間の判断が必要 |
| 性能・アクセシビリティ | **手動** | 専用ツール+人間の判断が必要 |

## 4. テスト方針書の依存関係

各テスト方針書が前提とする情報の流れを示す。

```
requirements.md（要件・受入条件）
    │
    ├──→ detail-design-*.md（詳細設計）
    │       │
    │       ├──→ 41 単体試験方針書
    │       │       各モジュールの入出力仕様から
    │       │       テストケースを導出
    │       │
    │       └──→ 42 結合試験方針書
    │               モジュール間のインターフェース仕様から
    │               テストケースを導出
    │
    └──→ 43 総合試験方針書
            │   要件・受入条件から
            │   業務シナリオ・非機能テストを導出
            │
            └──→ E2Eテスト方針書
                    総合試験のうち自動化対象を
                    Playwrightのテストケースとして定義
```

### テスト方針書間の参照ルール

| 方針書 | 入力（参照元） | 出力（後続への影響） |
|--------|-------------|-------------------|
| 単体試験 | 詳細設計書 | なし（独立して完結） |
| 結合試験 | 詳細設計書、単体試験の前提 | なし（独立して完結） |
| 総合試験 | 要件整理書 | E2Eテスト方針書の元ネタ |
| E2Eテスト | 総合試験方針書 | なし（総合試験の自動化実装） |

## 5. 7つのテンプレートの一覧と使い分け

### テンプレート全体マップ

```
40_test-spec/
├── 41_unit-test/
│   ├── test-spec-unit-frontend-template.md ··· [A]
│   └── test-spec-unit-backend-template.md ···· [B]
├── 42_integration-test/
│   ├── test-spec-integration-frontend-template.md ··· [C]
│   ├── test-spec-integration-backend-template.md ···· [D]
│   └── test-spec-integration-external-template.md ··· [E]
└── 43_system-test/
    ├── test-spec-system-template.md ··· [F]
    └── test-spec-e2e-template.md ······ [G]
```

### 各テンプレートの役割

| 記号 | テンプレート | 何を検証するか | 主なテスト対象 |
|------|-------------|---------------|---------------|
| [A] | [単体FE](41_unit-test/test-spec-unit-frontend-template.md) | コンポーネント・ストア・関数が単独で正しいか | Vue Component, Pinia Store, 純粋関数 |
| [B] | [単体BE](41_unit-test/test-spec-unit-backend-template.md) | Mapper・Serviceが単独で正しいか | MyBatis Mapper, Service（Mockito） |
| [C] | [結合FE](42_integration-test/test-spec-integration-frontend-template.md) | FE内部のモジュール連携が正しいか | Component+Store, 親子Component, Router |
| [D] | [結合BE](42_integration-test/test-spec-integration-backend-template.md) | BE内部のレイヤー連携が正しいか | Service+Mapper+DB, Controller全層 |
| [E] | [結合外部](42_integration-test/test-spec-integration-external-template.md) | 外部コンポーネントとの接続が正しいか | 外部API, 外部DB, MQ, 認証基盤 |
| [F] | [総合](43_system-test/test-spec-system-template.md) | 業務シナリオ・非機能要件を満たしているか | 業務フロー, 性能, UX, 障害リカバリ |
| [G] | [E2E](43_system-test/test-spec-e2e-template.md) | [F]のうち自動化可能なケース | Playwrightシナリオ |

### 案件規模別の選択ガイド

| 案件規模 | 使うテンプレート | 理由 |
|---------|-----------------|------|
| バグ修正 | [A] [B] | 修正箇所の単体確認で十分 |
| 小規模機能追加 | [A] [B] + [C] [D] | 既存コードとの結合確認が必要 |
| 中規模機能追加 | [A] [B] + [C] [D] + [F] | 業務シナリオの検証も必要 |
| 大規模・新機能 | [A]〜[G] 全て | 全レベルの検証が必要 |
| 外部システム連携追加 | 上記 + [E] | 外部接続の検証が追加で必要 |

## 7. よくある質問

### Q. 同じ機能を複数レベルでテストするのは重複では？

重複ではない。各レベルは**検証の観点が異なる**。

例：「チケット作成」機能の場合

| レベル | テスト内容 | 観点 |
|--------|----------|------|
| 単体 | Service.createTodo() にモックMapper渡して戻り値確認 | メソッド内のロジック正しさ |
| 結合 | POST /api/todos → DB INSERT → レスポンスJSON | 全層がHTTP→DBまで一貫動作するか |
| 総合 | 画面でフォーム入力→送信→一覧に反映→詳細画面で確認 | 業務フローとして成立するか |

### Q. 結合試験でAPIテスト（Controller+全層）をやるなら、総合試験との違いは？

- **結合試験のAPIテスト**: エンドポイント**単位**のリクエスト/レスポンスの技術的正しさ
- **総合試験**: 複数エンドポイントを**横断**する業務フローの検証

結合試験は `POST /api/todos` が201を返すか、総合試験は「チケット作成→一覧表示→詳細確認」の一連が業務として成立するか。

### Q. 外部コンポーネント接続テストはなぜ結合試験に入る？

結合試験の定義は「モジュール間の接合部の検証」。外部コンポーネントとの接合部も同じ原則が適用される。ただし以下の点が内部結合と異なる：

- テスト環境にスタブ/サンドボックスが必要
- タイムアウト・リトライ等のネットワーク固有の異常系がある
- 相手側の仕様変更リスクがある

このため専用のテンプレート（[E]）を分離している。

### Q. E2Eテスト方針書は単独で作れる？

作れるが、必ず総合テスト方針書（[F]）を先に作成すること。E2Eは総合試験のうち「自動化するケース」を切り出したものであり、[F]のトレーサビリティ表で対応関係を管理する。E2E単独では「何を自動化すべきか」の判断根拠がなくなる。
