# Phase 2C｜テスト仕様書と設計書の整合性チェック

## 問い

> テスト仕様書のID体系・テストレベル境界・ケース配置が設計ルールと一致し、レベル間で重複・矛盾がないか？

## チェック対象

- テストケースID体系の正しさ（FT-/MT-/SU-/FI-/SI-/CI-/EXT-/SYS-/E2E- プレフィックス）
- テストレベル境界の正しさ（依存をモック化→単体、実結合→結合、業務シナリオ→総合）
- レベル間の重複テスト検出（同じ検証を異なるレベルで二重に実施していないか）
- テスト仕様書と詳細設計書の用語・命名の一致
- 用語辞書との照合（定義済みの場合）

## 典型的ミス

1. テストケースIDのプレフィックスが規約と異なる（例: 単体なのに `SI-` を使用、結合なのに `FT-` を使用）
2. 「Service + 実Mapper + H2 DB」のテストを単体試験に分類している（実結合なので結合試験が正しい）
3. 単体試験と結合試験の両方で全く同じAPI応答パターンをテストしている（観点の違いなく純粋に重複）
4. テスト仕様書のメソッド名・エンドポイント名が詳細設計書と異なる
5. 「ユーザー」と「利用者」等、同じ概念に異なる名称が混在している

## 実行手順

### Step 1｜テストケースID体系の検証

全テストケースのIDプレフィックスが規約に沿っているか確認する。

```
| # | テストケースID | 記載テストレベル | 正しいプレフィックス | 一致 | 備考 |
|---|--------------|---------------|-------------------|------|------|
| 1 | FT-001       | FE単体         | FT-               | OK   | -    |
| 2 | SI-001       | BE単体         | SU-               | NG   | SIは結合用 |
| 3 | E2E-SC-001   | E2E            | E2E-SC-           | OK   | -    |
```

ID規約参照:
- 単体: `FT-`, `FT-ST-`, `FT-PF-`, `MT-`, `SU-`
- 結合: `FI-`, `FI-PC-`, `FI-NAV-`, `SI-`, `CI-`, `EXT-API-`, `EXT-DB-`, `EXT-MSG-`, `EXT-FS-`, `EXT-AUTH-`
- 総合: `SYS-SC-`, `SYS-NAV-`, `SYS-PF-`, `SYS-UX-`, `SYS-A11Y-`, `SYS-ERR-`, `E2E-SC-`, `E2E-NAV-`, `E2E-ERR-`

### Step 2｜テストレベル境界の検証

各テストケースの依存の扱い方を確認し、テストレベルへの配置が正しいか検証する。

```
| # | テストケースID | 配置レベル | 依存の扱い | 正しいレベル | 判定 |
|---|--------------|----------|----------|-----------|------|
| 1 | FT-001       | 単体      | APIをMSWモック | 単体     | OK   |
| 2 | SU-003       | 単体      | Mapper実結合+H2 | 結合   | NG   |
| 3 | SYS-SC-001   | 総合      | 全実環境     | 総合     | OK   |
```

判断基準:
- 依存をモック化 → 単体試験
- 依存を実結合 → 結合試験
- システム全体を実環境で動かす → 総合試験

### Step 3｜レベル間の重複テスト検出

異なるテストレベルに配置されたケースを比較し、観点の違いなく純粋に重複しているケースを検出する。
テストピラミッドの原則（各レベルで何を保証するかが明確）に照らして判断する。

```
| # | ケースA（ID/レベル） | ケースB（ID/レベル） | テスト内容 | 観点の違い | 重複判定 |
|---|-------------------|-------------------|----------|----------|---------|
| 1 | FT-001（単体）     | FI-001（結合）     | {機能名}表示 | 単体:ロジック / 結合:連携 | 重複なし |
| 2 | SU-002（単体）     | SI-002（結合）     | {機能名}API応答 | 同一パターン | 重複あり |
```

各レベルの責務（参考）:
- 単体: ロジックの正しさ、バリデーション
- 結合: API-DB間・コンポーネント間のデータ受け渡し、認証・認可フロー
- 総合/E2E: 画面遷移、ユーザーシナリオ

### Step 4｜設計書との用語・命名の照合

テスト仕様書で使用されているメソッド名、エンドポイント、データ項目名が詳細設計書と一致するか確認する。
用語辞書が定義されている場合は、辞書の正式用語との照合も行う。

```
| # | テスト仕様書の記述 | 詳細設計書の記述 | 一致 | 備考 |
|---|-----------------|---------------|------|------|
| 1 | {メソッド名}      | {メソッド名}    | OK   | -    |
| 2 | {APIパス}        | {APIパス}      | NG   | パスが異なる |
| 3 | {項目名}         | {項目名}       | NG   | 命名不一致 |
```

命名規約の確認:
- [ ] クラス名: PascalCase
- [ ] メソッド名: camelCase
- [ ] APIパス: kebab-case
- [ ] DBカラム: snake_case
- [ ] 同じ概念に同じ言葉が使われているか（用語の揺れがないか）

## 判定基準

- ID体系・レベル境界・命名が全て一致し、不要な重複がなければPass
- 不一致・重複がある場合は、テスト仕様書を修正してから次のPhaseへ進む
