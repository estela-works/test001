# Phase 2A｜テストケースカバレッジ完全性チェック

## 問い

> 要件・設計書のすべての仕様項目が、適切なテストケースでカバーされているか？

## チェック対象

- 要件整理書（requirements.md）の受入条件 → テストケースへのトレーサビリティ
- 詳細設計書（detail-design-*.md）の入出力仕様 → テストケースへのトレーサビリティ
- 正常系・異常系（業務エラー）・例外系（システムエラー）・境界値の網羅性
- テストレベル割り当ての正しさ（単体/結合/総合）
- テストピラミッドのバランス（単体 > 結合 > E2E）

## 典型的ミス

1. 要件整理書の受入条件に対応するテストケースが存在しない（カバレッジ漏れ）
2. 正常系のみテストし、異常系（バリデーションエラー、業務ルール違反）や例外系（DB接続断、タイムアウト等）のケースが欠落している
3. 境界値テスト（0件、1件、上限件数、文字列最大長等）が不足している
4. 非機能テスト観点（性能、セキュリティ、互換性等）が漏れている
5. ドメイン固有の組み合わせパターンが網羅されていない

## 実行手順

### Step 1｜上流ドキュメントの仕様項目抽出

要件整理書（総合試験・E2E対象）および詳細設計書（単体・結合対象）から、テスト対象となる仕様項目を全て抽出する。

```
| # | 仕様項目 | 出典ドキュメント | 該当セクション | テストレベル（期待） |
|---|---------|----------------|--------------|-------------------|
| 1 | ...     | ...            | ...          | 単体/結合/総合      |
```

### Step 2｜テストケースとのトレーサビリティ照合

抽出した仕様項目ごとに、対応するテストケースが存在するか照合する。
トレーサビリティマトリクス（要件ID → 設計項目 → テストケースID）として可視化し、空欄（未対応）がないことを確認する。

```
| # | 仕様項目 | 要件ID | 期待テストレベル | 対応テストケースID | カバー状態 | 備考 |
|---|---------|-------|---------------|-----------------|----------|------|
| 1 | ...     | REQ-xxx | 単体           | FT-001, SU-001  | OK       | -    |
| 2 | ...     | REQ-xxx | 総合           | （なし）         | NG       | 漏れ  |
```

### Step 3｜正常系・異常系・例外系・境界値の網羅性検証

各テスト対象について、以下の4観点でケースが存在するか確認する。
エラーの3分類（正常系/異常系=業務エラー/例外系=システムエラー）を意識して分類する。

```
| # | テスト対象 | 正常系 | 異常系（業務エラー） | 例外系（システムエラー） | 境界値 | 判定 |
|---|-----------|-------|-------------------|---------------------|-------|------|
| 1 | {機能名}   | 3     | 1                 | 0                   | 0     | NG（例外系・境界値なし） |
| 2 | {機能名}   | 2     | 2                 | 1                   | 2     | OK   |
```

異常系の確認観点:
- バリデーション（必須、型、範囲、形式、相関、サイズ）
- 業務ルール違反（状態遷移、排他制御、権限、上限）

例外系の確認観点:
- DB接続障害、外部API障害、タイムアウト

### Step 4｜非機能テスト観点の網羅性検証

非機能要件に対するテストケースが存在するか確認する。

```
| # | 非機能観点 | 対象テストケース | 網羅状態 | 備考 |
|---|-----------|---------------|---------|------|
| 1 | 性能（レスポンスタイム） | ... | OK/NG | 目標値が設定されているか |
| 2 | セキュリティ（認証・認可） | ... | OK/NG | |
| 3 | セキュリティ（インジェクション） | ... | OK/NG | |
| 4 | 互換性（ブラウザ・デバイス） | ... | OK/NG | |
| 5 | アクセシビリティ | ... | OK/NG | 対象外なら理由を明記 |
```

### Step 5｜ドメイン固有パターンの網羅性検証

対象アプリのドメイン固有テストパターンを確認する。
※ 以下は例。案件ごとにドメイン固有のパターンを洗い出して表を作成すること。

```
| # | テストパターン | 該当テストケース | 網羅状態 | 備考 |
|---|--------------|---------------|---------|------|
| 1 | 主要機能の単独操作（各パターン） | ... | OK/NG | 全パターンをカバーしているか |
| 2 | オプション・設定の組み合わせ | ... | OK/NG | 排他・併用ルールの全パターン |
| 3 | 計算ロジック（端数処理、上限/下限） | ... | OK/NG | 境界値 |
| 4 | 状態遷移シナリオ | ... | OK/NG | 許可されない遷移も含む |
```

### Step 6｜テストピラミッドとカバレッジ目標の確認

テストレベルごとのケース数バランスと、カバレッジ目標を確認する。

```
| テストレベル | ケース数 | 割合 | 推奨バランス | 判定 |
|------------|---------|------|------------|------|
| 単体テスト   | ...     | ...% | 最多        | OK/NG |
| 結合テスト   | ...     | ...% | 中程度      | OK/NG |
| 総合/E2E    | ...     | ...% | 最少        | OK/NG |
```

```
| カバレッジ種類 | 目標値 | 設定済み | 備考 |
|-------------|--------|---------|------|
| C1（分岐網羅） | 80%以上 | OK/NG | 推奨基準 |
| 要件カバレッジ | 100%   | OK/NG | 全要件にテストケースが存在 |
```

## 判定基準

- 全仕様項目にテストケースが対応し、正常系・異常系・例外系・境界値が揃っていればPass
- 非機能テスト観点が検討済み（対象外の場合は理由が明記）であればPass
- テストピラミッドのバランスが逆転（アイスクリームコーン）していないこと
- カバレッジ漏れがある場合は、テスト仕様書にケースを追加してから次のPhaseへ進む
