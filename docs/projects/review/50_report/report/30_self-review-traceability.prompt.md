# Phase 2C｜トレーサビリティチェック

## 問い

> 報告書の成果物が設計書と、テスト結果がテスト仕様書と、残課題が次フェーズへの申し送りと、それぞれ漏れなく対応づけられているか？

## チェック対象

- 成果物 ↔ 詳細設計書の対応関係（双方向）
- テスト結果 ↔ テスト仕様書の対応関係（双方向）
- 課題・残件 ↔ 次フェーズへの申し送りの完全性
- 派生要件（実装中に追加された要件）の追跡

## 典型的ミス

1. 詳細設計書で定義されたモジュールの一部が成果物一覧に含まれていない（実装したが記載漏れ、または未実装）
2. テスト仕様書のテストケースIDと報告書のテスト結果IDが対応していない（ID体系の不一致）
3. 実装中に発見した課題が報告書の課題欄には記載されているが、次フェーズへの申し送りに含まれていない
4. 設計変更が発生したのに、変更後の設計書の更新状況が記録されていない
5. 実装中に生まれた派生要件（追加機能、追加テスト等）にIDが付与されておらず、追跡できない
6. 下流→上流の逆方向トレーサビリティが欠如している（成果物からどの要件に基づくか遡れない）

## 実行手順

### Step 1｜成果物と詳細設計書の双方向対応確認

詳細設計書で定義された全モジュール・ファイルが、報告書の成果物一覧に含まれているか確認する。
**双方向リンク**: 設計書→報告書だけでなく、報告書→設計書の逆方向も確認する。

**実装作業報告書の場合:**
```
| # | 詳細設計書の定義 | 出典 | 報告書の成果物 | 対応 | 備考 |
|---|---------------|------|-------------|------|------|
| 1 | PlanEstimateService | detail-design-logic.md | PlanEstimateService.java | OK | - |
| 2 | DiscountCalculator | detail-design-logic.md | （なし） | NG | 未記載 |
| 3 | plan_master テーブル | detail-design-db.md | V1__create_plan_master.sql | OK | - |
```

**逆方向（報告書に記載があるが設計書に対応がないもの）:**
```
| # | 報告書の成果物 | 対応する設計書の定義 | 対応 | 備考 |
|---|-------------|------------------|------|------|
| 1 | ErrorHandler.java | （なし） | NG | 派生要件？設計書追加が必要 |
```

**テスト実装報告書の場合:**
```
| # | テスト仕様書のケース | テストケースID | 報告書の記載 | 対応テストコード | 対応 |
|---|-------------------|-------------|-----------|--------------|------|
| 1 | プラン料金計算の正常系 | SU-001 | あり | PlanEstimateServiceTest.java | OK |
| 2 | 割引組み合わせの境界値 | SU-005 | なし | - | NG |
```

### Step 2｜テスト結果とテスト仕様書の対応確認

報告書のテスト結果が、テスト仕様書のテストケースと正しく対応しているか確認する。
テストレベル（単体/結合/総合）ごとにカバレッジを集計する。

```
| # | テスト仕様書のケースID | テスト仕様書の概要 | テストレベル | 報告書での結果 | 対応状態 |
|---|---------------------|---------------|-----------|-------------|---------|
| 1 | FT-001 | プラン選択表示 | 単体FE | Pass | OK |
| 2 | FT-002 | オプション追加 | 単体FE | （記載なし） | NG（結果未記載） |
| 3 | SU-001 | 料金計算ロジック | 単体BE | Pass | OK |
| 4 | SI-001 | API-DB連携 | 結合 | Pass | OK |
```

**テストレベル別カバレッジ集計:**
```
| テストレベル | 仕様書のケース数 | 報告書に結果ありの数 | カバレッジ |
|------------|---------------|------------------|----------|
| 単体FE | ... | ... | ...% |
| 単体BE | ... | ... | ...% |
| 結合 | ... | ... | ...% |
| 総合 | ... | ... | ...% |
```

### Step 3｜課題・残件の申し送り完全性確認

報告書に記載された課題・残件が、次フェーズへの申し送りとして適切に引き継がれるか確認する。

```
| # | 課題・残件 | 重要度 | 報告書の課題欄 | 申し送り記載 | 対応フェーズ | 判定 |
|---|----------|--------|-------------|-----------|-----------|------|
| 1 | 性能改善が必要 | 重要 | あり | あり（次フェーズで対応） | テスト | OK |
| 2 | 仕様未確定の割引ルール | 致命的 | あり | なし | - | NG（申し送り漏れ） |
| 3 | テスト環境の制約 | 軽微 | あり | あり（手動テストで代替） | テスト | OK |
```

### Step 4｜設計変更のトレーサビリティ確認

実装・テスト中に発生した設計変更が、関連ドキュメントの更新状況とともに記録されているか確認する。
派生要件にはIDを付与し、元要件との関連を記録する。

```
| # | 設計変更内容 | 派生要件ID | 報告書に記載 | 設計書の更新 | 更新状況の記録 | 判定 |
|---|------------|----------|-----------|-----------|-------------|------|
| 1 | API応答フォーマット変更 | DRV-001 | あり | 更新済み | 記録あり | OK |
| 2 | DB項目追加 | DRV-002 | あり | 未更新 | 記録なし | NG |
```

## アンチパターン

| パターン名 | 症状 | 処方 |
|-----------|------|------|
| ID振り忘れ | 派生要件にIDがない | IDの自動採番ルールを決めておく |
| コピペ汚染 | 類似成果物をコピペして修正漏れ | コピー元との差分を必ず明記する |
| 暗黙知依存 | 「当然わかるはず」で書かない | 第三者が読んで理解できるか確認する |
| 片方向リンク | 上流→下流のみで逆方向が欠如 | 下流→上流のリンクも維持する |

## 判定基準

- 全成果物・テスト結果・課題が上流ドキュメントと漏れなく双方向に対応づけられていればPass
- 派生要件にIDが付与され、追跡可能であればPass
- 対応漏れ・申し送り漏れがある場合は、報告書を補完してから次のPhaseへ進む
