# Phase 2B｜報告書正確性チェック

## 問い

> 報告書に記載されたファイルパス・テスト結果・数値データが、実際のリポジトリ・実行結果と一致しているか？

## チェック対象

- ファイルパスが実際のリポジトリ構造と一致するか
- テスト結果（実行数・成功数・失敗数）が実際の実行ログと一致するか
- テンプレートからのコピーペーストで残った不正な記述がないか
- カバレッジデータが実際の計測値と一致するか
- 命名規約（クラス名・メソッド名・テーブル名・APIパス等）が正しく記載されているか

## 典型的ミス

1. ファイルパスのディレクトリ階層が実際と異なる（例: `src/main/service/` → 実際は `src/main/java/com/.../service/`）
2. テスト結果を設計書から転記し、実際には実行していない数値が記載されている
3. テンプレートの記入例（`XxxService.java` 等）がそのまま残っている
4. カバレッジ数値が別の案件・別の実行時点の値になっている
5. 命名規約の不統一（例: クラス名が`planEstimateService`（camelCase）と記載されているが正しくは`PlanEstimateService`（PascalCase））
6. 設計書と報告書でエンティティ名・テーブル名が異なる（コピペ地獄アンチパターン）

## 実行手順

### Step 1｜ファイルパスの実在確認（観点D）

報告書に記載された全ファイルパスについて、リポジトリに実在するか確認する。

```
| # | 報告書記載のパス | リポジトリでの実在 | 正しいパス | 判定 |
|---|---------------|-----------------|----------|------|
| 1 | src/main/java/.../PlanEstimateService.java | あり | - | OK |
| 2 | src/main/java/.../DiscountMapper.java | なし | src/main/java/.../DiscountMasterMapper.java | NG |
| 3 | src/test/.../PlanTest.java | あり | - | OK |
```

### Step 2｜テスト結果の実行ログとの照合

報告書のテスト結果を、実際のテスト実行ログ（`mvnw test` 等の出力）と照合する。

```
| # | 報告書の記述 | 実行ログの値 | 一致 | 備考 |
|---|------------|-----------|------|------|
| 1 | Tests run: 25 | Tests run: 25 | OK | - |
| 2 | Failures: 0 | Failures: 0 | OK | - |
| 3 | Errors: 0 | Errors: 0 | OK | - |
| 4 | Skipped: 0 | Skipped: 2 | NG | Skipped数が異なる |
```

### Step 3｜テンプレート残骸の検出

報告書内にテンプレートの記入例やプレースホルダーが残っていないか確認する。

```
| # | 検出対象パターン | 該当箇所 | 判定 |
|---|---------------|---------|------|
| 1 | 「XxxService」「YyyMapper」等の仮名 | ... | OK/NG |
| 2 | 「TODO」「TBD」「要記入」等のプレースホルダー | ... | OK/NG |
| 3 | 「202X年」「X月X日」等の仮日付 | ... | OK/NG |
| 4 | テンプレート説明文（「ここに〜を記載する」） | ... | OK/NG |
```

### Step 4｜命名規約の正確性確認

報告書に記載された名称が、プロジェクトの命名規約に従っているか確認する。

```
| # | 対象 | 報告書での記載 | 命名規約 | 正しい名称 | 判定 |
|---|------|-------------|---------|----------|------|
| 1 | クラス名 | ... | PascalCase | ... | OK/NG |
| 2 | メソッド名 | ... | camelCase | ... | OK/NG |
| 3 | DBテーブル名 | ... | snake_case（複数形） | ... | OK/NG |
| 4 | DBカラム名 | ... | snake_case | ... | OK/NG |
| 5 | APIパス | ... | kebab-case（複数形） | ... | OK/NG |
| 6 | JSON項目 | ... | snake_case | ... | OK/NG |
```

### Step 5｜数値データの整合性確認

報告書内の数値（件数、パーセンテージ等）が相互に矛盾していないか確認する。

```
| # | 確認項目 | 記載値 | 整合性 | 備考 |
|---|---------|-------|--------|------|
| 1 | 成果物ファイル数 vs 一覧の行数 | 8件 / 一覧8行 | OK | - |
| 2 | テスト総数 = 成功 + 失敗 + スキップ | 25 = 23 + 0 + 2 | OK | - |
| 3 | カバレッジ（報告書） vs 計測値 | 85% / 82% | NG | 値が不一致 |
```

## 判定基準

- 全ファイルパスが実在し、テスト結果が実行ログと一致し、テンプレート残骸がなければPass
- 命名規約が正しく記載されていればPass
- 不一致がある場合は、実際の値に修正してから次のPhaseへ進む
