# Phase 4｜横断的整合性チェック

## 問い

> 報告書内の複数セクションおよび関連ドキュメント全体を横断して、矛盾・漏れ・不整合がないか？

## 位置づけ

報告書全体を俯瞰し、セクション間・ドキュメント間の記述の矛盾・食い違いを検出する最終関門。
Phase 2A〜2Cで内部品質を、Phase 3で外部との差分を確認した上で、最後に報告書全体の一貫性を検証する。

## 実行手順

### Step 1｜報告書内セクション間の整合性確認

報告書の各セクション間で、記述が矛盾していないか確認する。

```
| # | セクションA | 記述A | セクションB | 記述B | 矛盾 | 内容 |
|---|-----------|-------|-----------|-------|------|------|
| 1 | 成果物一覧 | ファイル8件 | 概要 | 「7つのファイルを作成」 | あり | 件数不一致 |
| 2 | テスト結果 | 全件Pass | 課題欄 | 「テスト失敗あり」 | あり | 結果矛盾 |
| 3 | 設計変更 | API変更あり | 成果物一覧 | 変更ファイル記載あり | なし | - |
```

### Step 2｜実装報告書とテスト報告書の整合性確認

両方の報告書が存在する場合、相互の記述が矛盾していないか確認する。

```
| # | 実装報告書の記述 | テスト報告書の記述 | 矛盾 | 内容 |
|---|---------------|----------------|------|------|
| 1 | 成果物: PlanEstimateService.java | テスト対象: PlanEstimateService.java | なし | - |
| 2 | 設計変更: API応答フォーマット変更 | テスト前提: 旧フォーマット | あり | テスト仕様が未更新 |
| 3 | 残課題: 性能改善 | テスト対象外として記載 | なし | 整合 |
```

### Step 3｜報告書と設計書の用語・命名の一貫性確認

報告書で使用されている用語・命名が、設計書と一致しているか確認する。
用語辞書（プロジェクトで定義されている場合）との照合も行う。

```
| # | 概念 | 報告書での名称 | 設計書での名称 | 一致 | 統一案 |
|---|------|-------------|-------------|------|--------|
| 1 | ... | ... | ... | OK/NG | ... |
```

**命名規約の横断確認:**
```
| # | 対象 | 報告書A | 報告書B | 設計書 | 統一 | 備考 |
|---|------|--------|--------|-------|------|------|
| 1 | サービス名 | PlanEstimateService | PlanEstimateService | PlanEstimateService | OK | - |
| 2 | テーブル名 | plan_master | planMaster | plan_master | NG | 報告書Bが命名規約違反 |
```

### Step 4｜エラーコード・メッセージの横断一致確認

報告書に記載されたエラーコード・エラーメッセージが、設計書の定義と一致しているか確認する。

```
| # | エラーコード | 報告書の記述 | 設計書の定義 | 一致 | 備考 |
|---|-----------|-----------|-----------|------|------|
| 1 | ERR-V-001 | 「入力値が不正です」 | 「メールアドレスの形式が不正です」 | NG | メッセージが汎化されている |
| 2 | ERR-B-001 | 「在庫不足」 | 「在庫不足」 | OK | - |
```

Phase 2A〜Phase 4の結果を統合し、最終判定を行う。
指摘は重要度（致命的/重要/軽微/コメント）とタイプ（欠陥/矛盾/曖昧/改善/疑問）で分類する。

## アンチパターン

| パターン名 | 症状 | 処方 |
|-----------|------|------|
| コピペ地獄 | 同じ定義を報告書と設計書でコピペし、片方だけ更新 | 定義は1箇所に集約し、他は参照リンクにする |
| 暗黙の変更 | 変更履歴に残さず修正 | 変更箇所を明示、バージョン番号を更新 |
| 部分最適 | 各報告書が独立して作成され全体で矛盾 | 横断整合性チェックを最終関門とする |
| 二重否定 | 「〜でないことはない」等の曖昧表現 | 肯定形で書き直す |

## 判定基準

- 報告書内・ドキュメント間で矛盾がなく、用語・命名・エラーコードが統一されていればPass
- 致命的・重要な指摘が全て修正済みであればPass
- 矛盾または不統一がある場合は修正してから人間レビューへ提出
