# Phase 4｜横断整合性チェック

## 問い

> 型定義ファイル間・セクション間で矛盾がないか？共通レビュー観点A〜Dの最終確認は完了したか？

## 位置づけ

設計書全体を俯瞰し、セクション間・ファイル間の記述の矛盾・食い違いを検出する最終関門。
Phase 2A〜2Cで内部品質を、Phase 3で外部との差分を確認した上で、最後に設計書全体の一貫性を検証する。

## 典型的ミス

1. 型定義ファイルAでexportした型がファイルBでimportされているが、フィールド定義が異なる
2. index.tsのエクスポート一覧に新規型ファイルが追加されていない
3. 使用例セクションの型の使い方がバリデーション仕様セクションの定義と矛盾している

## 実行手順

### Step 1｜型ファイル間の相互参照チェック

設計書で定義されたすべての型ファイル間のimport/export関係を整理し、不整合を検出する。

```
| # | ファイル | export型 | import元ファイル | import型 | 整合 | 備考 |
|----|---------|---------|----------------|---------|------|------|
| 1 | types/plan.ts | Plan, PlanType | types/estimate.ts | Plan | OK | |
| 2 | types/plan.ts | PlanFormState | types/index.ts | PlanFormState | OK | re-export |
| 3 | types/estimate.ts | Estimate | types/plan.ts | - | - | 循環参照なし |
| 4 | types/option.ts | Option | types/estimate.ts | Option | OK/NG | |
| 5 | types/discount.ts | DiscountType | types/plan.ts | DiscountType | OK/NG | |
| ... | | | | | | |
```

確認観点:
- 循環参照（A→B→A）が発生していないか
- index.tsで全型が正しくre-exportされているか
- 同名の型が複数ファイルで定義されていないか

### Step 2｜共通レビュー観点 A〜D 最終確認

Phase 2A〜3の結果を踏まえ、共通レビュー観点A〜Dの最終確認を行う。

```
| 観点 | 確認内容 | Phase 2A結果 | Phase 2B結果 | Phase 2C結果 | Phase 3結果 | 最終判定 |
|------|---------|-------------|-------------|-------------|-------------|---------|
| A: 上流ドキュメント整合性 | basic-design-frontend.md、detail-design-frontend.md、detail-design-store.mdとの整合 | Pass/NG | Pass/NG | - | Pass/NG | Pass/NG |
| B: 最新仕様書整合性 | specs/配下の最新仕様との整合 | - | - | Pass/NG | Pass/NG | Pass/NG |
| C: 最新サービス仕様整合性 | プラン体系・料金ルール等との整合 | Pass/NG | Pass/NG | Pass/NG | - | Pass/NG |
| D: リポジトリ実装整合性 | 既存型定義ファイルとの整合 | - | - | - | Pass/NG | Pass/NG |
```

NGの観点がある場合、該当Phaseに戻って修正する。

### Step 4｜用語辞書・要件トレーサビリティチェック

設計書の用語が統一されているか、および要件まで遡れるか確認する（参照: knowhow/01_requirements-traceability.md、knowhow/02_design-consistency.md）。

**用語チェック:**
```
| # | 概念 | 型定義での名称 | 他設計書での名称 | 用語辞書の正式名称 | 統一 |
|---|------|-------------|-------------|-----------------|------|
| 1 | ...  | ...         | ...         | ...             | OK/NG |
```

**トレーサビリティチェック:**
```
| # | 型名 | 対応する画面/機能 | 基本設計の対応箇所 | 要件の対応箇所 | トレース可否 |
|---|------|---------------|----------------|-------------|-----------|
| 1 | ...  | ...           | ...            | ...         | OK/NG     |
```

チェック観点:
- 型の命名規則（knowhow/09_maintainability-readability.md）に準拠しているか
- 全型定義が上流設計書の画面/機能要件から辿れるか
- 要件に基づかない「孤立した型定義」がないか
- 曖昧表現（「適切に」「必要に応じて」）が排除されているか

### 最終判定

- 全Phase・全Stepが「Pass」であれば、人間レビューへ提出可能
- 1つでも「NG」があれば、該当Phaseに戻って修正後、再度本Phaseを実行する
- 残課題がある場合は、課題一覧を添えて人間レビューへ提出し、レビュー時に確認を求める

## 判定基準

- 全型ファイル間で循環参照がなく、import/exportが整合していればPass
- 共通レビュー観点A〜Dがすべて最終PassであればPass
- 用語・命名の一貫性と要件トレーサビリティが確保されていればPass
- 最終サマリーテーブルの全行がPassであれば、人間レビューへ提出
