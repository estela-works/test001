# Phase 2B｜制約・インデックスチェック

## 問い

> テーブルの制約定義（NOT NULL、FK、UNIQUE等）とインデックス設計が最新の仕様書（specs/）と整合しているか？

## チェック対象

詳細設計書の制約定義（PRIMARY KEY、FOREIGN KEY、NOT NULL、UNIQUE、CHECK）とインデックス定義が、仕様書のビジネスルール・データ整合性要件と一致しているか。

## 典型的ミス

- プラン名の一意性制約（UNIQUE）が仕様書で求められているのにテーブル定義に未設定
- 割引ルールテーブルのFK制約が未定義で、存在しないプランIDの割引が登録可能になっている
- キャンペーン開始日 <= 終了日のCHECK制約が未設定
- 見積検索で頻用されるユーザーID+作成日の複合インデックスが未定義

## 実行手順

### Step 1｜制約定義の全抽出

詳細設計書から全テーブルの制約定義を抽出する。

```
| # | テーブル名 | カラム名 | NOT NULL | PK | FK(参照先) | UNIQUE | CHECK | 備考 |
|---|----------|---------|---------|----|-----------|----- --|-------|------|
| 1 | ...      | ...     | ...     | ...| ...      | ...    | ...   | ...  |
```

### Step 2｜仕様書のビジネスルールとの照合

仕様書で定義されたデータ整合性ルールが、制約として正しく定義されているか確認する。

```
| # | ビジネスルール | 期待される制約 | 詳細設計の制約 | 一致 | 備考 |
|---|-------------|-------------|-------------|------|------|
| 1 | ...         | ...         | ...         | OK/NG | ... |
```

### Step 3｜インデックス設計の妥当性確認

検索パターン・ソート要件に対して適切なインデックスが設計されているか確認する。

```
| # | 検索パターン | 対象カラム | インデックス種別 | 定義有無 | 備考 |
|---|------------|----------|---------------|---------|------|
| 1 | ...        | ...      | B-tree/複合    | あり/なし | ... |
```

## 判定基準

- 全ビジネスルールに対応する制約が定義され、主要検索パターンにインデックスが設定されていればPass
- 未定義の制約またはインデックスがある場合は、詳細設計書を修正してから次のPhaseへ進む
