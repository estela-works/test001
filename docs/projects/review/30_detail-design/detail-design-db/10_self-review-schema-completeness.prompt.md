# Phase 2A｜スキーマ網羅性チェック

## 問い

> テーブル・カラム定義が基本設計（basic-design-backend.md）で定義されたデータモデルを過不足なくカバーしているか？

## チェック対象

詳細設計書のテーブル定義・カラム定義が、基本設計で定義されたEntity・データモデルの全項目を漏れなく反映しているか。

## 典型的ミス

- 基本設計の「プランEntity」に定義された「契約期間」フィールドに対応するカラムがテーブル定義にない
- 基本設計で必要とされた「割引ルールマスタ」テーブルが詳細設計に存在しない
- キャンペーンの有効期間（開始日・終了日）のカラムが1つだけ（終了日が欠落）
- プラン料金履歴テーブルが設計されておらず、料金改定の履歴追跡ができない

## 実行手順

### Step 1｜基本設計からのデータモデル抽出

basic-design-backend.mdから、全Entity・データ項目を抽出する。

```
| # | Entity名 | フィールド名 | データ型 | 基本設計の該当箇所 |
|---|----------|-----------|---------|-------------------|
| 1 | ...      | ...       | ...     | ...               |
```

### Step 2｜詳細設計テーブル定義との照合

基本設計のデータモデルと詳細設計のテーブル・カラム定義を突合する。

```
| # | Entity/テーブル | フィールド/カラム | 基本設計 | 詳細設計 | データ型一致 | 備考 |
|---|---------------|----------------|---------|---------|------------|------|
| 1 | ...           | ...            | あり    | あり    | OK/NG      | ...  |
```

### Step 3｜ドメイン固有テーブルの確認

携帯プラン見積アプリに必要なマスタテーブル・履歴テーブルが網羅されているか確認する。

```
| # | テーブル種別 | テーブル名 | 用途 | 存在 | 備考 |
|---|-----------|----------|------|------|------|
| 1 | プランマスタ | ...     | ...  | あり/なし | ... |
| 2 | 割引ルール  | ...     | ...  | あり/なし | ... |
| 3 | キャンペーン | ...     | ...  | あり/なし | ... |
| 4 | 料金履歴    | ...     | ...  | あり/なし | ... |
```

## 判定基準

- 全データモデル項目に対応するテーブル・カラムが存在し、データ型が一致すればPass
- 1つでも欠落またはNGがあれば、詳細設計書を修正してから次のPhaseへ進む
