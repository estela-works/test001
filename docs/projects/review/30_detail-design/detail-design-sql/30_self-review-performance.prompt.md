# Phase 2C｜パフォーマンスチェック

## 問い

> SQLのパフォーマンス設計（インデックス利用、N+1回避、データ量考慮）が最新のサービス仕様の要件を満たしているか？

## チェック対象

詳細設計書のSQLがインデックスを適切に利用し、N+1問題を回避し、想定データ量でのパフォーマンス要件を満たす設計になっているか。

## 典型的ミス

- プラン検索SQLのWHERE条件カラムにインデックスが定義されておらず、フルスキャンが発生する
- 見積一覧取得で割引情報を個別にSELECTしており、N+1問題が発生する
- LIKEの前方一致検索ではなく中間一致（%keyword%）になっておりインデックスが効かない
- 大量の見積履歴データに対するORDER BY + LIMITでソートキーにインデックスがない

## 実行手順

### Step 1｜インデックス利用状況の確認

各SQLのWHERE句・JOIN句・ORDER BY句で使用されるカラムに、DB設計でインデックスが定義されているか確認する。

```
| # | SQL ID | 使用カラム | 使用箇所 | インデックス有無 | インデックス種別 | 備考 |
|---|--------|----------|---------|---------------|--------------|------|
| 1 | ...    | ...      | WHERE   | あり/なし      | ...          | ...  |
```

### Step 2｜N+1問題の検出

一覧取得系SQLについて、関連データの取得方法を確認し、N+1パターンがないか検出する。

```
| # | 処理名 | メインSQL | 関連データ取得方法 | N+1リスク | 対策（JOIN/バッチ等） |
|---|--------|---------|----------------|----------|-------------------|
| 1 | ...    | ...     | ...            | あり/なし | ...               |
```

### Step 3｜データ量・パフォーマンス影響の評価

想定データ量での実行計画を考慮し、パフォーマンスリスクを評価する。

```
| # | SQL ID | 想定データ量 | 実行計画の懸念 | パフォーマンスリスク | 対策 |
|---|--------|-----------|-------------|-----------------|------|
| 1 | ...    | ...       | ...         | 高/中/低         | ...  |
```

### Step 4｜非機能要件・ページング設計との照合

SQLパフォーマンス設計が非機能要件を満たしているか確認する（参照: knowhow/05_performance-scalability.md）。

```
| # | SQL ID | 対応する非機能要件 | 目標値 | 設計上の懸念 | ページング対応 | 対応状況 |
|---|--------|----------------|--------|-----------|------------|---------|
| 1 | ...    | レスポンス1秒以内  | ...    | ...       | OK/NG/不要  | OK/NG   |
```

チェック観点:
- 性能目標値が定量的に定義されているか（曖昧な「高速」等でないか）
- 大量データ取得時にページング（LIMIT/OFFSET、カーソルベース）が設計されているか
- データ量の年間増加率と保持期間を考慮した設計か
- スロークエリの検知・アラート基準が定義されているか
- DBコネクションプールのサイズが設計されているか

## 判定基準

- 全SQLでインデックスが適切に利用され、N+1問題がなく、パフォーマンスリスクが許容範囲内であればPass
- 非機能要件の性能目標値を達成できる設計であればPass
- 高リスクの問題がある場合は、詳細設計書を修正してから次のPhaseへ進む
