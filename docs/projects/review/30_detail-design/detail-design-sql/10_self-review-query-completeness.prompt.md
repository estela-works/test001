# Phase 2A｜クエリ網羅性チェック

## 問い

> 基本設計（basic-design-backend.md）およびDB設計（detail-design-db.md）で必要とされる全データ操作に対応するSQLクエリが揃っているか？

## チェック対象

詳細設計書のSQL一覧が、基本設計の処理フロー・DB設計のテーブル定義から導かれる全データ操作を過不足なくカバーしているか。

## 典型的ミス

- 基本設計の「プラン一覧取得（条件付きフィルタ）」に対応するSELECTクエリが存在しない
- DB設計で定義された中間テーブル（プラン_割引_関連）へのINSERT/DELETEクエリが漏れている
- 基本設計の「見積履歴取得」に必要なJOINクエリが単テーブルSELECTになっている
- マスタデータ更新（プラン料金改定等）のUPDATEクエリが未定義

## 実行手順

### Step 1｜上流設計からのデータ操作一覧抽出

basic-design-backend.mdとdetail-design-db.mdから、SQL化が必要な全データ操作を抽出する。

```
| # | 処理名 | 操作種別(CRUD) | 対象テーブル | 上流設計の該当箇所 |
|---|--------|-------------|------------|-------------------|
| 1 | ...    | SELECT      | ...        | ...               |
| 2 | ...    | INSERT      | ...        | ...               |
```

### Step 2｜詳細設計SQLとの照合

抽出したデータ操作一覧と詳細設計のSQL定義を突合する。

```
| # | 処理名 | 上流の操作 | 詳細設計のSQL ID | 操作種別一致 | 対象テーブル一致 | 備考 |
|---|--------|----------|----------------|------------|---------------|------|
| 1 | ...    | ...      | ...            | OK/NG      | OK/NG         | ...  |
```

### Step 3｜パラメータ・結果マッピングの確認

各SQLのバインドパラメータと結果セットが、呼び出し元（Service/Repository）の期待と一致しているか確認する。

```
| # | SQL ID | バインドパラメータ | 結果セットのカラム | 呼び出し元の期待 | 一致 |
|---|--------|----------------|-----------------|---------------|------|
| 1 | ...    | ...            | ...             | ...           | OK/NG |
```

## 判定基準

- 全データ操作に対応するSQLが存在し、パラメータ・結果マッピングが正しければPass
- 1つでも欠落またはNGがあれば、詳細設計書を修正してから次のPhaseへ進む
