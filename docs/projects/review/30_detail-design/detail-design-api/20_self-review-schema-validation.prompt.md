# Phase 2B｜スキーマ・バリデーションチェック

## 問い

> リクエスト/レスポンスのスキーマ定義とバリデーションルールが最新の仕様書（specs/）と整合しているか？

## チェック対象

詳細設計書のリクエストボディ・レスポンスボディの型定義、バリデーションルールが、最新の仕様書と一致しているか。

## 典型的ミス

- 仕様書で必須項目に変更されたフィールドが、詳細設計ではOptionalのままになっている
- プラン料金の桁数制約（例：最大6桁）がバリデーションルールに反映されていない
- レスポンスに含まれるべき割引適用後の金額フィールドが欠落している
- 日付フォーマット（ISO 8601）が仕様書と詳細設計で異なる

## 実行手順

### Step 1｜リクエスト/レスポンススキーマの全抽出

詳細設計書から全エンドポイントのリクエスト・レスポンス定義を抽出する。

```
| # | エンドポイント | 方向 | フィールド名 | 型 | 必須/任意 | バリデーション |
|---|-------------|------|-----------|---|---------|-------------|
| 1 | ...         | Req  | ...       | ...| ...    | ...         |
| 2 | ...         | Res  | ...       | ...| ...    | -           |
```

### Step 2｜仕様書との照合

specs/配下の最新仕様書と突合し、型・必須/任意・制約の整合性を確認する。

```
| # | エンドポイント | フィールド | 詳細設計の定義 | 仕様書の定義 | 一致 | 備考 |
|---|-------------|----------|-------------|-------------|------|------|
| 1 | ...         | ...      | ...         | ...         | OK/NG | ... |
```

### Step 3｜バリデーションルールの網羅性確認

全リクエストフィールドに対して、適切なバリデーションルールが設定されているか確認する。

```
| # | エンドポイント | フィールド | 型チェック | 桁数/範囲 | 形式チェック | 必須チェック | 備考 |
|---|-------------|----------|----------|----------|-----------|------------|------|
| 1 | ...         | ...      | OK/NG    | OK/NG    | OK/NG     | OK/NG      | ...  |
```

### Step 4｜データフロー整合性チェック

全レイヤーを通してデータの型・名前が一貫しているか確認する（参照: knowhow/03_interface-design.md）。

```
| # | データ項目 | DB定義(型) | BE定義(型) | APIレスポンス(型) | FE定義(型) | 一貫性 | 備考 |
|---|----------|----------|----------|---------------|----------|--------|------|
| 1 | ...      | ...      | ...      | ...           | ...      | OK/NG  | ...  |
```

チェック観点:
- 各レイヤー間で型変換が正しく設計されているか（例: DB INTEGER → BE Long → API number → FE number）
- snake_case / camelCase の変換ルールが統一されているか
- 日付フォーマット（ISO 8601）が全レイヤーで統一されているか
- レスポンスサイズ: プロパティ数は20以下、ネスト深さは3層以内か
- 配列レスポンスはオブジェクトでラップされているか（`{ "items": [...] }`）
- null値の扱い: 不要なキーはJSONから除外する設計か

## 判定基準

- 全スキーマが仕様書と一致し、全フィールドに適切なバリデーションが設定されていればPass
- データフローが全レイヤーで一貫していればPass
- 不一致または未設定のバリデーションがある場合は、詳細設計書を修正してから次のPhaseへ進む
