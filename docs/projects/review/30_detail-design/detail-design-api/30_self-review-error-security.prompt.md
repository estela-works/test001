# Phase 2C｜エラーレスポンス・セキュリティチェック

## 問い

> エラーレスポンス設計とセキュリティ対策が最新のサービス仕様と整合しているか？

## チェック対象

詳細設計書のエラーレスポンス定義（HTTPステータスコード、エラーボディ）、認証・認可設計、入力サニタイズがサービス仕様の要件を満たしているか。

## 典型的ミス

- 404と400の使い分けがサービス仕様のエラーコード体系と異なる
- バリデーションエラー時のレスポンスボディにフィールド単位のエラー詳細が含まれていない
- 見積APIで認証なしアクセスが許可されているが、サービス仕様では認証必須
- エラーメッセージにDB内部情報（テーブル名等）が漏洩する設計になっている
- エラーレスポンスがRFC 9457 Problem Details形式に準拠していない
- セキュリティヘッダー（CSP、HSTS等）の設計が漏れている
- エラーメッセージに「何が起きたか」のみで「どうすればよいか」が含まれていない

## 実行手順

### Step 1｜エラーレスポンス定義の全抽出

詳細設計書から全エンドポイントのエラーレスポンス定義を抽出する。

```
| # | エンドポイント | HTTPステータス | エラーコード | エラーメッセージ | 発生条件 |
|---|-------------|-------------|-----------|-------------|---------|
| 1 | ...         | 400         | ...       | ...         | ...     |
| 2 | ...         | 404         | ...       | ...         | ...     |
| 3 | ...         | 500         | ...       | ...         | ...     |
```

### Step 2｜サービス仕様のエラー体系との照合

サービス仕様で定義されたエラーコード体系・レスポンス形式との整合性を確認する。

```
| # | エラー種別 | 詳細設計の定義 | サービス仕様の定義 | 一致 | 備考 |
|---|----------|-------------|-----------------|------|------|
| 1 | ...      | ...         | ...             | OK/NG | ... |
```

### Step 3｜セキュリティチェックリスト

各エンドポイントのセキュリティ対策を確認する（参照: knowhow/04_security-design.md）。

```
| # | エンドポイント | 認証要否 | 認可レベル | 入力サニタイズ | 情報漏洩防止 | 対応状況 |
|---|-------------|---------|----------|-----------|-----------|---------|
| 1 | ...         | ...     | ...      | OK/NG     | OK/NG     | OK/NG   |
```

### Step 4｜OWASP Top 10・セキュリティ設計チェック

OWASP Top 10に基づくセキュリティ対策が設計に含まれているか確認する。

```
| # | OWASP項目 | 対策内容 | 設計書の記載 | 対応状況 |
|---|----------|---------|-----------|---------|
| 1 | A01 アクセス制御の不備 | RBAC/ABAC設計、リソース単位の認可チェック | ... | OK/NG |
| 2 | A04 認証の不備 | セッション管理、パスワードポリシー | ... | OK/NG |
| 3 | A05 暗号化の失敗 | TLS、機密データ暗号化 | ... | OK/NG |
| 4 | A07 インジェクション | SQLインジェクション、XSS、CSRF対策 | ... | OK/NG |
| 5 | A08 ログと監視の不足 | 監査ログ出力項目・保存期間 | ... | OK/NG |
```

追加チェック:
- セキュリティヘッダーの設定が定義されているか（CSP、X-Content-Type-Options、HSTS、X-Frame-Options、Referrer-Policy）
- Cookie属性（`Secure`、`HttpOnly`、`SameSite=Lax`）が必須設定されているか
- 機密データ（パスワード、トークン、個人情報）がログ・エラーメッセージに出力されない設計か
- エラーレスポンスにスタックトレースや内部情報が露出しない設計か

### Step 5｜エラーメッセージ品質チェック

エラーメッセージが利用者にとって有用な情報を含んでいるか確認する（参照: knowhow/06_error-handling.md）。

```
| # | エラーコード | 何が起きたか | なぜ起きたか | どうすればよいか | エラーコード体系 | 品質 |
|---|-----------|-----------|-----------|-------------|-------------|------|
| 1 | ...       | OK/NG     | OK/NG     | OK/NG       | OK/NG       | OK/NG |
```

チェック観点:
- エラーコード体系（`ERR-{カテゴリ}-{連番}`）が定義されているか
- エラーレスポンスがRFC 9457 Problem Details形式に準拠しているか
- HTTPステータスコードの使い分けが適切か（400 vs 422、401 vs 403 等）
- 楽観ロック競合時に409を返す設計か

## 判定基準

- 全エンドポイントのエラーレスポンスがサービス仕様と一致し、セキュリティ対策が網羅されていればPass
- OWASP Top 10の主要項目への対策が設計に含まれていればPass
- エラーメッセージが4要素（何が・なぜ・どうすれば・エラーコード）を満たしていればPass
- 不一致または未対応がある場合は、詳細設計書を修正してから次のPhaseへ進む
