# 07. テストカバレッジ・テスト戦略

テスト設計の品質をレビューするためのノウハウ。テストレベルの設計、カバレッジ基準、観点リストの活用方法を整理する。

## なぜ重要か

- テストが不十分だとリリース後に障害が発生する
- テストが過剰だとコストが膨大になり、実行時間も長期化する
- 適切なテスト戦略がテスト効率と品質のバランスを取る

## テストレベルの設計

### テストピラミッド

```
          /  E2Eテスト  \        ← 少数・高コスト・遅い
         / 結合テスト     \      ← 中程度
        / 単体テスト        \    ← 多数・低コスト・速い
```

| テストレベル | 目的 | 担保すること |
|------------|------|------------|
| 単体テスト | 個々のメソッド・関数の動作確認 | ロジックの正しさ |
| 結合テスト | コンポーネント間の連携確認 | API-DB間、コンポーネント間のデータ受け渡し |
| E2Eテスト | ユーザー操作の一連のフロー確認 | ビジネスシナリオの実現 |

### テストレベル間の重複排除

| 確認事項 | 単体 | 結合 | E2E |
|---------|------|------|-----|
| ビジネスロジック | ○ | | |
| バリデーション | ○ | | |
| API-DB連携 | | ○ | |
| 認証・認可フロー | | ○ | |
| 画面遷移 | | | ○ |
| ユーザーシナリオ | | | ○ |

各レベルで何をテストするかを明確にし、重複テストを避ける。

## カバレッジの種類

### コードカバレッジ

| 種類 | 基準 | 特徴 |
|------|------|------|
| C0（命令網羅） | すべての命令を1回以上実行 | 最低限の基準。分岐の片方しかテストしない可能性 |
| C1（分岐網羅） | すべての分岐をtrue/false両方実行 | 実用的な基準。多くのプロジェクトで採用 |
| C2（条件網羅） | 複合条件の各条件をtrue/false両方実行 | 高品質だがテスト数が増大 |
| MC/DC | 各条件が独立して結果に影響することを確認 | 安全性重視システム向け |

### 要件カバレッジ

コードカバレッジだけでなく、要件カバレッジも重要。

```
要件カバレッジ = テストケースが紐づく要件数 / 全要件数 × 100%
```

- 目標: 100%（すべての要件にテストケースが存在する）
- 未対応の要件がないことを確認する

## テスト観点リスト

### 機能テスト観点

| カテゴリ | 観点 |
|---------|------|
| 正常系 | 正しい入力で期待どおりの結果が得られるか |
| 異常系 | 不正入力でエラーメッセージが適切に表示されるか |
| 境界値 | 上限値、下限値、上限+1、下限-1 |
| 同値分割 | 有効/無効な入力値のグループ |
| 状態遷移 | 各状態からの遷移が正しく動作するか |
| 組み合わせ | 複数条件の組み合わせ（ペアワイズテスト等） |

### 非機能テスト観点

| カテゴリ | 観点 |
|---------|------|
| 性能 | レスポンスタイムが目標値以内か |
| 負荷 | 同時接続数上限での動作 |
| セキュリティ | 認証・認可・インジェクション |
| 互換性 | ブラウザ・OS・デバイスの互換性 |
| アクセシビリティ | スクリーンリーダー対応、キーボード操作 |
| ユーザビリティ | 操作の直感性、エラーからの回復 |

### ドメイン固有テスト観点（料金計算アプリの例）

| 観点 | テスト項目例 |
|------|------------|
| 料金プラン | 全プランの基本料金が正しく計算されるか |
| オプション組み合わせ | 排他的なオプションの同時選択が防止されるか |
| 割引適用 | 複数割引の適用順序・上限が正しいか |
| 税計算 | 消費税の端数処理（切捨て/四捨五入）が正しいか |
| 日割り計算 | 月途中の申込/解約時の日割り計算が正しいか |

## テスト設計のレビュー観点

### カバレッジの十分性

- [ ] すべての要件に対応するテストケースが存在するか
- [ ] 正常系・異常系・境界値が網羅されているか
- [ ] コードカバレッジの目標値が設定されているか（推奨: C1 80%以上）
- [ ] テストケースの総数が妥当か（多すぎ/少なすぎ）

### テスト独立性

- [ ] テストケース間に依存関係がないか（実行順序に依存しない）
- [ ] テストデータが他のテストと共有されていないか
- [ ] 外部依存（API、DB）が適切にモック化されているか

### 期待結果の明確性

- [ ] 期待結果が「正しく動作すること」等の曖昧な表現でないか
- [ ] 具体的な値（ステータスコード200、レスポンスボディのJSON構造等）で記述されているか
- [ ] エラーケースのエラーコード・メッセージが明記されているか

### テストレベルの適切性

- [ ] 単体テストでテストすべき内容がE2Eに書かれていないか
- [ ] テストレベル間の境界が明確か
- [ ] 各レベルで何を保証するかが定義されているか

## アンチパターン

| パターン名 | 症状 | 処方 |
|-----------|------|------|
| アイスクリームコーン | E2Eテストが大量で単体テストが少ない | テストピラミッドに従いリバランス |
| ハッピーパスのみ | 正常系しかテストしていない | 異常系・境界値テストを追加 |
| テストの重複 | 同じ確認を複数レベルで実施 | テストレベルごとの責務を明確化 |
| 曖昧な期待結果 | 「正しく表示される」等 | 具体的な値・状態で記述 |
| テストケースの肥大化 | 1ケースで複数のことを確認 | 1テスト1検証に分割 |
