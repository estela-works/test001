# 01. 要件トレーサビリティ

要件定義から設計・実装・テストまで、各成果物間の追跡性を確保するためのノウハウ。

## なぜ重要か

- 要件の抜け漏れを早期に発見できる
- 変更影響範囲を正確に把握できる
- テスト網羅性の根拠を示せる
- 人間レビュー時に「この設計はどの要件に基づくか」を即答できる

## トレーサビリティマトリクス（TM）

### 基本構造

```
要件ID → 基本設計項目 → 詳細設計項目 → 実装ファイル → テストケースID
REQ-001 → BD-FUNC-001 → DD-API-001 → UserController.java → TC-API-001
```

### 作成のポイント

| ポイント | 説明 |
|---------|------|
| 双方向リンク | 上流→下流だけでなく、下流→上流のリンクも維持する |
| 粒度の統一 | 要件の粒度と設計の粒度が1:Nになるのは正常。N:Mは粒度見直しのサイン |
| 空行の検出 | マトリクスに空欄がある＝未対応の要件 or 根拠のない設計 |
| 変更時の更新 | 要件変更時にTMを必ず更新し、影響範囲を可視化する |

### よくある問題と対策

| 問題 | 原因 | 対策 |
|------|------|------|
| TMが形骸化する | 作成後に更新されない | 設計変更時のチェックリストにTM更新を組み込む |
| 粒度がバラバラ | 要件と設計で分割基準が異なる | 要件IDの命名規則を最初に定義する |
| 暗黙の要件がある | 非機能要件や業務慣行が文書化されていない | 要件整理時に「暗黙の前提」セクションを設ける |
| 派生要件の追跡漏れ | 設計中に生まれた追加要件を管理しない | 派生要件にも専用IDを付与し、元要件との関連を記録 |

## レビュー時のチェックポイント

### 要件定義書レビュー

- [ ] すべての要件にユニークIDが振られているか
- [ ] 機能要件と非機能要件が分離されているか
- [ ] 各要件に優先度・受入基準が定義されているか
- [ ] 要件間の依存関係が明記されているか
- [ ] 用語集が定義され、用語が統一されているか

### 基本設計書レビュー

- [ ] すべての要件IDが基本設計のどこかに紐づいているか
- [ ] 基本設計に要件IDのない「孤立した設計項目」がないか
- [ ] 1つの要件が複数設計項目に分割される場合、分割理由が明記されているか
- [ ] 非機能要件（性能、セキュリティ等）の設計への反映箇所が特定されているか

### 詳細設計書レビュー

- [ ] 基本設計の各機能が詳細設計に展開されているか
- [ ] API・DB・ロジックの各詳細設計が相互に参照し合っているか
- [ ] 詳細設計から要件まで遡れるか（逆方向トレーサビリティ）

### テスト仕様書レビュー

- [ ] すべての要件に対応するテストケースが存在するか
- [ ] テストケースから要件・設計への逆引きが可能か
- [ ] 要件変更があった場合、対応テストケースが更新されているか

## アンチパターン

| パターン名 | 症状 | 処方 |
|-----------|------|------|
| ID振り忘れ症候群 | 途中から追加した要件にIDがない | IDの自動採番ルールを決めておく |
| コピペ汚染 | 類似要件をコピペして修正漏れ | コピー元との差分を必ず明記する |
| 暗黙知依存 | 「当然わかるはず」で書かない | 第三者が読んで理解できるか確認する |
| 過剰分割 | 1要件を細かく分割しすぎて全体像が見えない | 要件グループを設けて階層管理する |
