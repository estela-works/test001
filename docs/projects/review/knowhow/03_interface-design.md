# 03. インターフェース設計

API・画面・外部連携のインターフェース設計をレビューする際のノウハウ。

## なぜ重要か

- インターフェースは複数チーム・コンポーネントの境界であり、認識のずれが最も起きやすい
- API設計の問題は後から修正するコストが非常に高い（利用者への影響）
- 画面設計のミスはユーザー体験を直接損なう

## REST API設計のレビュー観点

### エンドポイント設計

| チェック項目 | ベストプラクティス |
|------------|------------------|
| リソース指向 | 動詞でなく名詞を使う（`POST /orders` ○、`POST /createOrder` ×） |
| 命名規則 | パスはkebab-case＋複数形（`/delivery-schedules`） |
| 階層構造 | 親に強く紐づく場合はネスト（`/articles/1/comments`）、独立なら別リソース |
| バージョニング | パス方式（`/v1/users`）を推奨 |
| カスタム操作 | RPC的操作は `POST /drafts/{id}/copy` のようにパスで表現 |

### HTTPメソッドの適切な使い分け

| メソッド | 用途 | 冪等性 | 注意点 |
|---------|------|--------|--------|
| GET | 参照 | あり | キャッシュ可能。副作用を持たせない |
| POST | 作成・複雑な検索 | なし | 検索条件が複雑な場合はPOSTも可 |
| PUT | リソース全体の置換 | あり | 新規作成には原則使わない |
| PATCH | 部分更新 | なし | JSON Merge Patch形式推奨 |
| DELETE | 削除 | あり | 楽観ロック時はクエリで`.lock_no`を渡す |

### リクエスト/レスポンス設計

| チェック項目 | ベストプラクティス |
|------------|------------------|
| クエリパラメータ | snake_case（`order_id`）。標準項目: `q`, `sort`, `fields`, `limit` |
| 配列のラップ | 配列はオブジェクトでラップする（`{ "items": [...] }`） |
| null値 | 不要なキーは除外し、JSONから除く |
| 日付 | ISO 8601形式（`2023-09-30T00:00:00Z`） |
| レスポンスサイズ | プロパティ数は20以下、ネスト深さは3層まで |

### HTTPステータスコード

| コード | 用途 | 使い分けのポイント |
|--------|------|------------------|
| 200 | 成功 | GET、PUT、PATCH、DELETE |
| 201 | 同期的作成成功 | POST で即座に作成完了した場合 |
| 202 | 非同期受付 | 処理が即完了しない場合 |
| 204 | 成功（レスポンスなし） | DELETE 成功時など |
| 400 | バリデーション失敗 | 入力値の形式エラー |
| 401 | 認証失敗 | トークン無効・期限切れ |
| 403 | 認可失敗 | 権限不足 |
| 404 | リソース不在 | |
| 409 | 楽観ロック競合 | 同時更新の衝突 |
| 422 | ビジネスロジック検証失敗 | 入力形式は正しいが業務ルール違反 |

### エラーレスポンス

RFC 9457 Problem Details形式を推奨。

```json
{
  "type": "https://example.com/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "errors": [
    {
      "field": "email",
      "message": "メールアドレスの形式が不正です"
    }
  ]
}
```

## 画面インターフェース設計

### レビュー観点

| 観点 | チェック項目 |
|------|------------|
| レイアウト | 文字サイズ、文字数制限、項目幅、テーブルレイアウト |
| 画面遷移 | 同タブ・新タブ・モーダルの使い分けが統一されているか |
| 操作 | ボタン押下時の挙動（ローディング、二重押下防止） |
| フィードバック | 成功・エラー・警告の表示方法が統一されているか |
| レスポンシブ | 各画面サイズでのレイアウト崩れがないか |

### データフロー整合性（DB→BS→BFF→FE）

全レイヤーを通してデータの型・名前が一貫しているか確認する。

```
DB: plans.monthly_fee (INTEGER)
  → BE: Plan.monthlyFee (Long)
    → API Response: { "monthly_fee": 3000 }
      → FE: plan.monthlyFee (number)
```

## 外部連携インターフェース

| チェック項目 | 内容 |
|------------|------|
| 通信プロトコル | HTTP/HTTPS、WebSocket、gRPC等の選定理由 |
| 認証方式 | APIキー、OAuth2、クライアント証明書 |
| タイムアウト | 接続タイムアウト、読み取りタイムアウトの設定値 |
| リトライ | リトライ回数、間隔、べき等性の考慮 |
| データ形式 | JSON、XML、CSV等の仕様合意 |
| 文字コード | UTF-8の統一、BOM有無 |

## レビュー時のチェックポイント

- [ ] RESTリソース指向で設計されているか
- [ ] HTTPメソッドが適切に使い分けられているか（PUT/PATCHの混在なし）
- [ ] バージョニングはパス方式か
- [ ] エラーレスポンスはProblem Details形式か
- [ ] 楽観ロックの方式が定義されているか
- [ ] ヘルスチェックエンドポイント（`/health`）が定義されているか
- [ ] 画面項目とAPI項目の対応が取れるか
- [ ] 全レイヤーのデータ型が一貫しているか
