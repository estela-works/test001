# 02. 設計の一貫性・整合性

ドキュメント間およびドキュメント内の矛盾を検出し、設計品質を確保するためのノウハウ。

## なぜ重要か

- 設計書間の矛盾は実装時の手戻りに直結する
- 用語の不統一は誤解を生み、バグの原因になる
- 一貫性のない設計書はレビュー効率を著しく低下させる

## 一貫性チェックの3つのレベル

### Level 1: ドキュメント内の一貫性

同一ドキュメント内での矛盾検出。

| チェック項目 | 具体例 |
|------------|--------|
| 用語の統一 | 「ユーザー」と「利用者」が混在していないか |
| 表記の統一 | 「〜する」「〜を行う」等の語尾が統一されているか |
| ID体系の統一 | REQ-001, REQ-002...のように連番が飛んでいないか |
| 図表と本文の整合 | 図に描かれた要素が本文で説明されているか |
| 前提条件の一貫性 | 序盤で述べた前提が後半で矛盾していないか |

### Level 2: 同一フェーズ内の横断整合性

同じ設計フェーズの複数ドキュメント間での矛盾検出。

| チェック項目 | 具体例 |
|------------|--------|
| エンティティ定義 | BE基本設計のエンティティとDB設計のテーブルが一致するか |
| API定義 | API設計のリクエスト/レスポンスとFE設計のデータ型が一致するか |
| エラーコード | ロジック設計で発生するエラーがAPI設計のレスポンスに定義されているか |
| 状態遷移 | FE設計の画面状態とBE設計のビジネスステータスが対応しているか |

### Level 3: フェーズ間の縦断整合性

要件定義→基本設計→詳細設計→テスト仕様の段階間での矛盾検出。

| チェック項目 | 具体例 |
|------------|--------|
| 要件の反映漏れ | 要件定義にある機能が基本設計に存在しないか |
| 勝手な解釈変更 | 基本設計で要件の意味が変わっていないか |
| 詳細化の妥当性 | 基本設計の抽象表現が詳細設計で正しく具体化されているか |
| スペック仕様の反映 | 最新の仕様書（料金、割引ルール等）が反映されているか |

## 突合テクニック

### 表形式での機械的突合

感覚的なレビューではなく、表を作って機械的に照合する。

```
| 基本設計の機能 | 詳細設計(API) | 詳細設計(DB) | 詳細設計(FE) | 整合 |
|--------------|--------------|-------------|-------------|------|
| プラン一覧表示 | GET /plans   | plans テーブル | PlanList.vue | OK   |
| プラン詳細表示 | GET /plans/:id | plans テーブル | PlanDetail.vue | OK |
| 見積計算      | POST /estimates | estimates テーブル | ???        | NG   |
```

### 用語辞書の活用

プロジェクト開始時に用語辞書を作成し、レビュー時に照合する。

```
| 正式用語 | 禁止表現 | 英語名 | 備考 |
|---------|---------|--------|------|
| 料金プラン | プラン、コース | plan | 「プラン」単体は曖昧なので使用禁止 |
| 割引 | 値引き、ディスカウント | discount | |
| 見積 | 見積り、見積もり | estimate | 送り仮名統一 |
```

### 変更履歴の照合

設計変更があった場合、影響する全ドキュメントの変更履歴を突合する。

## レビュー時のチェックポイント

- [ ] 用語辞書に定義された用語が全ドキュメントで統一されているか
- [ ] 同一エンティティの属性（名前、型、制約）が全設計書で一致するか
- [ ] 画面項目とAPI項目とDBカラムの対応が取れるか
- [ ] エラーメッセージの文言とエラーコードが全設計書で一致するか
- [ ] 変更があった箇所の関連ドキュメントがすべて更新されているか
- [ ] 図（ER図、画面遷移図、シーケンス図）と本文の記述が一致するか
- [ ] 数値（件数上限、タイムアウト値等）がドキュメント間で一致するか

## アンチパターン

| パターン名 | 症状 | 処方 |
|-----------|------|------|
| コピペ地獄 | 同じ定義を複数箇所にコピペし、片方だけ更新 | 定義は1箇所に集約し、他は参照リンクにする |
| 暗黙の変更 | 変更履歴に残さず修正 | 変更箇所を赤字表示、バージョン番号を更新 |
| 部分最適 | 各設計書が独立して最適化され全体で矛盾 | 横断整合性チェックを必須フェーズにする |
| 二重否定 | 「〜でないことはない」等の曖昧表現 | 肯定形で書き直す |
