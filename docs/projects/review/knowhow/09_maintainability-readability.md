# 09. 保守性・可読性・命名規則

設計書・コードの保守性と可読性を確保するためのレビューノウハウ。

## なぜ重要か

- ソフトウェアの生涯コストの80%以上は保守に費やされる
- 可読性の低いコードはバグの温床であり、変更時の影響範囲が把握しにくい
- 命名規則の不統一はチーム間のコミュニケーションコストを増大させる

## 命名規則

### 基本原則

| 原則 | 説明 | 良い例 | 悪い例 |
|------|------|--------|--------|
| 意図を表現する | 名前から目的がわかる | `calculateMonthlyFee` | `calc`, `doProcess` |
| 省略しない | 略語は避ける | `customerName` | `custNm`, `cn` |
| 一貫性を保つ | 同じ概念に同じ言葉 | `get/set/find` を統一 | `get/fetch/retrieve` が混在 |
| スコープに応じた長さ | 広いスコープ → 長い名前 | ループ変数: `i`, クラス名: `EstimateCalculationService` | 逆は読みにくい |

### 命名規約（ケース別）

| 対象 | 規約 | 例 |
|------|------|-----|
| クラス名 | PascalCase | `PlanEstimateService` |
| メソッド名 | camelCase | `calculateDiscount` |
| 変数名 | camelCase | `monthlyFee` |
| 定数 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| DBテーブル | snake_case（複数形） | `discount_rules` |
| DBカラム | snake_case | `monthly_fee` |
| APIパス | kebab-case（複数形） | `/delivery-schedules` |
| JSON項目 | snake_case | `"monthly_fee": 3000` |

### 型名のサフィックス規約

| サフィックス | 用途 | 例 |
|------------|------|-----|
| Request | APIリクエスト型 | `CreateEstimateRequest` |
| Response | APIレスポンス型 | `EstimateListResponse` |
| State | 状態管理型 | `EstimateFormState` |
| Display | 表示用型 | `PlanDisplay` |
| Error | エラー型 | `ValidationError` |
| Props | コンポーネントプロパティ | `PlanSelectorProps` |

## 設計原則（SOLID）

| 原則 | 正式名 | 設計レビューでの確認 |
|------|--------|-------------------|
| S | 単一責任原則 | 1クラス/1関数が1つの責務のみ持っているか |
| O | 開放閉鎖原則 | 拡張に開かれ、修正に閉じた設計か |
| L | リスコフの置換原則 | サブクラスがスーパークラスの代替として機能するか |
| I | インターフェース分離原則 | 不要なメソッドを実装させるインターフェースがないか |
| D | 依存性逆転原則 | 上位モジュールが下位モジュールに直接依存していないか |

## コード構造の可読性

### 関数設計

| チェック項目 | 基準 |
|------------|------|
| 関数の長さ | 30行以下が目安。50行を超えたら分割を検討 |
| 引数の数 | 3つ以下が理想。4つ以上はオブジェクトにまとめる |
| ネストの深さ | 3段以下。深いネストは早期リターンで解消 |
| 副作用 | 関数名から予測できない副作用がないか |

### コメント

| 書くべきコメント | 書くべきでないコメント |
|----------------|---------------------|
| WHY（なぜこの実装にしたか） | WHAT（コードが何をするか）→ コード自体で表現 |
| 業務ルールの根拠 | 自明な処理の説明 |
| TODO/FIXME（技術的負債） | コメントアウトされた古いコード |
| 正規表現等の複雑なロジック | 変更履歴（バージョン管理で追跡） |

## 設計書の可読性

### 文書品質のチェック

| チェック項目 | 内容 |
|------------|------|
| 5W1H | 誰が、何を、いつ、どこで、なぜ、どのように |
| 二重否定の回避 | 「〜でないことはない」→ 肯定形に書き直す |
| 語尾の統一 | 「〜する」「〜を行う」等を統一 |
| 図表と本文の整合 | 図に出てくる要素が本文で説明されているか |
| 曖昧表現の排除 | 「適切に」「必要に応じて」→ 具体的な条件・基準を記述 |

### 設計書のレイアウト

| ポイント | 説明 |
|---------|------|
| 見出し階層 | 3階層以内。深すぎる階層は読みにくい |
| 表の活用 | 比較・一覧は表形式で整理 |
| 図の活用 | アーキテクチャ、フロー、状態遷移は図で可視化 |
| ファイルサイズ | 500行を超えたら分割を検討（プロジェクトルール） |

## レビュー時のチェックポイント

- [ ] 命名規則が一貫して適用されているか
- [ ] クラス・関数が単一責任原則を守っているか
- [ ] 関数の長さ・引数の数・ネストの深さが基準以内か
- [ ] マジックナンバーが定数化されているか
- [ ] コメントがWHYを説明しているか（WHATの過剰なコメントがないか）
- [ ] 設計書の用語が統一されているか
- [ ] 曖昧表現（「適切に」「必要に応じて」）が排除されているか
- [ ] 設計書が500行以内に収まっているか
