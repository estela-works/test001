# 10. レビュープロセス・メトリクス

レビューの進め方、品質指標（メトリクス）、レビュー改善サイクルに関するノウハウ。

## なぜ重要か

- レビューはバグを最も早期かつ低コストで発見できる品質保証活動
- レビューの質はプロセスと指標で管理しなければ属人化する
- メトリクスなしではレビューの効果を定量的に評価できない

## レビューの種類と使い分け

| 種類 | 参加者 | 特徴 | 適用場面 |
|------|--------|------|---------|
| セルフレビュー | 作成者本人 | AIプロンプトを活用した機械的チェック | 全成果物（本プロジェクトの主要手法） |
| ピアレビュー | 同僚1〜2名 | 非公式、即座にフィードバック | 日常の設計・コード確認 |
| ウォークスルー | 作成者主導 | 作成者が説明しながら確認 | 設計方針の共有、知識伝達 |
| インスペクション | モデレータ主導 | 正式な手順に従った体系的チェック | 重要な設計書、品質基準を満たす必要がある場合 |

## レビュープロセスの設計

### 効果的なレビューの5ステップ

```
1. 計画     → レビュー対象・レビュアー・観点を決める
2. 準備     → レビュアーが事前に資料を読み込む
3. 実施     → 指摘を記録（事実と改善案を分離）
4. 修正     → 作成者が指摘を反映
5. 確認     → 修正内容の妥当性を確認
```

### レビュー計画時の決定事項

| 項目 | 内容 |
|------|------|
| レビュー対象 | どのドキュメント・コードをレビューするか |
| レビュー観点 | 何をチェックするか（チェックリスト） |
| レビュアー選定 | 必要な技量・経験を持つ人を選ぶ |
| レビュー方式 | セルフ/ピア/ウォークスルー/インスペクション |
| 時間配分 | 1回のレビュー時間（推奨: 60〜90分以内） |
| 完了基準 | 何をもってレビュー完了とするか |

### レビュアー選定のポイント

- 設計問題を見つけ出せる技量と経験を持つ人を選ぶ
- ドメイン知識を持つ人（業務観点）と技術知識を持つ人（技術観点）を組み合わせる
- レビュアーが2〜3名を超えると効率が低下する

## 指摘の分類

### 重要度分類

| 重要度 | 定義 | 対応 |
|--------|------|------|
| 致命的 | システム障害やデータ不整合を引き起こす | 必ず修正（リリースブロッカー） |
| 重要 | 機能不全や性能問題を引き起こす可能性 | 修正推奨（リスク判断） |
| 軽微 | 可読性や保守性に影響 | 可能なら修正 |
| コメント | 改善提案、情報共有 | 対応は任意 |

### 指摘タイプ分類

| タイプ | 説明 | 例 |
|--------|------|-----|
| 欠陥 | 仕様違反、ロジックミス | 要件にある機能が設計されていない |
| 矛盾 | ドキュメント間の不整合 | API設計とDB設計でカラム名が異なる |
| 曖昧 | 解釈が分かれる記述 | 「適切に処理する」の基準が不明 |
| 改善 | より良い設計の提案 | 「この部分はキャッシュを使うと性能向上する」 |
| 疑問 | 設計意図の確認 | 「このテーブルにインデックスが不要な理由は？」 |

## レビューメトリクス

### 基本メトリクス

| メトリクス | 計算方法 | 目安 |
|-----------|---------|------|
| レビュー密度 | レビュー工数(h) / 成果物規模(KL or ページ) | 設計書: 0.5〜1.0 h/ページ |
| 指摘密度 | 指摘件数 / 成果物規模 | プロジェクトの過去実績と比較 |
| 指摘修正率 | 修正済み件数 / 指摘件数 × 100% | 100%が目標 |
| レビュー効率 | 発見欠陥数 / レビュー工数(h) | 高いほど効率的 |

### メトリクスの読み方

| 状況 | 解釈 | アクション |
|------|------|-----------|
| 指摘密度が高い（誤字脱字レベル） | 事前チェック不足 | セルフレビューの強化 |
| 指摘密度が高い（技術的指摘） | 設計者のスキル不足 or 難易度が高い | ペアプログラミング、トレーニング |
| 指摘密度が低すぎる | レビューが甘い可能性 | レビュアーの追加、観点の見直し |
| 修正率が低い | 指摘の対応漏れ | 追跡管理の仕組みを導入 |

### チェックリスト管理

| ポイント | 説明 |
|---------|------|
| 項目数の上限 | 20項目程度。A4用紙1枚に収まる量 |
| 定期的な更新 | 過去の指摘傾向を反映して更新 |
| カスタマイズ | プロジェクト特性に合わせて観点を調整 |
| 形骸化防止 | チェックリストを読み上げるだけのレビューを避ける |

## レビュー改善サイクル

```
1. レビュー実施
      ↓
2. メトリクス収集（指摘件数、種類、重要度）
      ↓
3. 傾向分析（どの観点の指摘が多いか）
      ↓
4. 根本原因の特定（なぜその指摘が多いか）
      ↓
5. プロセス改善（チェックリスト更新、トレーニング実施）
      ↓
6. 次回レビューで効果確認
      ↓
1. に戻る
```

## AIを活用したレビューの効率化

### 本プロジェクトでのアプローチ

| フェーズ | AI活用 | 人間の役割 |
|---------|--------|-----------|
| セルフレビュー | プロンプトに従い機械的チェック | プロンプトの改善、結果の判断 |
| 差分チェック | ドキュメント間の自動突合 | 業務観点の妥当性判断 |
| 横断整合性 | 全ドキュメントの横断的矛盾検出 | ビジネスロジックの正しさ判断 |

### AIレビューの限界

| AIが得意なこと | AIが苦手なこと |
|--------------|---------------|
| 形式的な整合性チェック | ビジネス要件の妥当性判断 |
| 網羅的な組み合わせ列挙 | 暗黙の前提条件の発見 |
| 一貫性の検証 | ユーザー体験の評価 |
| パターンに基づく指摘 | 創造的な設計改善提案 |

## レビュー時のチェックポイント

- [ ] レビュー計画（対象、観点、レビュアー、方式）が策定されているか
- [ ] チェックリストが20項目以内に絞られているか
- [ ] 指摘の重要度とタイプが分類されているか
- [ ] メトリクス（指摘密度、修正率等）が計測されているか
- [ ] 過去のレビュー指摘がチェックリストに反映されているか
- [ ] レビュー完了基準が明確か
