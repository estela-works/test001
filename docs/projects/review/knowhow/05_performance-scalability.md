# 05. パフォーマンス・スケーラビリティ

非機能要件としてのパフォーマンスとスケーラビリティを設計段階でレビューするためのノウハウ。

## なぜ重要か

- 稼働後にパフォーマンス問題が発覚すると、アーキテクチャの根本的な見直しが必要になる
- データ量やユーザー数の増加を見越した設計がないと、運用開始後に性能劣化が発生する
- 非機能要件は後付けが困難なため、設計段階で確実に盛り込む必要がある

## 非機能要件の定量化

### 基本指標

| 指標 | 定義 | 設計時に決めるべきこと |
|------|------|---------------------|
| レスポンスタイム | リクエストからレスポンスまでの時間 | 目標値（例: 画面表示1秒以内） |
| スループット | 単位時間あたりの処理件数 | ピーク時の目標TPS（例: 100 TPS） |
| 同時接続数 | 同時にシステムを利用するユーザー数 | ピーク時の最大同時接続数 |
| データ量 | 蓄積されるデータの総量 | 初期データ量、年間増加率、保持期間 |
| 可用性 | システムが利用可能な時間の割合 | SLA（例: 99.9%） |
| RPO/RTO | 許容データ損失量/復旧目標時間 | 災害時のリカバリ目標 |

### 非機能要件の記述例

```
性能要件:
- 画面レスポンス: 平均1秒以内、最大3秒以内（95パーセンタイル）
- 同時利用者数: 通常500人、ピーク1,000人
- バッチ処理: 日次集計を1時間以内に完了
- データ量: 初年度100万件、年間50万件増加、5年間保持
```

## スケーラビリティ設計の観点

### 水平スケーリング vs 垂直スケーリング

| 方式 | 特徴 | 設計時の考慮 |
|------|------|------------|
| 水平（スケールアウト） | サーバー台数を増やす | ステートレス設計、セッション外部化、データ分散 |
| 垂直（スケールアップ） | サーバースペックを上げる | 上限がある。暫定対応として使う |

### スケーラビリティ設計チェック

- [ ] アプリケーションがステートレスに設計されているか
- [ ] セッション情報が外部ストア（Redis等）に保存されているか
- [ ] DBコネクションプールのサイズが設計されているか
- [ ] オートスケーリングの条件（CPU、メモリ、キュー長等）が定義されているか
- [ ] データベースのシャーディングやレプリケーション方針があるか

## パフォーマンス設計のチェック観点

### データベース

| チェック項目 | 内容 |
|------------|------|
| インデックス設計 | 主要なクエリに対するインデックスが定義されているか |
| N+1問題 | リスト取得時にN+1クエリが発生しない設計か |
| クエリ最適化 | 大量データ取得時にページングが設計されているか |
| コネクションプール | プールサイズと待ち時間が定義されているか |
| スロークエリ対策 | スロークエリの検知・アラートが設計されているか |

### キャッシュ戦略

| 種類 | 適用場面 | 注意点 |
|------|---------|--------|
| ブラウザキャッシュ | 静的リソース（CSS、JS、画像） | Cache-Controlヘッダーの設計 |
| CDNキャッシュ | 地理的に分散するユーザーへの配信 | キャッシュ無効化（パージ）の設計 |
| アプリケーションキャッシュ | マスタデータ、計算結果 | TTL設定、キャッシュ更新タイミング |
| DBキャッシュ | 頻繁に参照されるクエリ結果 | キャッシュとDBの整合性保証 |

### 非同期処理

| チェック項目 | 内容 |
|------------|------|
| 非同期化の判断 | レスポンスタイムに影響する重い処理は非同期化されているか |
| メッセージキュー | キューの選定（RabbitMQ、SQS等）と設計 |
| リトライ | 失敗時のリトライ回数と間隔（指数バックオフ） |
| デッドレターキュー | 処理不能メッセージの退避先が設計されているか |

## 性能テストの種類

設計段階で、どの性能テストを実施するか計画する。

| テスト種類 | 目的 | 確認すること |
|-----------|------|------------|
| 負荷テスト | 想定負荷での動作確認 | 目標レスポンスタイム内に収まるか |
| ストレステスト | 限界性能の確認 | システムがどこまで耐えられるか |
| スパイクテスト | 急激な負荷増加への対応 | オートスケーリングが正常に動作するか |
| 耐久テスト | 長時間稼働での安定性 | メモリリーク等の問題がないか |
| スケーラビリティテスト | スケールアウト時の性能向上 | 台数増加に比例して性能が向上するか |

## レビュー時のチェックポイント

- [ ] 性能目標値が定量的に定義されているか（曖昧な「高速」等でないか）
- [ ] ピーク時の同時接続数・データ量が想定されているか
- [ ] データ量の年間増加率と保持期間が定義されているか
- [ ] キャッシュ戦略が設計されているか
- [ ] N+1クエリや大量データ取得のパフォーマンスリスクが検討されているか
- [ ] 非同期処理の対象と方式が定義されているか
- [ ] 性能テストの種類と実施計画があるか
