# 06. エラーハンドリング・異常系設計

異常系の設計品質をレビューするためのノウハウ。正常系だけでなく「何が失敗し得るか」を網羅的に設計する。

## なぜ重要か

- 本番障害の多くは異常系の考慮不足が原因
- エラーハンドリングの設計が不十分だと、障害の原因特定に時間がかかる
- ユーザーに適切なフィードバックを返せず、UXが大きく損なわれる

## エラーの3分類

設計時にエラーを3つに分類して整理する。

| 分類 | 定義 | 例 | 設計上の対応 |
|------|------|-----|------------|
| 正常系 | 期待どおりの動作 | 入力→処理→出力 | 主要なフロー設計 |
| 異常系 | 想定内のエラー（業務エラー） | バリデーション違反、在庫不足 | エラーメッセージ表示、リカバリー手順 |
| 例外系 | 想定外のエラー（システムエラー） | DB接続断、メモリ不足 | ログ出力、アラート、フォールバック |

## 異常系設計の原則

### 1. フェイルファスト（早期検出）

```
入力検証 → ビジネスルール検証 → 処理実行 → 結果返却
  ↓ NG          ↓ NG              ↓ NG
  即座に        即座に            ロールバック
  エラー返却    エラー返却        ＋エラー返却
```

- 問題は可能な限り早い段階で検出する
- 不正な状態のまま処理を続行しない

### 2. エラーの伝播設計

| レイヤー | 責務 |
|---------|------|
| プレゼンテーション | ユーザー向けメッセージの表示、リトライ導線 |
| ビジネスロジック | 業務ルール違反の検出、業務エラーの生成 |
| データアクセス | DB例外のラップ、トランザクション制御 |
| インフラ | 接続タイムアウト、リトライ、サーキットブレーカー |

### 3. トランザクション設計

| パターン | 説明 | 適用場面 |
|---------|------|---------|
| 全体ロールバック | 1件でもエラーなら全体取消 | 整合性が最重要な処理 |
| 部分コミット | 正常分のみコミット、異常分はスキップ | バッチ処理で1件の失敗が全体に影響しない場合 |
| 補償トランザクション | 後から取消操作を実行 | 分散トランザクション（Saga パターン） |

## エラーメッセージ設計

### メッセージの4要素

| 要素 | 説明 | 良い例 | 悪い例 |
|------|------|--------|--------|
| 何が起きたか | エラーの概要 | 「メールアドレスの形式が不正です」 | 「エラーが発生しました」 |
| なぜ起きたか | 原因 | 「@の後にドメインが必要です」 | 「入力値が不正です」 |
| どうすればよいか | 回復手順 | 「正しい形式で入力してください」 | （なし） |
| エラーコード | 問い合わせ用識別子 | 「ERR-V-001」 | （なし） |

### エラーコード体系の設計

```
ERR-{カテゴリ}-{連番}

カテゴリ:
  V: バリデーションエラー
  B: ビジネスロジックエラー
  A: 認証・認可エラー
  S: システムエラー
  E: 外部連携エラー
```

## 異常系パターン集

### バリデーション

| 観点 | チェック項目 |
|------|------------|
| 必須チェック | 必須項目が未入力の場合 |
| 型チェック | 数値項目に文字が入力された場合 |
| 範囲チェック | 最大値・最小値を超えた場合 |
| 形式チェック | メールアドレス、電話番号等のフォーマット違反 |
| 相関チェック | 開始日 > 終了日のような項目間の矛盾 |
| サイズチェック | 文字数上限、ファイルサイズ上限の超過 |

### 業務ロジック

| 観点 | チェック項目 |
|------|------------|
| 状態遷移 | 許可されない状態遷移（例: 完了→下書き） |
| 排他制御 | 同時更新の競合（楽観ロック・悲観ロック） |
| 権限 | 操作権限のないユーザーによるアクセス |
| 上限 | 登録件数上限、利用回数上限の超過 |
| 依存 | 削除しようとしたデータが他から参照されている |

### システム・インフラ

| 観点 | チェック項目 |
|------|------------|
| 接続障害 | DB、外部API、キャッシュへの接続失敗 |
| タイムアウト | 処理時間超過 |
| ディスク | ストレージ容量不足 |
| メモリ | メモリ不足（OutOfMemory） |
| ネットワーク | DNS解決失敗、証明書期限切れ |

## レジリエンス設計パターン

| パターン | 説明 | 適用場面 |
|---------|------|---------|
| リトライ | 一時的障害を自動回復 | ネットワーク瞬断、DBデッドロック |
| サーキットブレーカー | 障害の連鎖を遮断 | 外部APIの長時間ダウン |
| フォールバック | 代替手段で処理継続 | キャッシュからの応答 |
| バルクヘッド | 障害の影響範囲を限定 | スレッドプール・コネクションプールの分離 |
| タイムアウト | 無限待ちを防止 | 外部連携の応答遅延 |

## レビュー時のチェックポイント

- [ ] すべてのAPIエンドポイントにエラーレスポンスが定義されているか
- [ ] エラーの3分類（異常系・例外系）が整理されているか
- [ ] エラーメッセージがユーザーに理解可能な形式か（技術用語を含まないか）
- [ ] エラーコード体系が定義されているか
- [ ] トランザクションのロールバック方針が設計されているか
- [ ] 外部連携のタイムアウト・リトライが設計されているか
- [ ] 同時更新時の排他制御（楽観ロック/悲観ロック）が定義されているか
- [ ] エラー発生時のログ出力項目が定義されているか
- [ ] 0除算、マイナス値、オーバーフローが考慮されているか
