# Phase 2A｜テンプレート充足性・要件トレーサビリティチェック

## 問い

> テンプレートの全項目が充足され、機能-要件の対応・エンティティ-APIのマッピングが取れているか？

## 参照ノウハウ

- [01_requirements-traceability.md](../../knowhow/01_requirements-traceability.md) — 要件トレーサビリティ
- [04_security-design.md](../../knowhow/04_security-design.md) — セキュリティ設計
- [05_performance-scalability.md](../../knowhow/05_performance-scalability.md) — パフォーマンス・スケーラビリティ

## チェック対象

- テンプレート（basic-design-backend-template.md）の全セクションが漏れなく充填されているか
- 要件整理書（requirements.md）の全要件（機能要件・非機能要件）が設計書にマッピングされているか
- エンティティ定義と、それを操作するAPIの対応関係が明示されているか
- 全要件にユニークなIDが付与され、双方向に追跡可能か

## 典型的ミス

- 要件整理書に記載された割引ルール組み合わせ処理が、機能一覧に含まれていない
- エンティティとして「キャンペーン」を定義しているが、それを取得・更新するAPIが存在しない
- 税計算（税込/税抜）に関する要件が非機能要件セクションに反映されていない
- セキュリティ要件（認証・認可・入力検証）が非機能要件に含まれていない
- 性能要件（応答時間・同時接続数）が定量的に定義されていない
- 要件IDが一部のユーザーストーリーに付与されておらず追跡不能

## 実行手順

### Step 1｜テンプレート充填チェック

テンプレートの全セクション・全テーブルについて、充填状態を確認する。

```
| # | セクション | サブセクション | 充填状態 | 備考 |
|---|-----------|-------------|---------|------|
| 1 | 1. 概要 | 1.1 本設計書の目的 | 済/未 | ... |
| 2 | 1. 概要 | 1.2 バックエンドの役割 | 済/未 | ... |
| 3 | 2. 機能要件 | 2.1 機能一覧 | 済/未 | ... |
| 4 | 3. データ要件 | 3.1 データ構造 | 済/未 | ... |
| 5 | 3. データ要件 | 3.2 エンティティ | 済/未 | ... |
| 6 | 4. API要件 | 4.1 エンドポイント一覧 | 済/未 | ... |
| 7 | 4. API要件 | 4.2 レスポンス形式 | 済/未 | ... |
| 8 | 4. API要件 | 4.3 エラーレスポンス | 済/未 | ... |
| 9 | 5. 非機能要件 | 5.1 性能要件 | 済/未 | ... |
| 10 | 5. 非機能要件 | 5.2 セキュリティ要件 | 済/未 | ... |
| 11 | 6. 制約条件 | - | 済/未 | ... |
```

### Step 2｜要件-機能トレーサビリティマトリクス

要件整理書の全要件（ユーザーストーリー）と、設計書の機能一覧の対応を突合する。

```
| # | 要件ID | 要件概要 | 対応機能ID | 機能名 | 対応状況 |
|---|--------|---------|-----------|--------|---------|
| 1 | US-001 | ... | F-001 | ... | OK/漏れ |
| 2 | US-002 | ... | F-002, F-003 | ... | OK/漏れ |
| 3 | US-003 | ... | （なし） | - | 漏れ |
```

プラン見積アプリ固有の確認ポイント:
- 料金プラン一覧取得の要件が機能化されているか
- 割引ルール組み合わせ計算の要件が機能化されているか
- キャンペーン期間管理の要件が機能化されているか
- 家族割グループ依存関係の要件が機能化されているか
- 税計算（税込/税抜変換）の要件が機能化されているか

### Step 3｜エンティティ-APIマッピング表

定義された全エンティティについて、それを操作するAPIエンドポイントが存在するか確認する。

```
| # | エンティティ | CRUD | 対応API（メソッド + パス） | 対応状況 |
|---|------------|------|-------------------------|---------|
| 1 | Plan | R | GET /api/plans | OK |
| 2 | Plan | R | GET /api/plans/{id} | OK |
| 3 | Discount | R | GET /api/discounts | OK |
| 4 | Estimate | C | POST /api/estimates | OK |
| 5 | Campaign | R | （なし） | 漏れ |
```

### Step 4｜非機能要件トレーサビリティチェック

要件整理書の非機能要件（セキュリティ・性能・可用性）が、設計書の非機能要件セクションに漏れなくマッピングされているか確認する。

```
| # | 非機能要件カテゴリ | 要件書の記載 | 設計書の該当箇所 | 定量的定義 | 対応状況 |
|---|------------------|------------|---------------|-----------|---------|
| 1 | 性能（応答時間） | ... | 5.1 性能要件 | ○/× | OK/漏れ |
| 2 | 性能（同時接続数） | ... | 5.1 性能要件 | ○/× | OK/漏れ |
| 3 | セキュリティ（認証） | ... | 5.2 セキュリティ要件 | - | OK/漏れ |
| 4 | セキュリティ（認可） | ... | 5.2 セキュリティ要件 | - | OK/漏れ |
| 5 | セキュリティ（入力検証） | ... | 5.2 セキュリティ要件 | - | OK/漏れ |
| 6 | データ保持（RPO/RTO） | ... | 5. 非機能要件 | ○/× | OK/漏れ |
```

確認ポイント:
- 性能要件が定量的に記述されているか（「高速」ではなく「1秒以内」等）
- セキュリティ要件がOWASP Top 10の主要項目をカバーしているか
- 可用性・データ保持に関する要件が明記されているか

## 判定基準

- テンプレートの全セクションが充填済みであること
- 要件-機能マトリクスで未対応の要件がないこと
- 全エンティティに対して必要なCRUD操作のAPIが定義されていること
- 非機能要件（セキュリティ・性能）が漏れなくマッピングされ、定量的に定義されていること
- 上記すべてを満たせばPass。1つでも漏れがあれば設計書を修正してから次のPhaseへ進む
