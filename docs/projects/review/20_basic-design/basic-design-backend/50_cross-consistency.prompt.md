# Phase 4｜横断的整合性チェック

## 問い

> 設計書内の複数セクションが相互に矛盾していないか？

## 参照ノウハウ

- [02_design-consistency.md](../../knowhow/02_design-consistency.md) — 設計の一貫性・整合性
- [09_maintainability-readability.md](../../knowhow/09_maintainability-readability.md) — 保守性・可読性・命名規則

## 位置づけ

設計書全体を俯瞰し、セクション間の記述の矛盾・食い違いを検出する最終関門。
Phase 2A〜2Cで内部品質を、Phase 3で外部との差分を確認した上で、最後に設計書全体の一貫性を検証する。

## 実行手順

### Step 1｜全セクションの主張抽出

設計書の各セクションから、他セクションに影響する「主張」（エンティティ定義、API仕様、機能定義、非機能要件、制約条件等）を抽出する。

```
| # | セクション | 主張 | 関連セクション |
|---|-----------|------|--------------|
| 1 | 2. 機能要件 | 見積計算機能はプラン+割引+税の3段階で計算する | 4. API要件、3. データ要件 |
| 2 | 3. データ要件 | Discountエンティティにmax_combinable属性がある | 4. API要件 |
| 3 | 4. API要件 | POST /api/estimates は割引IDの配列を受け取る | 3. データ要件 |
| 4 | 5. 非機能要件 | API応答時間は1秒以内 | 4. API要件、6. 制約条件 |
```

### Step 2｜セクション間の突合

関連するセクション同士の主張を突き合わせ、矛盾がないか確認する。

```
| # | セクションA | 主張A | セクションB | 主張B | 矛盾 | 内容 |
|---|-----------|-------|-----------|-------|------|------|
| 1 | 機能要件 | 割引は最大3つ併用可 | API要件 | discountIds配列に上限なし | あり | 上限の不一致 |
| 2 | データ要件 | Campaign.endDateはLocalDate | API要件 | endDateをISO8601文字列で返却 | なし | 型変換で対応可 |
| 3 | 非機能要件 | 応答1秒以内 | 制約条件 | H2インメモリDB | なし | インメモリなら十分 |
```

### Step 3｜用語・命名の一貫性

設計書全体で同じ概念に異なる名称が使われていないか確認する。

```
| # | 概念 | セクションAでの名称 | セクションBでの名称 | 統一案 |
|---|------|-------------------|-------------------|--------|
| 1 | 料金プラン | プラン / 料金プラン | Plan / plan | 「料金プラン」に統一 |
| 2 | 割引 | 割引 / ディスカウント | discount / 値引き | 「割引」に統一 |
| 3 | 見積 | 見積 / 見積もり / 試算 | estimate | 「見積」に統一 |
```

命名規則の横断チェック:
```
| # | 命名対象 | 期待規則 | 違反箇所 | 備考 |
|---|---------|---------|---------|------|
| 1 | Javaクラス名 | PascalCase | ... | 型サフィックス: Request, Response, Entity |
| 2 | APIパス | kebab-case複数形名詞 | ... | 動詞パスがないか |
| 3 | DBテーブル/カラム | snake_case | ... | camelCaseが混在していないか |
| 4 | JSONフィールド | プロジェクト統一規則 | ... | snake_case or camelCase |
```

### Step 4｜セキュリティ要件の横断整合チェック

セキュリティに関する記述がセクション間で矛盾していないか確認する。

```
| # | セキュリティ観点 | 非機能要件での記述 | API要件での記述 | データ要件での記述 | 整合性 |
|---|----------------|----------------|--------------|----------------|--------|
| 1 | 認証方式 | ... | ... | - | OK/矛盾 |
| 2 | 認可（ロール） | ... | ... | - | OK/矛盾 |
| 3 | 入力検証 | ... | ... | ... | OK/矛盾 |
| 4 | 機密データ | ... | - | ... | OK/矛盾 |
```

### Step 5｜下流設計書への引き継ぎ確認

基本設計書の各セクションが、下流の詳細設計書に必要十分な情報を提供しているか確認する。

```
| # | 下流設計書 | 必要な情報 | 基本設計書での記述 | 充足 | 備考 |
|---|-----------|-----------|----------------|------|------|
| 1 | detail-design-api.md | エンドポイント定義 | 4.1 エンドポイント一覧 | OK/不足 | ... |
| 2 | detail-design-logic.md | ビジネスルール | 2.1 機能一覧 | OK/不足 | 割引組み合わせ詳細 |
| 3 | detail-design-logic.md | エラーハンドリング方針 | 5. 非機能要件 | OK/不足 | 例外処理の集約方針 |
| 4 | detail-design-sql.md | テーブル構造 | 3.2 エンティティ | OK/不足 | ... |
| 5 | detail-design-db.md | データ関連 | 3.1 データ構造 | OK/不足 | ... |
| 6 | detail-design-api.md | セキュリティ要件 | 5.2 セキュリティ要件 | OK/不足 | 認証・認可・入力検証 |
```

### Step 6｜最終サマリ

Phase 2A〜Phase 4の全結果を集約し、残課題を一覧化する。

```
| Phase | 結果 | 残課題数 | 主な課題 |
|-------|------|---------|---------|
| 2A テンプレート充足性 | Pass/Fail | 0 | - |
| 2B 内部整合性 | Pass/Fail | 0 | - |
| 2C 技術的実現可能性 | Pass/Fail | 0 | - |
| 3 差分チェック | Pass/Fail | 0 | - |
| 4 横断整合性 | Pass/Fail | 0 | - |
```

## 判定基準

- 全セクション間で矛盾がなく、用語が統一されていること
- 下流設計書への引き継ぎ情報が充足していること
- 全Phaseの結果がPassであること
- 上記すべてを満たせば人間レビューへ提出可能。矛盾・不統一がある場合は修正してから提出
