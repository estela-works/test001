# Phase 2C｜技術的実現可能性チェック

## 問い

> アーキテクチャ制約の下で、技術的に実現可能な設計になっているか？

## 参照ノウハウ

- [03_interface-design.md](../../knowhow/03_interface-design.md) — インターフェース設計
- [04_security-design.md](../../knowhow/04_security-design.md) — セキュリティ設計
- [05_performance-scalability.md](../../knowhow/05_performance-scalability.md) — パフォーマンス・スケーラビリティ
- [06_error-handling.md](../../knowhow/06_error-handling.md) — エラーハンドリング・異常系

## チェック対象

- 設計書のアーキテクチャ方針が制約条件と矛盾していないか
- DB設計（エンティティ定義）がリレーショナルDBとして成立するか
- API設計がRESTの一般的なパターンに沿っているか
- プラン見積特有のドメイン複雑性（割引組み合わせ、税計算等）が適切に考慮されているか
- セキュリティ設計が基本的な脅威に対処しているか
- エラーハンドリングの方針がレイヤーごとに定義されているか

## 典型的ミス

- H2（インメモリDB）の制約を考慮せず、大量データ前提の設計をしてしまう
- 割引ルールの組み合わせ爆発を考慮せず、単純なCRUD設計にしてしまう
- キャンペーン期間の判定ロジックをAPI層に持たせ、ビジネスロジック層が空になる

## アンチパターン

| ID | アンチパターン | 説明 |
|----|-------------|------|
| AP-1 | 計算ロジックのAPI層漏出 | 料金計算・割引適用をControllerに書く設計。Serviceレイヤーに集約すべき |
| AP-2 | エンティティ間の循環依存 | Plan -> Discount -> Plan のような循環参照を設計してしまう |
| AP-3 | キャンペーン期間のハードコード | 期間をDBで管理せずコード内に埋め込む設計 |
| AP-4 | 家族割の無限再帰 | 家族グループの割引計算で、メンバー相互参照による無限ループが発生する設計 |
| AP-5 | セキュリティの後回し | 「後で対応」としてセキュリティ設計を省略。基本設計段階で認証・認可・入力検証の方針を決めるべき |
| AP-6 | エラーハンドリングの場当たり対応 | レイヤーごとの例外処理方針が未定義で、catch漏れや握りつぶしが発生する |
| AP-7 | 入力検証のフロントエンド依存 | フロントエンドの検証のみに頼り、バックエンドでの検証を設計しない |

## 実行手順

### Step 1｜アーキテクチャ制約との整合チェック

制約条件セクションの各制約に対して、設計内容が矛盾していないか確認する。

```
| # | 制約項目 | 制約内容 | 関連する設計内容 | 矛盾 | 備考 |
|---|---------|---------|----------------|------|------|
| 1 | データ保存 | H2インメモリDB | エンティティ設計 | なし/あり | ... |
| 2 | スレッドセーフティ | ConcurrentHashMap | 同時見積計算 | なし/あり | ... |
| 3 | フレームワーク | Spring Boot | レイヤー構成 | なし/あり | ... |
```

### Step 2｜DB設計実現可能性チェック

エンティティ定義がRDBのテーブル設計として成立するか検証する。

```
| # | エンティティ | 主キー定義 | 外部キー関係 | 正規化状態 | 問題点 |
|---|------------|-----------|------------|-----------|--------|
| 1 | Plan | id (自動採番) | なし | OK | - |
| 2 | Discount | id (自動採番) | plan_id -> Plan | OK | - |
| 3 | Estimate | id (自動採番) | plan_id, discount_ids | 要確認 | 多対多の扱い |
| 4 | Campaign | id (自動採番) | なし | OK | 期間カラムの型確認 |
| 5 | FamilyGroup | id (自動採番) | member_ids | 要確認 | 自己参照の設計 |
```

### Step 3｜API設計パターンチェック

各APIエンドポイントがRESTの標準パターンに沿っているか確認する。

REST API設計の基準:
- **パス設計**: リソース指向（名詞・複数形）、kebab-case、動詞を含めない
- **HTTPメソッド**: GET（取得）/ POST（作成）/ PUT（全置換）/ PATCH（部分更新）/ DELETE（削除）
- **べき等性**: GET, PUT, DELETE はべき等。POST は非べき等
- **レスポンスサイズ**: 1オブジェクトのプロパティは20個以下、ネスト3階層以下を推奨
- **日時フォーマット**: ISO 8601形式（例: `2026-03-05T10:00:00+09:00`）
- **配列レスポンス**: オブジェクトでラップする（`{"items": [...], "total": 10}`）

```
| # | エンドポイント | メソッド | パス設計 | べき等性 | レスポンス設計 | RESTパターン準拠 | 問題点 |
|---|-------------|---------|---------|---------|-------------|----------------|--------|
| 1 | プラン一覧取得 | GET | /api/plans | べき等 | 配列ラップ | OK | - |
| 2 | 見積計算 | POST | /api/estimates | 非べき等 | 単一オブジェクト | OK | - |
| 3 | 割引適用確認 | GET | /api/check-discount | べき等 | - | NG | 動詞パスを避ける |
```

### Step 4｜ドメイン複雑性の設計対応チェック

プラン見積特有の複雑なビジネスロジックに対して、設計が適切に対処しているか確認する。

```
| # | ドメイン複雑性 | 設計書での対処 | レイヤー配置 | 妥当性 | 備考 |
|---|--------------|-------------|------------|--------|------|
| 1 | 料金プラン計算 | 計算APIの定義 | Service層 | OK/NG | ... |
| 2 | 割引ルール組み合わせ | 排他/併用の定義 | Service層 | OK/NG | 組み合わせ爆発への対処 |
| 3 | キャンペーン期間判定 | 期間エンティティ | Service層 | OK/NG | 開始日・終了日の型 |
| 4 | 税込/税抜変換 | 変換ロジック | Service/Util層 | OK/NG | 丸め処理の定義 |
| 5 | 家族割グループ依存 | グループエンティティ | Service層 | OK/NG | メンバー数依存の計算 |
```

### Step 5｜セキュリティ設計チェック

設計書のセキュリティ関連の記述が、基本的な脅威に対処しているか確認する。

OWASP Top 10 2025の主要項目を基準とする:
- **A01 アクセス制御の不備**: 全エンドポイントに認可チェックが定義されているか
- **A04 認証の不備**: 認証方式（セッション/JWT等）が明記されているか
- **A07 インジェクション**: 入力検証の方針がレイヤーごとに定義されているか

```
| # | セキュリティ観点 | 設計書の記述 | 対処状況 | 備考 |
|---|----------------|------------|---------|------|
| 1 | 認証方式 | ... | 定義済/未定義 | セッション? JWT? |
| 2 | 認可（エンドポイント別） | ... | 定義済/未定義 | ロール定義は? |
| 3 | 入力検証（バックエンド） | ... | 定義済/未定義 | 各APIの必須/型/範囲チェック |
| 4 | 入力検証（DB制約） | ... | 定義済/未定義 | NOT NULL, UNIQUE, CHECK等 |
| 5 | 機密データの扱い | ... | 定義済/未定義 | ログ出力抑制、暗号化 |
| 6 | セキュリティヘッダー | ... | 定義済/未定義 | CSP, HSTS, X-Frame-Options |
```

### Step 6｜エラーハンドリング設計チェック

エラーハンドリングの方針がレイヤーごとに定義され、異常系に対処できる設計になっているか確認する。

エラー分類の基準:
- **正常系**: 想定通りの処理フロー
- **異常系（業務エラー）**: 想定内のビジネスルール違反（バリデーション、状態不整合等）
- **例外系（システムエラー）**: 想定外の障害（DB接続失敗、タイムアウト等）

```
| # | エラー分類 | 代表例 | レイヤー | 処理方針 | 定義状況 |
|---|-----------|--------|---------|---------|---------|
| 1 | バリデーション | 必須項目未入力 | Controller | 400レスポンス | 定義済/未定義 |
| 2 | ビジネスルール違反 | 排他割引の同時適用 | Service | 422レスポンス | 定義済/未定義 |
| 3 | リソース未存在 | 存在しないプランID | Service | 404レスポンス | 定義済/未定義 |
| 4 | 認証エラー | 未認証アクセス | Filter/Interceptor | 401レスポンス | 定義済/未定義 |
| 5 | システムエラー | DB接続失敗 | Global Handler | 500レスポンス | 定義済/未定義 |
| 6 | 外部連携エラー | 外部API障害 | Service | リトライ/フォールバック | 定義済/未定義 |
```

確認ポイント:
- 例外処理の集約方針（`@ControllerAdvice`等）が定義されているか
- エラー時のトランザクション方針（ロールバック/補償トランザクション）が定義されているか
- システムエラー時にスタックトレースがレスポンスに露出しない設計か

## 判定基準

- アーキテクチャ制約との矛盾がないこと
- 全エンティティがRDBテーブルとして設計可能であること
- APIが標準的なRESTパターンに沿っていること
- ドメイン固有の複雑性に対する設計方針が明示されていること
- セキュリティ設計の基本方針（認証・認可・入力検証）が定義されていること
- エラーハンドリングの方針がレイヤーごとに定義されていること
- 上記すべてを満たせばPass。問題がある場合は設計書を修正してから次のPhaseへ進む
