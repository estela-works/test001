# Phase 4｜横断的整合性チェック

## 問い

> 設計書内の複数セクションが相互に矛盾していないか？

## 参照ノウハウ

- [02_design-consistency.md](../../knowhow/02_design-consistency.md) — 設計の一貫性・整合性
- [09_maintainability-readability.md](../../knowhow/09_maintainability-readability.md) — 保守性・可読性・命名規則

## 位置づけ

設計書全体を俯瞰し、セクション間の記述の矛盾・食い違いを検出する最終関門。
Phase 2A〜2Dで内部品質を、Phase 3で外部との差分を確認した上で、最後に設計書全体の一貫性を検証する。

## 実行手順

### Step 1｜全セクションの主張抽出

設計書の各セクションから、他セクションに影響する「主張」（状態定義、データフロー、条件分岐、コンポーネント構成等）を抽出する。

```
| # | セクション | 主張 | 関連セクション |
|---|-----------|------|--------------|
| 1 | ...       | ...  | ...          |
```

### Step 2｜セクション間の突合

関連するセクション同士の主張を突き合わせ、矛盾がないか確認する。

```
| # | セクションA | 主張A | セクションB | 主張B | 矛盾 | 内容 |
|---|-----------|-------|-----------|-------|------|------|
| 1 | ...       | ...   | ...       | ...   | あり/なし | ... |
```

### Step 3｜用語・命名の一貫性

設計書全体で同じ概念に異なる名称が使われていないか確認する。

```
| # | 概念 | セクションAでの名称 | セクションBでの名称 | 統一案 |
|---|------|-------------------|-------------------|--------|
| 1 | ...  | ...               | ...               | ...    |
```

命名規則の横断チェック:
```
| # | 命名対象 | 期待規則 | 違反箇所 | 備考 |
|---|---------|---------|---------|------|
| 1 | コンポーネント名 | PascalCase | ... | 例: PlanSelector, EstimateResult |
| 2 | Props型名 | PascalCase + Props | ... | 例: PlanSelectorProps |
| 3 | 状態変数名 | camelCase | ... | 例: selectedPlan, isLoading |
| 4 | イベントハンドラ名 | handle + 動詞 | ... | 例: handleSubmit, handleCancel |
| 5 | カスタムフック名 | use + 名詞/動詞 | ... | 例: usePlanList, useEstimate |
| 6 | 定数名 | UPPER_SNAKE_CASE | ... | 例: MAX_DISCOUNT_COUNT |
```

確認ポイント:
- コンポーネント名・Props型・状態変数・イベントハンドラの命名規則が統一されているか
- バックエンド設計書との間で同じ概念に異なる名称が使われていないか
- 表示ラベル（日本語）とコード上の名称の対応が明確か

## 判定基準

- 全セクション間で矛盾がなく、用語が統一されていればPass
- 命名規則がフロントエンド全体で統一されていること
- 矛盾または不統一がある場合は修正してから人間レビューへ提出
