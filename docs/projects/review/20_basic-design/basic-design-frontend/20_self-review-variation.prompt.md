# Phase 2B｜バリエーション差異の保全チェック

## 問い

> 通常版/プラス版などのサービス差異が、統合ロジックで消えていないか？

## チェック対象

通常版・プラス版ごとの条件が、単一Getterに統合した際に失われていないか。

## 典型的ミス

プラス版では「smart補償必須」なのに、共通Getter統合後に「不要」になってしまう。

## 実行手順

### Step 1｜バリエーション差異の列挙

設計書から、バリエーション（通常版/プラス版、プランA/B等）ごとに異なる条件・振る舞いを全て抽出する。

```
| # | バリエーション | 条件・振る舞い | 設計書の該当箇所 |
|---|---------------|---------------|----------------|
| 1 | ...           | ...           | ...            |
```

### Step 2｜全バリエーション x 全条件の組み合わせ検証表

条件2つなら最低4パターン、条件3つなら最低8パターンを網羅する。

```
| # | バリエーション | 条件A | 条件B | 期待結果 | 設計書の記述 | 一致 |
|---|---------------|-------|-------|---------|-------------|------|
| 1 | 通常版        | true  | true  | ...     | ...         | OK/NG |
| 2 | 通常版        | true  | false | ...     | ...         | OK/NG |
| 3 | 通常版        | false | true  | ...     | ...         | OK/NG |
| 4 | 通常版        | false | false | ...     | ...         | OK/NG |
| 5 | プラス版      | true  | true  | ...     | ...         | OK/NG |
| ...                                                              |
```

### Step 3｜統合ロジックとの突合

統合Getter/関数が上記の全パターンを正しくカバーしているか確認する。

## 判定基準

- 全組み合わせが網羅され、全行「一致」であればPass
- 条件の組み合わせ漏れ、またはNGがあれば設計書を修正
