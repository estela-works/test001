# Phase 2D｜データフローの型一貫性チェック

## 問い

> DB -> BS -> BFF -> FE の全レイヤーで型が一貫しているか？

## 参照ノウハウ

- [04_security-design.md](../../knowhow/04_security-design.md) — セキュリティ設計

## チェック対象

- 設計書のAPI経路が、アーキテクチャ全層を通じて型的に成立するか
- フロントエンド層での入力バリデーションが設計されているか

## 典型的ミス

DBカラムが VARCHAR(256) でも BFF/FE の型が number のためテキストが流通しない。

## アンチパターン

| ID | アンチパターン | 説明 |
|----|-------------|------|
| AP-1 | DB型だけで判断する | BS〜FEの実コードまで必ず追跡する |
| AP-2 | 「既存パイプラインに自動反映される」と過信する | 各層で明示的に確認する |
| AP-3 | 既存の実装パターンを無視して新しい経路を設計する | 既存同種データのAPI経路と比較する |
| AP-4 | 分析メモの結論をコード裏取りなしで信頼する | 必ず実コードで裏取りする |

## 実行手順

### Step 1｜全データソース指定の抽出

設計書から、外部データ（API取得・DB参照）を使うすべての箇所を抽出する。

```
| # | データ項目 | 用途 | 設計書の該当箇所 |
|---|-----------|------|----------------|
| 1 | ...       | ...  | ...            |
```

### Step 2｜5層の型確認

各データ項目について、DB / BS / BFF / OpenAPI / FE の5層で型を確認する。

```
| # | データ項目 | DB型 | BS型(Java) | BFF型 | OpenAPI型 | FE型(TS) | 一貫性 |
|---|-----------|------|-----------|-------|----------|---------|--------|
| 1 | ...       | VARCHAR(256) | String | string | string | string | OK |
| 2 | ...       | INT  | Integer   | number | integer | number  | OK |
| 3 | ...       | ...  | ...       | ...   | ...      | ...     | NG |
```

### Step 3｜既存同種データのAPI経路との比較

同じ種類のデータを扱う既存APIの経路パターンと比較し、設計の一貫性を確認する。

### Step 4｜フロントエンド入力バリデーション設計チェック

ユーザー入力を受け付ける全フィールドについて、フロントエンド層での入力検証が設計されているか確認する。

注意: フロントエンドのバリデーションはUX向上目的であり、セキュリティ保証はバックエンド側で行う。

```
| # | 入力フィールド | バリデーション種別 | FEでの検証 | BEでの検証（対応確認） | 設計状況 |
|---|-------------|-----------------|-----------|-------------------|---------|
| 1 | ... | 必須チェック | あり/なし | あり | OK/不足 |
| 2 | ... | 型チェック（数値） | あり/なし | あり | OK/不足 |
| 3 | ... | 範囲チェック | あり/なし | あり | OK/不足 |
| 4 | ... | 形式チェック（日付） | あり/なし | あり | OK/不足 |
| 5 | ... | 文字数上限 | あり/なし | あり | OK/不足 |
```

確認ポイント:
- フロントエンドのバリデーションルールがバックエンドと一致しているか（上限値、必須条件等）
- バリデーションエラー時のメッセージがユーザーにとって分かりやすいか
- フロントエンドのバリデーションのみに依存した設計になっていないか

## 判定基準

- 全データ項目で5層の型が一貫していればPass
- ユーザー入力フィールドにフロントエンドバリデーションが設計されていること
- FEとBEのバリデーションルールが一致していること
- 型の不一致、または既存パターンからの逸脱がある場合は設計書を修正
