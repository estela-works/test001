# 既契約連携拡大：インターネット／光データ取得先検討

## 概要

既契約連携拡大に伴い、インターネット／光サービスの以下の情報を画面表示するためのデータ取得先を比較検討した資料。

**表示対象の情報：**

- プランクラス（インターネット種別）
- プラン名
- オプション
- 割引
- 料金関連情報

## 画面イメージ

### 対象画面の構成

「インターネット・電話」タブを持つ画面で、赤枠で囲われたエリアが今回の対象領域。

**上部料金エリア：**

| 項目 | 備考 |
|------|------|
| 初期費用 | - |
| 課末月額 | - |
| プラン月額 | - |
| 割引 | - |
| 割引適用後 | - |
| 合計 | 表示例：4,400円 |

**インターネット種別の選択肢：**

- ご契約しない
- マンション1ギガ
- 戸建1ギガ
- 戸建10ギガ

**プラン欄：**

- プルダウン形式でプラン名を選択
- 表示例：マンション1ギガタイプA（2年定型あり）4,400円

**下部：** オプション・割引の表示領域

---

## 3案の比較

### 比較表

| 項目 | 案① 光サービスマスタを直接参照 | 案② 光サービスマスタを料SIMマスタにコピー | 案③ サビパラ3Mから料SIMマスタにコピー |
|------|------|------|------|
| **工数** | 低 | 中 | 高 |
| **メリット** | 光ドメインで使用中の情報をそのまま利用でき必要な情報が揃っている / マスタのメンテナンスが不要 | 光ドメインで使用中の情報をコピーするため必要な情報が揃っている / 光ドメイン側の変更があってもコピーを利用するため即座に不具合にはならない | 光ドメインの影響を受けない独立性 |
| **デメリット** | 光ドメインのマスタのため、テーブル仕様変更の影響を直接受ける / 知らない間に変更され急に表示できなくなるリスクあり | 料SIMマスタへのデータ整備が必要 / 光ドメイン側の仕様変更時に対応は必要（即不具合にはならない） / 光サービスマスタ更新時の料SIMマスタメンテ方法の検討が必要 | サビパラ3Mからの料SIMマスタデータ整備が必要（単純コピーではないため整備コスト高） / 料金取得方法が未確定で調査から必要 / サビパラ3M更新時の料SIMマスタメンテ方法の検討が必要 |

> **注記：** 案③についてはメリット欄に「他のメリットがパッと出てこなかったのであれば教えていただきたく…」との補足コメントあり。まだ議論・整理途中の段階。

> **工数補足：** 案③が最も高い前提で、案①・②はそれと比較して相対的に設定。

---

## 案①：光サービスマスタを直接参照する

### 方針

光ドメインで持っている光サービスマスタを直接参照し、インターネット／光のプランクラスやプラン名等を取得する。

### データソース

**テーブル：** `m_hkr_service`（光サービスマスタ）

| 列名（日本語） | 列名（英字） | データ型 |
|----------------|-------------|----------|
| サービスコード | service_code | VARCHAR(5) |
| サービスID | service_id | VARCHAR(5) |
| サービス名称 | service_name | VARCHAR(255) |

### データ例

| service_code | service_id | service_name |
|-------------|-----------|--------------|
| AQ001 | D08DY | ドコモ 戸建・タイプA/東 |
| AQ002 | D08DZ | ドコモ 戸建・タイプB/東 |
| AQ003 | D08E0 | ドコモ 戸建・単独タイプ/東 |
| AQ004 | D08E1 | ドコモ マンション・タイプA/東 |
| AQ005 | D08E2 | （不鮮明） |

### データフロー

```
光サービスマスタ (m_hkr_service)
  └─ service_name ──→ 画面のプラン選択プルダウンに直接表示
```

### ポイント

- データは光ドメインのマスタにある
- 料SIM側ではデータを保持しない
- 必要なときに直接参照して画面表示する

---

## 案②：光サービスマスタを料SIMマスタにコピーする

### 方針

光ドメインで持っている光サービスマスタの中身を、料SIMで持っている固定回線プランマスタにコピーし、インターネット／光のプランクラスやプラン名等を取得する。

### コピー元

**テーブル：** `m_hkr_service`（光サービスマスタ）

- service_code
- service_id
- service_name

### コピー先

**テーブル：** `m_fixedline_plan`（固定回線プランマスタ）

| 列名（日本語） | 列名（英字） |
|----------------|-------------|
| 固定回線プランID | fixedline_plan_id |
| 固定回線プラン名 | fixedline_plan_name |
| サービスコード | service_code |
| 固定回線プランタイプ | fixedline_plan_type |
| 固定回線プランクラス | fixedline_plan_class_id |

### コピー先データ例

| fixedline_plan_name | service_code | fixedline_plan_class_id |
|---------------------|-------------|------------------------|
| マンション1ギガタイプA（2年定型あり） | （NULLあり） | 1 |
| マンション1ギガタイプA | （NULLあり） | 1 |
| マンション1ギガタイプB（2年定型あり） | （NULLあり） | 1 |
| マンション1ギガタイプB | （NULLあり） | 1 |
| マンション1ギガ単独タイプ（2年定型あり） | （NULLあり） | 1 |
| マンション1ギガ単独タイプ | （NULLあり） | 1 |

> **設計上のポイント：** service_code列が一部NULLになっており、コピー時にどう紐付けるかが検討課題。

### データフロー

```
光サービスマスタ (m_hkr_service)
  └─ コピー ──→ 固定回線プランマスタ (m_fixedline_plan)
                    └─ fixedline_plan_name ──→ 画面のプラン選択プルダウンに表示
```

### ポイント

- 元データは光側にある
- 表示用・利用用には料SIM側に複製したマスタを使う
- 光側変化の影響をワンクッション緩和できる

---

## 判断軸の整理

| 判断軸 | 案① | 案② | 案③ |
|--------|------|------|------|
| 速さ・簡単さ | 最も強い | 中間 | 最も弱い |
| システム間影響の分離 | 弱い（直接依存） | 中間（コピーで緩和） | 強い（独立） |
| 保守運用のしやすさ | 新規メンテ不要だが他システム変更に弱い | 自システム側に持てるが同期運用が必要 | 独立性は高いが整備負荷が大きい |
| 将来の変更耐性 | 弱い | 中間 | 高いが構築負担が重い |

---

## 所感

- **案①** は最も簡単で早いが、他ドメイン依存のリスクが明確
- **案②** は現実的な折衷案として有力。影響緩和と実現性のバランスが取れている
- **案③** は独立性はあるが、メリット整理が弱く、コストも高いため採用ハードルが高い（議論途中の印象）
