テストレイヤー構成

コンポーネントテスト
@vue/test-utils + Vitest
描画・ユーザーイベント・Props検証
ストアテスト
Pinia + Vitest
状態管理・アクション・ゲッター検証
ユーティリティテスト
Vitest
純粋関数・ヘルパー関数検証

レイヤー別責務

レイヤー テスト対象 モック対象 優先度
ストア 状態管理、アクション、API連携 API呼び出し 高
コンポーネント 描画、イベント、Props ストア、Router 中
ユーティリティ 純粋関数、フォーマッター なし 高

各レイヤーの検証項目

ストアテスト

  • state の初期値
  • 非同期アクション
  • ゲッターの計算結果
  • API失敗時の状態

コンポーネントテスト

  • 要素の存在・テキスト
  • Props による表示変化
  • ユーザー操作の結果
  • イベントの発火

ユーティリティテスト

  • 正常な入力の処理
  • 境界値・エッジケース
  • NULL/undefined処理
  • フォーマット変換

data-testid 規則

テスト用要素特定のための属性命名規則

{component}-{element}
todo-card-title
要素の特定
{action}-button
delete-button
アクションボタン
{element}-{index}
todo-item-0
リストアイテム
<!-- コンポーネント側 -->
<button data-testid="delete-button" @click="handleDelete">

// テスト側
wrapper.find('[data-testid="delete-button"]');

ベストプラクティス

推奨事項

  • ユーザー視点でテストを書く
  • data-testid で要素を特定
  • await / waitFor で非同期待機
  • ファクトリ関数でデータ生成
  • 1テスト1検証の原則

アンチパターン

  • snapshot テストの多用
  • 実装詳細のテスト
  • setTimeout での待機
  • クラス名での要素特定
  • テスト間の依存関係

まとめ

3層構造

コンポーネント・ストア・ユーティリティを明確に分離してテスト

モック活用

API・Router・Storeを適切にモック化して独立性を確保

data-testid

スタイル変更に強い安定したテストを実現

ユーザー視点

実装詳細ではなくユーザー行動をテスト
