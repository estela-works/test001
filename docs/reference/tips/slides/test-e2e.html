テストピラミッドでの位置づけ

E2E（ここ）
フロントエンド / バックエンド
単体テスト
  • ユーザーシナリオの検証
  • 主要フローの動作確認
  • 少数・高価値
  • 実行コストが高い

E2Eテストの目的

統合動作確認

フロントエンド・バックエンド・DBが連携して動作することを確認

ユーザー視点

実際のユーザー操作をシミュレートして検証

リグレッション防止

デプロイ前の最終確認として機能

クリティカルパス保護

主要業務フローが壊れていないことを保証

E2Eテストの範囲

検証すべきこと

  • 主要ユーザーシナリオ
  • 画面遷移フロー
  • CRUD操作の一連の流れ
  • 重要なエラーハンドリング

検証すべきでないこと

  • 個別のビジネスロジック
  • バリデーションの網羅
  • エッジケース
  • 細かいUI表示

→ 単体テスト・統合テストで検証すべき内容はE2Eに含めない

ロケーター戦略（優先順位）

1
getByRole
セマンティックな要素
2
getByLabel
フォーム要素
3
getByText
テキストによる特定
4
getByTestId
上記で特定できない場合
// 推奨: セマンティックなロケーター
page.getByRole('button', { name: '送信' });
page.getByLabel('メールアドレス');

// 代替: data-testid
page.getByTestId('todo-list');

Page Objectモデル

メリット

  • テストコードの可読性向上
  • ページ変更時の修正箇所が一箇所
  • 再利用可能な操作メソッド
  • 保守性の向上
// Page Object
class TodoPage {
  async createTodo(title) {
    await this.newButton.click();
    await this.titleInput.fill(title);
    await this.saveButton.click();
  }
}

// テストでの使用
const todoPage = new TodoPage(page);
await todoPage.createTodo('新規Todo');

待機戦略

推奨: 条件による待機

await expect(element).toBeVisible();

要素が表示されるまで自動待機

非推奨: 固定時間待機

await page.waitForTimeout(3000);

不安定、テストが遅くなる

Playwrightの自動待機

// これらの操作は自動待機される
await page.click('button'); // 要素が表示・有効になるまで
await page.fill('input', 'text'); // 要素が編集可能になるまで
await expect(el).toBeVisible(); // 要素が表示されるまで

ベストプラクティス

推奨事項

  • ユーザー視点でテストを書く
  • シナリオ重視（一連のフロー）
  • Page Objectでロジック分離
  • 自動待機を活用
  • テストの独立性を確保

アンチパターン

  • 固定時間待機（waitForTimeout）
  • CSSセレクターの多用
  • テスト間のデータ依存
  • E2Eテストの過剰な追加
  • 実装詳細のテスト

まとめ

ピラミッドの頂点

少数・高価値なテストに絞り、主要フローを確実に保護

ユーザー視点

実際のユーザー操作をシミュレートしてテスト

Page Object

ページ操作を再利用可能なクラスに分離

セマンティックロケーター

getByRole等で壊れにくいテストを実現
