# アップグレード戦略

`Vue 3.2.45 -> 3.5.13` は major upgrade ではありませんが、`3.3`, `3.4`, `3.5` の 3 段階をまたぐため、実務上は「一括で行くか」「段階で刻むか」の判断が重要です。

## 結論の目安

- 小中規模、テストが厚い、依存が少ないなら `一括移行`
- 大規模、TSX/SSR/UI ライブラリ依存が多い、テストが薄いなら `段階移行`

## 判断表

| 条件 | 一括移行向き | 段階移行向き |
| --- | --- | --- |
| プロジェクト規模 | 画面数が少ない、責務が単純 | 画面数が多い、共有部品が多い |
| テストカバレッジ | 型検査、単体、E2E が揃っている | 手動確認依存が強い |
| 依存数 | Vue 周辺依存が少ない | Router / Store / UI / SSR / DevTools が多い |
| TSX 利用 | ほぼ使っていない | TSX が多い |
| SSR 利用 | CSR 中心 | SSR / hydration が重要 |
| 開発体制 | 専任で短期集中できる | 複数チーム並行で変更が入り続ける |

## 一括移行

### 向いている条件

- 依存ライブラリが少ない
- CI が強く、失敗原因をすぐ切り分けられる
- リリース窓が十分ある

### メリット

- 差分レビューが 1 回で済む
- 中間状態を長く抱えない
- ドキュメントと実装の整合が取りやすい

### デメリット

- 失敗時の切り分けが重い
- Vite / TS / UI ライブラリも同時に触ると爆発しやすい

### 推奨パターン

1. 先にツールチェーンだけ整える
2. Vue core を `3.5.13` に上げる
3. 破壊的変更修正をまとめて実施
4. 最後に `defineModel` などのコード改善を別コミットに分離

## 段階移行

### 向いている条件

- 業務影響が大きい
- UI ライブラリや SSR の依存が強い
- 開発が継続中で長いフリーズが難しい

### メリット

- 問題の発生点を version ごとに切り分けやすい
- 監視とロールバックの単位を小さくできる

### デメリット

- 中間状態の保守コストが増える
- CI とドキュメントの更新回数が増える

### 推奨パターン

1. `3.2.45 -> 3.3.latest`
2. `Reactivity Transform` / TSX / toolchain の調整
3. `3.3 -> 3.4.latest`
4. 削除 API 対応
5. `3.4 -> 3.5.13`
6. `useTemplateRef`, Reactive Props Destructure の採用可否を判断

## 実務上の意思決定ルール

### 一括移行を選んでよい条件

- `vue-tsc --noEmit`
- `npm run build`
- 主要 E2E

上記 3 点が日常的に安定していること。

### 段階移行を選ぶべき条件

- `Reactivity Transform` を使っている
- TSX が多い
- SSR hydration mismatch の既存負債がある
- UI ライブラリ major upgrade も同時に予定している

## 非推奨の進め方

- Vue core と UI ライブラリ major change を同時に実施する
- Vue core と Store major change を同時に実施する
- 監視項目を決めずに本番へ出す

## 現実的な推奨

多くの既存業務プロジェクトでは、以下が最も事故率が低いです。

1. `Node / Vite / plugin-vue / vue-tsc / TypeScript` を先に整える
2. Vue core を `3.5.13` へ上げる
3. 削除 API と TSX 問題を潰す
4. `defineModel`, `useTemplateRef` などのコード改善は別 PR に分離する
