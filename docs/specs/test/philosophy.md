# テスト設計思想

> **ドキュメント種別**: 設計ガイドライン（継続的にメンテナンス）

## 1. 概要

本ドキュメントは、プロジェクト全体のテスト設計に関する思想・方針を定義する。テストの目的、設計原則、各レイヤーの役割分担を明確にし、品質保証の一貫性を確保する。

## 2. テストの基本思想

### 2.1 テストの目的

| 目的 | 説明 |
|------|------|
| **品質保証** | ソフトウェアが仕様通りに動作することを保証する |
| **回帰防止** | 変更による既存機能への影響を早期に検出する |
| **設計改善** | テスト容易性を意識した設計を促進する |
| **ドキュメント** | テストコードが「動く仕様書」として機能する |

### 2.2 テストピラミッド

本プロジェクトは「テストピラミッド」の考え方に基づき、以下の比率でテストを構成する。

```
        /\
       /  \     E2E (少数・高コスト)
      /----\    39件 - 主要ユーザーシナリオ
     /      \
    /--------\  フロントエンド (中間)
   /          \ 92件 - コンポーネント・ストア
  /------------\
 /              \ バックエンド (多数・低コスト)
/----------------\ 175件 - 単体・統合テスト
```

| レイヤー | 特性 | 役割 |
|---------|------|------|
| 単体テスト | 高速・低コスト・多数 | ロジックの正確性を保証 |
| 統合テスト | 中速・中コスト・中数 | コンポーネント間連携を検証 |
| E2Eテスト | 低速・高コスト・少数 | ユーザー視点での動作を確認 |

### 2.3 設計原則

#### FIRST原則

| 原則 | 説明 | 適用 |
|------|------|------|
| **F**ast | テストは高速に実行できる | 単体テストは1秒以内 |
| **I**ndependent | テスト間の依存がない | 各テストは独立実行可能 |
| **R**epeatable | 何度実行しても同じ結果 | 外部依存をモック化 |
| **S**elf-validating | 成功/失敗が自動判定 | アサーションで検証 |
| **T**imely | 実装と同時にテスト作成 | TDD/テストファースト推奨 |

#### AAA パターン

テストメソッドは以下の構造で記述する。

```
Arrange（準備）: テストデータ・前提条件の準備
Act（実行）    : テスト対象の処理を実行
Assert（検証） : 結果の検証
```

## 3. テストレイヤーの役割分担

### 3.1 責務マトリクス

| 検証項目 | バックエンド | フロントエンド | E2E |
|---------|:------------:|:--------------:|:---:|
| ビジネスロジック | ◎ | - | - |
| データアクセス | ◎ | - | - |
| API仕様 | ◎ | - | △ |
| バリデーション | ◎ | ◎ | △ |
| 状態管理 | - | ◎ | - |
| コンポーネント描画 | - | ◎ | - |
| ユーザー操作 | - | △ | ◎ |
| 画面遷移 | - | △ | ◎ |
| 統合動作 | - | - | ◎ |

◎: 主担当 / △: 補助的に検証 / -: 対象外

### 3.2 カバレッジ目標

| レイヤー | 目標カバレッジ | 備考 |
|---------|---------------|------|
| バックエンド Service層 | 80%以上 | ビジネスロジック中心 |
| バックエンド Controller層 | 70%以上 | API仕様の網羅 |
| バックエンド Mapper層 | 60%以上 | 主要クエリの検証 |
| フロントエンド Store | 80%以上 | 状態管理の信頼性 |
| フロントエンド Component | 60%以上 | 描画・イベント処理 |
| E2E | - | シナリオベース（カバレッジ不問） |

## 4. テスト分類と命名規則

### 4.1 テスト分類

| 分類 | 説明 | 命名プレフィックス |
|------|------|------------------|
| 正常系 | 期待通りの入力で期待通りの結果 | `test_正常系_`、`should` |
| 異常系 | エラー入力でエラー処理が動作 | `test_異常系_`、`shouldThrow` |
| 境界値 | 境界条件での動作確認 | `test_境界値_`、`boundary` |

### 4.2 命名規則

#### バックエンド（JUnit 5）

```java
@DisplayName("正常系: 存在するIDでTodoが取得できる")
@Test
void getTodoById_正常系_存在するID() { ... }

@DisplayName("異常系: 存在しないIDでEntityNotFoundExceptionが発生")
@Test
void getTodoById_異常系_存在しないID() { ... }
```

#### フロントエンド（Vitest）

```typescript
describe('todoStore', () => {
  describe('fetchTodos', () => {
    it('正常系: APIからTodo一覧を取得できる', async () => { ... });
    it('異常系: API失敗時にエラーがセットされる', async () => { ... });
  });
});
```

#### E2E（Playwright）

```typescript
test.describe('Todo管理画面', () => {
  test('新規Todoを作成できる', async ({ page }) => { ... });
  test('Todoを削除できる', async ({ page }) => { ... });
});
```

## 5. テストデータ管理

### 5.1 データ管理方針

| 方針 | 説明 |
|------|------|
| **テスト独立性** | 各テストは独自のデータを用意し、他テストに依存しない |
| **クリーンアップ** | テスト後は状態をリセットし、副作用を残さない |
| **最小限のデータ** | テストに必要な最小限のデータのみ準備する |
| **意味のある値** | テストの意図が分かる値を使用する |

### 5.2 レイヤー別データ管理

| レイヤー | 方式 | 詳細 |
|---------|------|------|
| バックエンド | @Transactional + ロールバック | テスト後自動ロールバック |
| フロントエンド | モック / ファクトリ関数 | vi.mock, createTestTodo() |
| E2E | API経由セットアップ / beforeEach | テスト前にAPI呼出でデータ準備 |

## 6. モック・スタブ戦略

### 6.1 モック使用方針

| 対象 | モック化 | 理由 |
|------|:--------:|------|
| 外部API | ◎ | 不安定要素の排除 |
| データベース | △ | 統合テストでは実DBを使用 |
| 時刻 | ◎ | テストの再現性確保 |
| ランダム値 | ◎ | テストの再現性確保 |
| 他サービス | ◎ | 単体テストでの独立性確保 |

### 6.2 レイヤー別モック戦略

| レイヤー | モック対象 | ツール |
|---------|-----------|--------|
| バックエンド | Mapper（Service単体時） | Mockito |
| フロントエンド | API呼び出し、Router | vi.mock, MSW |
| E2E | なし（実環境） | - |

## 7. CI/CD統合

### 7.1 テスト実行タイミング

| タイミング | 実行テスト | 目的 |
|-----------|-----------|------|
| コミット時 | 単体テスト | 即時フィードバック |
| プルリクエスト | 単体 + 統合 | マージ前品質確認 |
| マージ後 | 全テスト（E2E含む） | リリース品質確認 |

### 7.2 失敗時の対応

| 状況 | 対応 |
|------|------|
| 単体テスト失敗 | マージブロック、即時修正 |
| 統合テスト失敗 | マージブロック、原因調査 |
| E2Eテスト失敗 | 警告、手動確認後判断 |
